「Kura-AI」项目中 Agent 采用了什么推理范式？如何设计的

⭐ Kura AI 项目链接：https://github.com/MarisaMagic/Kura-AI

0 前言

这是 Kura-AI 专题的第一篇。后面每一篇我会围着一个功能点或技术点展开：它要解决什么、我是怎么做的、为什么没换一种做法、落地时又补了哪些优化。

第一篇我想先回答最底层的问题：这个项目里的 Agent，我到底采用了什么推理范式？

先把结论放在前面。Kura-AI 的主干不是教科书里那种手写 Thought: / Action: / Observation: 的文本 ReAct，也不是 Plan-and-Execute，更不是 Multi-Agent 或独立的 Reflection 环。我选的是：

  • 主干：LangChain v1 create_agent 驱动的 Function-Calling ReAct——模型用原生 tool_calls 决定「调工具还是终答」，工具结果以 ToolMessage 回注，再进入下一轮推理；
  • 外壳：每轮进入循环前，用确定性代码做压缩、选档、读图、记忆预注入和本轮策略；循环内用工具配额与失败信号纠偏；高危 MCP 写入再插入人工确认；
  • 工具内子图：search_knowledge_base 内部是固定的 LangGraph RAG 流水线（检索 → 打分 → 可选改写 / 扩展）。主 Agent 只决定「要不要搜」，检索质量在工具里收口。

选型的第一约束来自产品形态。Kura-AI 是一个用户可配置的知识库对话智能体平台：模型、提示词、知识库、MCP 工具都由用户自己配。任务形态开放，流程不固定，中途改口、补图、换问法是常态。这种产品要的第一件事是灵活度，而不是「一次规划走完全流程」。后面的所有取舍，基本都从这句话出发。

flowchart TD
  userMsg[用户消息] --> prep[轮次脚手架]
  prep --> compact[会话压缩或滑动窗口]
  prep --> kbPick[知识库前置选档]
  prep --> vision[两阶段读图]
  prep --> memory[记忆预注入]
  prep --> policy[本轮工具策略]
  compact --> react[create_agent ReAct 循环]
  kbPick --> react
  vision --> react
  memory --> react
  policy --> react
  react --> decide{模型: 调工具还是终答}
  decide -->|tool_calls| exec[执行工具]
  exec --> observe[ToolMessage 回注]
  observe --> decide
  decide -->|无工具| answer[最终回复]
  exec --> mcpGate{高危 MCP?}
  mcpGate -->|需确认| human[人工确认后续跑]
  human --> react

1 功能设计：这一轮对话要完成什么

谈范式之前，我习惯先把「一轮对话」当成一份产品合同写清楚：它要完成什么、边界在哪、什么算做成。实现入口是 app/chat/agent_service.py 的 iter_chat_stream_events（生产流式路径）和 chat_with_agent_sync（同步兜底路径）。

1.1 边界：能做什么、不能做什么、什么算成功

我给一轮对话立了四条规矩：

  • 能做什么：按需调用知识库、联网搜索、会话记忆、附件读写、该智能体启用的 MCP 外部工具，流式给出带来源的回答。
  • 不能做什么：知识库检索与联网搜索同轮互斥，由对话页开关决定，后端也会校验；共享（非属主）会话默认不加载属主 MCP，避免发布者的凭据被别人的对话内容驱动。
  • 必须让位：高危 MCP 写入要用户确认一次才能执行；工具明确返回失败或无结果时，必须如实说「没搜到 / 打不开」，禁止编造来源、页面或知识库结论。
  • 什么算成功：用户能看到思考步骤、正文和来源；会话可续、可取消、可重生成；助手消息落库后，超出窗口的旧轮会归档进会话记忆。

这四条决定了后面所有设计。范式再漂亮，越了权、编造了来源、共享会话把属主的 MCP 跑起来了，都不算做成。

1.2 工具面：始终挂载，本轮用策略禁用

build_model_and_agent() 每一轮都会把整套工具挂上，而不是按开关动态增删：

能力 工具
会话附件 read / search / list_session_attachments_brief
联网 web_search、fetch_url、web_image_search
知识库 search_knowledge_base、search_knowledge_by_image
会话记忆 search_session_memory
外部能力 该智能体已启用的 MCP 工具

一个实现细节：TOOL_DISABLED_THIS_TURN 并不是什么命名常量，它只是几个禁用文案函数返回的字符串前缀。对我自己来说无所谓，但读代码的人搜这个标识时会扑空，所以专门说明一句。

为什么不按开关拆两套 Agent？我当时犹豫过，最后否掉了，理由有两条：少一次重建 tool schema 的成本；更重要的是，模型如果根本看不见某个工具，反而更容易幻觉出一次「调用」。把拒绝写成 ToolMessage，等于把纠偏信号留在 ReAct 自己的观察环节里。

工具描述本身也是指令。以知识库为例，search_knowledge_base 的 description 会写清：范围已由系统预选、只需传 query、引用必须带 [来源N]、同一轮最多成功检索一次。模型做选择时能看到的只有名称、描述和参数 Schema——这三样写含糊，后面再靠 system prompt 补救，效果通常不好。

1.3 提示词分层：人设进 System，本轮策略进 Human

系统提示由 _compose_system_prompt() 拼出来，只放两样东西：

  1. 智能体自己的人设（ua.system_prompt，空则回退 You are a helpful assistant.）；
  2. 本轮启用的检索纪律——开了联网就追加引用、失败码、禁止编造的条文；开了知识库就追加图片 Markdown 纪律和「无资料就拒答」。

本轮开关、选档范围、附件提示、记忆摘录、读图描述、MCP 批准备注，故意不进 System。它们由 _format_turn_context_block() 拼成「【本轮上下文（仅本回合有效）】」，再 _append_turn_context_message() 并进最后一条 Human。这块上下文不落库：下一轮重新算，人设不会被「本轮只许搜知识库」这种临时句子污染。

可以把它想成店员身上的工牌和柜台上的当日告示。工牌是人设，长期有效；告示是「今天只开知识库窗口、附件在 2 号柜、这张图系统已经预读过」，只对这一单生效。把告示写进工牌，过两天人设就脏了。

1.4 决策层次：模型选工具，工程层负责收口

工具「选谁、填什么参数」仍然由模型通过 Function Calling 自主决定。我没有另写一个路由 Agent。约束是分层叠上去的：

层次 机制
用户 / API use_knowledge_retrieval 与 use_web_search 互斥
提示 System 纪律 + Human 本轮上下文写明允许 / 禁止哪些工具
工具描述 名称、何时用、何时不要用、参数 Schema
运行时策略 禁用工具返回 TOOL_DISABLED_THIS_TURN
配额 每轮调用次数上限，防止 ReAct 空转刷 API
安全 高危 MCP 需确认；共享会话默认不加载属主 MCP
预处理 知识库选档缩小检索面，工具侧不再接收 file_key

2 实现思路：为什么是这套，而不是其它

2.1 主干为何选 Function-Calling ReAct

产品是开放对话，不是固定审批流。用户可能先问知识库里的一页 PDF，下一句改口要搜网上的最新版本，再补一张图问「类似的还有吗」。这种路径没法在进门时一次性画死，适合 ReAct 的「走一步看一步」。

为什么是 Function Calling 而不是经典文本 ReAct？我的理由很实际：

文本 ReAct 要模型按约定格式吐 Thought / Action，解析失败、字段对不齐是常态。原生 tool_calls 有 Schema，参数类型由运行时校验；前端流式里也能靠 tool_call_chunks 判断「这句话其实是在准备调工具」，把过渡句从正文迁进思考区（3.2 会展开）。对一个要流式展示、要展示来源、还要接 MCP 的产品，结构化调用比解析自由文本稳得多。

create_agent 还有一层工程收益：流式、取消、状态更新这些生产能力，运行时已经给了。自己用裸循环调模型，这些都得重做一遍。

2.2 为何不做成 Plan-and-Execute

Plan-and-Execute 的卖点是「先定完整计划，再按清单执行」，适合长流程、怕跑偏的任务。我没走这条路，主要是三件事对不上：

第一，用户每轮已经用开关框死了检索模式——只开知识库、只开联网、或者都不开。再单独养一个 Planner，先产出步骤清单，首 token 会更慢，而「本轮大致要干什么」其实已经被开关说完了。

第二，对话场景改口太频繁。计划刚写完，用户补一句「不对，看附件第 3 页」，清单就过期了。动态 Replan 能补弹性，但每步多一次评估调用，聊天体感会明显变钝。

第三，仓库里没有「先产出步骤列表再逐步执行」的规划模块。看起来最像规划的，是知识库前置选档（app/kb/kb_document_preselect.py）：子模型、temperature=0、结构化输出一组 file_key。它只缩小检索范围，并不拆任务、不调度后续步骤，不能算 Plan-and-Execute。

2.3 为何不做成 Multi-Agent，也不套独立 Reflection 环

一个用户配置的智能体，产品模型就是一个角色加一袋子工具。拆成 Researcher / Writer / Reviewer，交接上下文、对齐人设、分摊费用都会涨一截，调试时还多几条责任链。这和「自定义智能体中心」——用户改一份提示词、挂几个 MCP 就该能跑——合不上。

项目里确实有「子模型」（sub_model_name / sub_api_key）。它只打杂：记忆查询重写、知识库选档、RAG 打分 / 改写 / HyDE、会话压缩摘要、两阶段读图。调用方式是确定的函数调用，不是角色之间的 handoff，所以它不是 Multi-Agent。子 Key 配不齐就整份回退主配置，不混搭 endpoint：

独立 Reflection 环也没上。再套一轮「评估 → 不达标就重做」，至少多一次 LLM，聊天的首字延迟和费用都会线性涨。当前的质量策略更轻：

  • 提示词纪律要求引用编号与工具返回逐字对齐，失败码必须如实转述；
  • 工具侧给出 TOOL_CALL_LIMIT_REACHED、WEB_SEARCH_NO_RESULTS、KNOWLEDGE_BASE_NO_RELEVANT_INFO 这类可机读观察；
  • RAG 子图内部有打分与改写，那是工具里的局部自修正，不是对话级反思。

把延迟留给流式正文，比再请一个评审模型更符合对话产品。

2.4 为何不手写一张对话大图，LangGraph 用在哪

之前写 LangGraph 的时候说过：标准工具循环优先 create_agent，复杂业务拓扑才值得把节点和边摊开。Kura-AI 的难点在工具生态、记忆、多模态和安全，不在「采购审批那种确定性路由」。主对话如果画成大图，每加一个工具都要改边，用户自定义 MCP 更没法预画。

人工闸门也没有用 interrupt() 把整张图停住，而是 MCP confirmation：工具先返回「请确认」，前端展示 server / tool / 参数预览，用户批准后带 mcp_approved_pending_id 按 regenerate 续跑，注入的提示会写明已批准哪一笔、只允许立刻再调这一个工具一次（原文见 3.3）。

LangGraph 用在该用的地方。知识库检索步骤固定，还需要条件路由——初检 → 打分 → 必要时改写问句再扩检 → 二次门控，无资料就 no_answer 结束。这条链路封装在 app/kb/rag_pipeline.py，由 search_knowledge_base 在工具内部调用。主 Agent 仍然只做一件事：要不要搜。检索质量不交给它在对话循环里「再想想」。

补充一句：no_answer 不是具名常量，它是 RAGState 的一个字段加上条件边上的 route 字符串，工具侧看到这个结局就转成「知识库无相关资料」的拒答文案。

2.5 真正的设计点：ReAct 外套一轮次脚手架

如果只看 create_agent，Kura-AI 像一个普通的工具循环 Agent。真正把对话做稳的，是我在进入循环之前加的那层确定性准备，落在 _prepare_to_invoke_messages() 和 iter_chat_stream_events() 的前半段：

  1. 上下文：超长会话按字符预算压缩（摘要进 session metadata，原文窗口仍 append-only）；未开压缩时退回最近 N 轮滑动窗口。压缩同时受 CHAT_USE_SESSION_MEMORY 与 CHAT_COMPACT_ENABLED 双开关控制，关掉会话记忆时默认直接走窗口。
  2. 选档：子模型根据当前问题和最近对话，把知识库检索限定在相关 file_key；失败则回退全库，不阻断对话。
  3. 读图：本轮带图、模型支持视觉，且启用了知识库 / 联网检索或挂有 MCP 工具时，先做一次无工具的视觉预读，产出 caption；之后 Agent 全程纯文本，避免「看图 + 选工具」挤在同一次慢调用里。预读失败再回退成单阶段带图问答。
  4. 记忆：按最新输入做一次会话记忆预检索，摘录并进本轮 Human；仍不够，模型还可以再调一次 search_session_memory。
  5. 策略：把本轮允许 / 禁止的工具、选档范围、附件提示、caption、MCP 批准备注，写进最后一条 Human。

顺序就写在 _prepare_to_invoke_messages() 里：

流式路径里，选档和记忆预注入还会 asyncio.gather 并行，少掉一段串行等待。

这就是「全局确定性准备 + 单步 ReAct」。它不是三种教科书范式里的任何一个纯标签，而是按产品约束折出来的结构：重活尽量在 invoke 前和工具内做完，主循环保持简单，好流式、好取消、好解释。

3 优化：性能、体验、可靠性

脚手架和主循环能跑，还不等于能用。下面这些是已经落地的优化，不是规划。

3.1 性能与成本

主模型只跑 ReAct，打杂交给子模型。 记忆重写、选档、RAG 打分、压缩摘要这些任务对「聊天人格」没有要求，用 sub_model_name 配置的便宜模型即可；子 Key 配不齐就实时回退主配置，避免混搭出一套对不齐的 endpoint。

少一轮循环，比在循环里省 token 更划算。 web_search 提供 extra_query，鼓励一次调用跑两组检索（比如两种画风、两个关键词），少一次 ReAct 往返。配额上，知识库和记忆每轮各只许占用 1 次（按调用计数，发起即占位）；web_search 默认 2 次、fetch_url 默认 3 次、文字搜图默认 2 次——配置注释写得很直白：防 ReAct 循环刷限流。

工具始终挂载、用返回值禁用，避免每轮按开关重建 Agent，也给模型留下可观察的拒绝信号。

多模态只在需要时出现。 附件在库里存 image_ref 而不是 base64；两阶段读图成功后，后续 ReAct 不再带原图。即便走单阶段带图，一旦本轮已经出现 ToolMessage，message_codec.strip_image_urls_after_tools 也会把 Human 里的 image_url 换成短占位，避免第 2、第 3 次模型调用再传一遍大图（1.2 里那个 _StripImagesAfterTools middleware 挂的就是它）。

生产路径是 Redis Job SSE，不是只开一条直连 stream。 创建 Job 后订阅 GET /chat/jobs/{id}/stream?since_seq=，事件落在 Redis 里。刷新或短暂断线可以用 since_seq 续传，生成不会因为页面重载就丢。空闲轮询从 40ms 退避到 300ms，追加事件用 Lua 一次完成 RPUSH 和过期，避免每条事件打三次 Redis。全局还有 LLM_MAX_INFLIGHT（默认 8）做并发闸门，排队会以 queued 事件告诉前端。

取消检查必须节流。 流式循环按 chunk 频率走，但读 Redis 取消标记最多每 CHAT_CANCEL_CHECK_INTERVAL（默认 0.25s）一次。工具执行阶段往往没有 chunk，另外挂一个 0.3s 的 watchdog，命中就 cancel 掉 Agent 任务——否则用户点了停止，还要干等到当前工具跑完。

长对话用字符预算压缩，而不是永远只留最近 10 轮。 CHAT_COMPACT_TRIGGER_CHARS 默认 80000，触发阈值还计入 system 长度、工具估算和 headroom。摘要由子模型合并「已有摘要 + 被移出的旧轮」，写入 compact_states，并且按分支的 turn_key 前缀匹配，切到兄弟版本时尽量复用已有摘要。压缩失败则只截断、不写坏 metadata，下一轮再试。

3.2 体验

ReAct 对用户最不友好的一点，是「它在想，但界面像卡死」。我把循环拆成两条可见的流：

  • content：最终给用户看的正文；
  • thinking_item：思考时间线，step（选档、MCP 加载、读图、检索）和 text（工具调用前的过渡句）按发生顺序交错。

流式里一旦出现 tool_call_chunks，此前已经当正文流出的那截文字会被撤回，标上 moved_from_content 迁进思考区。这和 ReAct 的语义对齐：工具调用前的输出是 Reason，不是 Answer。前端 agentChatThinking.js 的 reducer 对话页和编辑器预览共用，历史回放优先读落库的 thinking_items（缺了才回退 rag_steps + thinking_text 合成）。

一个格式细节：moved_from_content 和 append 是 thinking_item 事件包络上的旗标，不在 item 内部；落库的 thinking_items 数组里只存 {type, text} 或 {type, icon, label, detail} 这样的纯内容项。

来源走统一的 sources 通道，知识库和联网互斥，不会在同一条回复里混两套编号。知识库图片必须原样复制工具给出的、带 exp / sig 的 /api/v1/media/ Markdown，禁止改写成外链或本地路径。

停止、重生成、MCP 确认都算体验的一部分。停止覆盖「正在调工具」的静默段；重生成在消息树上插兄弟版本，MCP 批准续跑则原地覆盖目标助手消息。确认卡片展示 server、工具名和参数预览，避免用户只看到一个「允许」按钮。

3.3 可靠性与安全

  • 循环硬封顶：recursion_limit: 30，再叠加每工具每轮配额，避免「再搜一次」递归到停不下来。
  • 失败必须可叙述：纪律条文点名 TOOL_CALL_LIMIT_REACHED、WEB_SEARCH_NO_RESULTS、WEB_IMAGE_SEARCH_FAILED、FETCH_URL_FAILED、TOOL_DISABLED_THIS_TURN 等。模型拿到的是观察，不是空白。
  • 降级优先于中断：MCP 单服务失败记一条 rag_step，不拆整轮对话；连接超时时用缓存的 schema 挂 stub 工具，避免工具表整表消失导致模型乱猜；选档、记忆重写、压缩、读图、网页重排失败，各自有 fallback（全库 / 原 query / 只截断 / 单阶段带图 / 原序）。
  • 非可信内容隔离：网页、MCP 返回、读图描述会套隔离块并截断，提示模型那些字符串不可执行、不可当系统指令。
  • MCP 确认：confirm_policy 为 auto / always / never；auto 按工具名启发式识别写操作。每轮待确认次数有上限，完全相同的调用会去重。批准记录带 TTL，续跑提示只授权那一次。未批准时工具返回观察而不是真执行：

批准后带着 mcp_approved_pending_id 续跑，注入提示的原文是：「用户已批准执行 MCP 工具 {server}/{tool} 一次。请立即调用该工具一次；不要调用其他高危工具。」——一次授权对应一次调用，批准记录取出即清。

  • 请求隔离：工具共享状态挂在 ContextVar 上，并发对话的 RAG 步骤、配额、待确认列表互不可见。
  • 共享会话默认关掉属主 MCP；LLM / MCP / 联网 URL 做 SSRF 校验。这些已经超出「推理范式」，但它们决定了 ReAct 被允许走到多远。

4 对照与收束

把教科书标签和 Kura-AI 实装置在同一张表里，会更清楚「我选的是哪一层，改的是哪一层」：

维度 教科书说法 Kura-AI 实装
主循环 ReAct：思考 → 行动 → 观察 Function-Calling ReAct，create_agent，recursion_limit=30
规划 Plan-and-Execute 先出步骤清单 无 Planner；用户开关 + 选档 + 本轮 Human 上下文
多智能体 Researcher / Writer 协作 单 Agent；子模型只打杂
反思 独立评估环或 Reflexion 错题本 提示词纪律 + 失败码 + RAG 子图内打分改写
LangGraph 对话主流程画成大图 主对话用 create_agent；RAG 固定子图藏在工具里
人工介入 interrupt() 整图暂停 高危 MCP 确认后 regenerate 续跑
上下文 越聊越长的线性历史 压缩摘要 + 滑动窗口兜底 + Milvus 会话记忆按需检索

一句话收束：Function-Calling ReAct 负责单步灵活度，轮次脚手架负责长上下文、检索范围、多模态和安全闸门，工具内子图负责检索质量。 三者叠在一起，才是 Kura-AI 现在的推理范式。
