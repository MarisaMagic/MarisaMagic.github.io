「Kura-AI」Agent 推理范式 Tool-Use-Loop 设计

0 前言

这篇文章讲的是 Kura-AI 对话智能体怎么推理：模型怎么一步步判断「还要不要再调工具，还是已经可以回答了」，以及这条循环外面还有哪些约束。

Kura-AI 选的是 Tool-Use-Loop（工具使用循环）。「下一步该干什么」交给支持原生工具调用（Function Calling）的模型自己判断；「这一轮能不能调、最多调几次、模型能看见哪些材料」则由服务端在本轮对话中进行约束。项目并没有使用手写 ReAct 文本解析，也没有先让模型写出完整计划再执行。

1 Agent 主循环

1.1 策略选择

对话智能体走的是 LangChain create_agent 驱动的 Tool-Use-Loop。模型通过原生工具调用决定下一步——调哪个工具、参数填什么，都写在结构化字段里，而不是混在一段自由文本中。工具跑完后，结果再喂回模型。模型觉得不用再调工具了，就输出正式回答。

1.2 如何实现

入口在 app/api/v1/user_agents/chat.py。日常对话走的是流式路径：chat_stream_endpoint → chat_with_agent_stream → iter_chat_stream_events。

真正把模型和 Agent 拼起来的，是 app/chat/agent_service.py 里的 build_model_and_agent。它用 init_chat_model（OpenAI 兼容协议）建好模型，带上工具列表和系统提示，再交给 langchain.agents.create_agent。

循环本身和工具执行都交给 LangChain / LangGraph，项目里没有另写一套调度器。

本轮如果开了知识库，循环通常走两轮就结束。模型不会输出 Thought / Action 这种文本，服务端也就没什么可解析的：

1.3 其它方案

  1. 手写 ReAct 文本循环（模型输出 Thought / Action / Observation，服务端解析后再拼回去）。

    • 优点：不依赖模型的 function calling，旧模型也能跑。
    • 缺点：现在主流 LLM 大多已经支持原生工具调用。自己写解析器，还要处理格式漂移、半截流式和多工具并行，实现成本高，后面也难维护。

  2. Plan-and-Execute（先单独用 Planner 列出完整步骤，再逐步执行，必要时再规划）。

    • 优点：更适合复杂的长任务。计划先写清楚，后面执行时不容易跑偏。
    • 缺点：多一次规划就要多调一次大模型，延迟更高，token 消耗也更多。Kura-AI 目前主要是知识问答这类相对简单的场景，每一轮真正要管住的，是检索互斥和工具次数——这些已经写在系统提示里了。对这种对话来说，用工具策略比再加一层规划更划算。

  3. Reflection（做完再检查：生成 → 评估 → 改进，给主循环加一层质量闭环）。

    • 优点：回答如果出现幻觉或明显错误，多一次 critic 评判可以把坏答案拦下来，让模型重写。
    • 缺点：不少工具内部已经有很明确的提示（比如知识库检索会告诉模型有没有资料、有没有超限、要不要待确认），系统提示也对回答可靠性做了约束。再加一层反思，等于 每轮多一次完整调用，延迟和 token 都会上去。另外，RAG 子图里的文档打分只服务 search_knowledge_base 内部，并不会约束外层最终回答。

2 工具策略

2.1 策略选择

Kura-AI 的做法是：工具列表始终挂在 Agent 上，本轮能不能用，靠策略拦住。组 Agent 时，知识库、联网、记忆、附件、MCP 会一次性交给模型。用户勾选的「本轮用知识库 / 用联网」并不会把工具从列表里拿掉；真正执行时，再按本轮开关和次数上限拦截。

2.2 如何实现

开关来自对话 API 上的 use_knowledge_retrieval / use_web_search。ChatRequest 在 schema 层就把它们设成互斥，两个不能同时为真。

真正起作用的地方分两层：

  1. 组装层在 build_model_and_agent。附件工具、web_search / fetch_url / web_image_search、search_knowledge_base、search_knowledge_by_image、search_session_memory 按配置往列表里加；MCP 外部工具作为 extra_tools 追加，按名字排序后交给 create_agent。
  2. 执行层在各工具函数内部。以 app/kb/search_tool.py 的 _search_knowledge_base 为例：先问 is_knowledge_allowed_this_turn()，再 try_acquire_knowledge_tool_slot()，两关都过了才跑 run_rag_graph。联网搜索的配额写在系统配置里，主要是防止模型在循环里反复刷接口被限流，默认 WEB_SEARCH_MAX_CALLS_PER_TURN=2。

工具本身用的是 LangChain StructuredTool，schema 给模型看。MCP 远程工具由 load_agent_mcp_tools 接入；单个服务挂了只记错误，不会把整轮对话打断。请求之间靠 app/chat/tools.py 的 _RequestState + ContextVar 隔离，并发请求彼此看不见。共享会话默认不加载属主的 MCP，避免别人的对话去驱动属主凭据。

还是「GPT Plus 年费怎么退？」这句。工具列表不会因为开关变化而拆掉。本轮如果只开了联网、没开知识库，模型仍然看得到 search_knowledge_base；真去调的话，拿到的是错误码，循环继续走，整轮不会 500：

本轮已经成功检索过一次，再调就会返回 TOOL_CALL_LIMIT_REACHED。系统会要求模型拿已有结果作答，而不是再搜一遍。

2.3 为什么这样做

延迟。 项目中不会按开关去重建 create_agent。工具 schema 保持稳定，模型就不用在「上一轮还有 web_search，这一轮突然没了」之间来回猜工具名。

可控，也省 token。 知识库每轮只允许成功占用 1 次，记忆检索同样 1 次；联网搜索、读页、搜图各自有上限。MCP 外部工具在系统里也有次数限制，避免模型在循环里反复调用。

失败怎么处理。 工具被禁用，或者次数用完，都返回带错误码的字符串（TOOL_DISABLED_THIS_TURN / TOOL_CALL_LIMIT_REACHED）。循环不会中断，模型被要求据此不再调用工具，而不是抛异常把整轮打掉。系统提示里的检索纪律会点名这些错误码，要求如实说「未找到」，而不是让模型编造来源。

2.4 其它方案

  1. 按开关重建工具列表。

    • 优点：schema 里就看不到它，模型自然调不到。
    • 缺点：build_model_and_agent 的注释写死了「检索工具始终挂载」。相邻两轮如果工具集合来回变，模型更容易编一个已经卸掉的名字。改成明确返回错误码之后，模型能在同一轮里不再调用这个工具。

  2. 硬拦截（一违规就抛异常，直接拆掉 create_agent 循环）。

    • 优点：服务端最省事，一次停干净。
    • 缺点：对话要的是「告诉用户这轮不能搜 / 已经搜过了」，而不是直接停止。错误码进 ToolMessage 之后，模型才有机会把它收成一句人话。

3 本轮上下文

3.1 策略选择

Kura-AI 把内容拆成两处：长期纪律放进 system，本轮材料接在用户原话后面。人设，以及「什么时候允许搜知识库、怎么标知识库来源」，写在 system_prompt 里。本轮选中的文档范围、附件提示、读图描述、记忆摘录，只接到最后一条 Human 上，只对这一轮有效。会话历史里留下的仍是用户原话；检索出来的、临时拼上去的附加材料，不会写进历史。

3.2 如何实现

先用 storage.append_messages 写入「GPT Plus 年费怎么退？」，再在 _prepare_to_invoke_messages 里把本轮材料拼到内存副本上。这份材料不会二次入库，也不会再开第二条 user 消息。

_compose_system_prompt 只拼人设和本轮检索纪律。本轮材料由 _format_turn_context_block 和 _append_turn_context_message 负责。知识库开启时，循环开始前会先跑 _run_kb_document_preselect_with_context，圈好 file_key，写进本轮块，同时注入 search_knowledge_base。之后工具侧不再让模型自己填检索范围。

发给模型的最后一条 Human 长这样。刷新页面再 load，历史上只剩第一句：

3.3 为什么这样做

把本轮的工具限制、知识库范围（如果有）写进 system_prompt 其实也能跑。最后没有这么做，主要是这几个原因：

  • 角色不一样。 system 放的是人设和长期纪律。知识库文档范围、读图结果、记忆摘录，是「这一问临时带上的材料」，更适合跟在用户问句后面。

  • 外部内容不该进 system。 读图描述、记忆摘录、用户上传的附件、超长上下文压缩出来的摘要，本质上都是外部拿来的文本。这些东西写进人设，模型更容易把它们当成指令。

  • 先用轻量子模型圈好文档。 主循环开始前，先用一次轻量模型调用，把检索范围定到例如 GPT-Plus退款说明.pdf，再写进本轮块并注入检索工具。主模型第一轮就可以直接搜，不用先空转一轮去试「该查哪几份文档」。

3.4 其它方案

  1. 本轮材料也写进 system_prompt。

    • 优点：每一轮都能在最前面看到，也不会写进历史。
    • 缺点：人设会被一份经常变动的清单撑得很长；外部文本进了 system，注入风险更大；做压缩时，这块临时内容还会被算进 system 长度。

  2. 另开一条 System / Human，并写入历史。

    • 优点：调试时能看见当时开了什么开关。
    • 缺点：压缩、记忆、重新生成时，系统会把这块当成用户真的说过的话。

收束

整条主路径可以看成三步：先决定这一轮模型能看见什么，再把工具列表交给 create_agent，最后用原生工具调用跑完这一轮循环。循环什么时候停，靠配额，以及模型自己判断「还要不要再调工具」。

graph TD
    A["对话入口 chat.py"] --> B["本轮上下文"]
    B --> B1["选文档 / 记忆预注入 / 读图描述"]
    B1 --> B2["并入最后一条 Human，不写会话历史"]
    B2 --> C["工具策略"]
    C --> C1["始终挂载 KB / Web / 记忆 / 附件 / MCP"]
    C1 --> C2["set_turn_tool_policy + 每轮配额"]
    C2 --> D["主循环"]
    D --> D1["create_agent invoke / astream"]
    D1 --> D2{"模型是否给出 tool_calls"}
    D2 -->|是| D3["工具执行：禁用或次数用完则返回错误码"]
    D3 --> D1
    D2 -->|否| E["助手文本写入历史"]
    D1 -->|"recursion_limit 或取消"| E
