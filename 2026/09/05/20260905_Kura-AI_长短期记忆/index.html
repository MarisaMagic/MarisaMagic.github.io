「Kura-AI」项目中长短期记忆是如何设计的

⭐ Kura AI 项目链接：https://github.com/MarisaMagic/Kura-AI

0 前言

这是 Kura-AI 专题的第 4 篇。第 1 篇写推理范式时，已经点过「会话压缩、记忆预注入、落库后归档」；第 2、第 3 篇分别写知识库怎么建、Agentic RAG 怎么搜。这一篇停在同一场对话内部：窗口越聊越长之后，什么留下给模型看，什么归档，怎么找回来。

先把结论放在前面。Kura-AI 的记忆是单会话内的三层，不是教科书 STM / LTM 的一对一翻译：

  • 原文树：PostgreSQL mg_chat_messages 保存这场对话完整长什么样，含重生成分叉；Redis 只缓存当前路径。UI 永远读这一层。压缩不删这里的任何一行。
  • 短时上下文：这一轮主模型实际看见什么。默认按字符预算触发：子模型把挤出窗口的旧轮写成摘要，摘要进会话行 mg_chat_sessions.metadata_json；送给模型的是现场拼出来的「摘要 + 近文原文」，这条摘要 Human 不落回消息表。关掉压缩才退回最近 N 轮滑动窗口。
  • 会话归档记忆：离开原文窗口的整轮原文切块，写入与知识库隔离的 Milvus 集合 kura_ai_chat_memory。压缩摘要本身不进向量库。进循环前预注入一小段，仍不够再调一次 search_session_memory。

跨会话「这个用户是谁」的长期画像故意没有做。产品是按智能体、按会话隔离的对话中心，不是全局私人助理。

flowchart TD
  user[用户提问] --> load[storage.load 当前路径]
  load --> compact[压缩视图或滑动窗口]
  load --> prefetch[记忆预检索]
  compact --> inject[摘录并进本轮 Human]
  prefetch --> inject
  inject --> react[create_agent ReAct]
  react -->|不够再搜| tool[search_session_memory 每轮一次]
  tool --> react
  react --> save[助手消息落库]
  save --> archive[后台归档离开窗口的整轮]
  archive --> milvus[Milvus kura_ai_chat_memory]
  milvus --> prefetch
  milvus --> tool

入库细节和第 1 篇的主循环范式只引用、不展开。知识库检索和记忆检索同构——hybrid、子模型打杂——但不复述第 2、第 3 篇。

1 先把「这场对话要记住什么」想清楚

谈压缩和向量之前，我先把「这场对话要记住什么」当成产品合同写清楚。读路径入口是 app/chat/agent_service.py 的 _prepare_to_invoke_messages；写路径入口是同一文件里助手落库之后的 schedule_archive_session_memory。

1.1 边界：能记住什么、不能做什么、什么算成功

我给一场对话的记忆立了四条规矩：

  • 能做什么：续聊时模型看见最近原文，外加一份可重放的压缩摘要；窗口外的旧轮可按当前问题预注入，或由 Agent 再搜一次；重生成、切分支时，共享前缀的摘要和向量能复用，旁支轮次不会串进当前回答。
  • 不能做什么：记忆不跨会话、不跨用户、不进知识库 collection kura_ai_kb。模型改不了 memory_scope。同一轮 search_session_memory 最多调用一次——槽位发起即占位、失败不释放；顺带说一句，工具 description 里对模型写的是「最多成功调用一次」，措辞比实现更严，两边口径不一致，读代码时留意。
  • 必须让位：压缩摘要失败时，本轮只截断原文窗口，不把半成品写进 metadata。没有 EMBEDDING_API_KEY 时，归档和检索整条跳过，对话仍能继续，只是早期事实找不回来。
  • 什么算成功：前端时间线仍是完整消息树；主模型上下文不随轮数线性膨胀；用户说「上次那个数」时，能从归档里捞回具体片段，而不是只剩一句「之前讨论过相关问题」。

这四条决定了后面所有设计。摘要再漂亮，把原文改没了、把兄弟分支的结论搜进来、没嵌入密钥就把整轮对话打成 500，都不算做成。

1.2 作用域是会话，不是用户

记忆设计的第一步不是选 Milvus，而是定作用域。Kura-AI 的隔离键只有一行：

三元组缺一不可。同一个用户开两个会话，记忆互不可见；同一个智能体被两个人用，也互不可见。删会话时必须先 purge_session_memory_vectors，再删 PostgreSQL 行——代码注释写的是「PG 会话行删除后无法再查 session_id」：会话行一删，就再也拼不出 scope 键，向量会变成没人能删的孤儿。

知识库用的是 kb_scope = u{uid}_a{aid}，少一维。那是「这个智能体的文档」，这份记忆是「这场对话被挤出窗口的旧轮」。两套 collection、两套生命周期，不能混。

1.3 一轮 = 一条 Human 及其后直到下一条 Human

压缩、归档、检索共用同一个切分：一轮从用户开口算起，收走后面的助手回复、工具调用、工具回注，直到下一条用户消息。app/chat/memory_turns.py 的 group_turns 是双指针，O(n)。

稳定身份不是「第 3 轮」这种下标。turn_key 取轮首用户消息的数据库行 id。重生成会在同一条用户消息下插兄弟助手版本，下标会漂，行 id 不会。压缩状态、Milvus 过滤、归档去重，都挂在这个键上。

path_ids 与消息不等长时返回空列表，调用方退回旧的下标逻辑。这是兼容，不是主路径。

2 实现思路，以及为什么不换

第 1 篇把记忆写成脚手架上的两步：压缩视图，再预注入。往下拆，每一步都是我在否决另一种更常见的做法。

2.1 短时上下文：怎么压缩，压完放哪

这里的「压缩」不是 gzip，也不是把旧消息从库里删掉。它是：估算即将送给主模型的 prompt 太长时，用子模型把挤出窗口的旧轮写成一份摘要；原文仍在消息表，摘要只写进会话元数据；这一轮真正发给 create_agent 的，是现场拼出来的视图。

主路径在 CHAT_USE_SESSION_MEMORY 和 CHAT_COMPACT_ENABLED 都开时，走 build_compacted_model_messages。

先分清三份东西

东西 存在哪 压缩会不会改它
用户 / 助手 / 工具的原文 mg_chat_messages（消息树，append-only） 不会。 UI 回看、重生成、事后归档都读这里
摘要文本 + 覆盖了哪些轮 同一会话行 mg_chat_sessions.metadata_json 会。 成功压缩才 patch_session_metadata
模型本轮看见的列表 只存在于这次请求的内存里 每轮重拼；那条 【会话压缩摘要】 Human 不 append_messages

主路径写入的 JSON 长这样，最多留 4 条（照顾重生成分叉）：

covered_turn_keys 是已经被摘要掉的那几轮的轮首用户消息行 id。旧字段 compact_summary + compact_until_turn_index 现在只当兼容层用：写入侧在拿不到 turn_keys 时才写它；读取侧更宽容一点——metadata 里根本没有 compact_states 列表时，旧字段会被惰性映射成一条 state，保证老会话升级后不丢摘要。

摘要不进 Milvus。向量库里是离开窗口之后的原文切块，和这份摘要是两条线：摘要保目标与约束，向量保「那个数是 0.37」。

怎么压

每轮进循环前跑一遍，步骤是固定的。

1. 按轮切开。 一轮 = 一条用户 Human + 其后直到下一条 Human 之前的助手 / 工具消息。

2. 读上次压到哪。 用当前路径的 turn_key 去 compact_states 里找最长前缀匹配，得到已有 summary 和 keep_from（从第几轮起仍保留原文）。没压过则 keep_from = 0，摘要为空。

3. 估算会不会爆。 用字符数，不接各家 tokenizer：

默认阈值 CHAT_COMPACT_TRIGGER_CHARS = 80000。不到阈值：不新压，只把已有摘要重放进去。

4. 超了，从尾巴往回留约 24000 字。 _choose_keep_from 从最新一轮往旧的加，加到超过 CHAT_COMPACT_KEEP_CHARS 就停（最新一轮即使超预算也保留）。中间那段 turns[旧 keep_from : 新 keep_from] 叫 dropped——只是不再放进模型上下文，不是从数据库删。

5. 子模型写新摘要。 _run_summarizer 把「已有摘要」和 dropped 的纯文本合成一份（输入侧先截到 60000 字），输出上限 4000 字。提示词要求保留目标、决定、未完成事项、文件名 / ID / 数字；禁止写入本轮检索开关、选档范围、附件列表。成功则写入 compact_states，keep_from 前移；失败则本轮只截断窗口，不改 metadata，下一轮再试。

6. 现场拼模型视图。

关掉压缩，才退回 apply_sliding_window_turns，只留最近 CHAT_MEMORY_WINDOW_TURNS（默认 10）轮，连摘要都不写。函数注释写的是：「主路径已改为按字符预算压缩（CHAT_COMPACT_ENABLED）；本函数仅作关闭压缩时的回退。」

用数字走一遍

假设已经聊了 20 轮，上次把 1–8 轮摘要过，窗口从第 9 轮开始。本轮估算 ≥ 80000：

  1. 从第 20 轮往回留到大约 24000 字，比如新窗口从第 14 轮起。
  2. 第 9–13 轮打成纯文本，和旧摘要一起交给子模型。
  3. 新摘要写入 mg_chat_sessions.metadata_json.compact_states，covered_turn_keys 变成第 1–13 轮的行 id。
  4. 主模型看见：摘要 Human + 第 14–20 轮原文。
  5. mg_chat_messages 里 1–20 轮一行都在。
  6. 助手落库后，归档线程才把已离开窗口、尚未进向量库的轮次写入 Milvus——那是下一节，不是压缩本身。
flowchart LR
  pg[mg_chat_messages 原文不动]
  meta[mg_chat_sessions.metadata_json]
  view[本次请求的模型视图]
  pg --> view
  meta -->|重放 summary| view
  pg -->|dropped 轮交给子模型| sum[新摘要]
  sum --> meta

不采用另外四条路。

永远最近 N 轮。 一轮里只要出现几次工具回注，10 轮的字符数就能把上下文撑满；早期约定、文件名、用户约束却整段消失。字符预算按「模型实际要吞多少字」触发，比按轮数公平。

只裁剪、不摘要。 窗口外的目标、未完成事项、关键实体会直接蒸发。摘要就是为了把这些留下来。

摘要覆盖原文。 UI 要回看，归档要按原文切块，重生成要保留旧分支。所以原文必须留在消息表，压缩只改 metadata 和模型视图。

按 token 精确计数。 要为每个供应商接 tokenizer，还要处理多模态占位。字符预算够用：阈值远大于保留窗口，中间留了 tools 粗估和 12000 字 headroom，宁早压、不踩上限。

2.2 不用 LangGraph Checkpointer 当短期记忆

create_agent 在 Kura-AI 里不带 checkpointer。会话真相在 app/chat/storage.py：消息是树，parent_id 指向上一行，selected_child_id 指向当前选中的孩子。重生成走 insert_assistant_version，在同一条用户消息下插入兄弟助手版本，并改选中指针；旧分支完整留着。

Checkpointer 按 thread_id 拍整张图的 State 快照，适合「同一条执行线程暂停再续」。它盖不住「同一会话多条分支、前端决定看哪条路径」。Kura-AI 要的短期记忆，是当前路径上的消息列表，不是 Agent 图的存档位。

这也是为什么第 1 篇把「暂停恢复」做成 Redis Job SSE，而不是 LangGraph interrupt()。记忆层和执行层拆开：消息树管对话版本，Job 管这一轮生成能不能续传。

2.3 长期是会话归档，不是用户 Store

离开原文窗口的整轮，才会进入 Milvus。窗口边界由 verbatim_keep_from_for_session 读取压缩状态；还在窗口里的轮次，模型已经看见原文，不必再向量化。

归档函数的注释几乎就是设计说明：

每轮先 turn_to_text：用户、助手、工具各有截断（8000 / 12000 / 2000 字），再按 CHAT_MEMORY_CHUNK_MAX_CHARS（默认 1400）切开。chunk_id 带会话摘要哈希和 turn_key，跨分支不撞车。嵌入与知识库同一套 qwen3-vl-embedding，写入独立集合 kura_ai_chat_memory。成功后把新 turn_key 并进 memory_archived_turn_keys。

db_models.py 里还留着一张 ChatMemoryCursor，按 last_archived_turn_index 记水位。代码已经不再读写它。下标水位过不了分支；改成 turn_key 集合之后，共享前缀自然幂等。

不采用另外四条路。

跨会话用户画像。 「不吃辣」这种偏好，下一场新会话默认不继承。产品的隔离单元是会话：删会话就要能删干净，共享智能体也不能把提问者的闲聊写进属主的长期档案。要做用户级 Store，作用域、权限、遗忘都得另开一层，现在没有这层需求。

和知识库共用 collection。 知识库是 L3 叶子 + L4 图片 + Auto-merge 父块，按 kb_scope 活到智能体被删。记忆是整轮对话切块，按 session_id 活到会话被删，还要带 turn_key。schema 和生命周期都对不上。

把压缩摘要当记忆正文。 摘要擅长目标和约束，不擅长「那个数是 0.37」。向量库存原文切块，检索才能把数字、人名、代码片段捞回来。

一落库就全量向量化。 窗口内的轮次已经在 prompt 里。提前嵌入只是重复付费，还让检索集合掺进模型本就看得见的近文，顶掉更早的命中。

2.4 读路径：预注入 + 一次工具

写入是增量归档，读出是两条互补通道，都只打当前路径上已归档的 turn_key。

预注入。 _prepare_to_invoke_messages 用本轮用户输入跑 proactive_session_memory_inject_text，默认 top_k=3。有命中就拼进最后一条 Human 的「本轮上下文」，不进 System，也不落库——和选档范围、读图 caption、MCP 批准备注同一条纪律。流式路径里，这段预检索和知识库选档 asyncio.gather，算过一次的结果用 skip_memory_retrieve 跳过第二遍。

工具。 search_session_memory 默认配置下始终挂在 create_agent 上（受 CHAT_USE_SESSION_MEMORY 门控，默认开）。工具描述把调用条件写死：指代在近文里找不到、追问早期事实、任务依赖多轮之前的上下文。近文已经有答案，或问题其实该走知识库 / 附件，就不要调。try_acquire_memory_tool_slot 每轮只许占用一次——发起即占位、失败不释放，超了返回 TOOL_CALL_LIMIT_REACHED。

检索本身比知识库子图薄。子模型先做查询重写，把「那个」「上次」补成可检索的主题；失败则退回原句。然后 dense + 服务端 BM25，RRF 融合。过滤表达式同时锁 memory_scope 和 turn_key 白名单；白名单为空时写成 turn_key in [-1]，保证一次都命不中，而不是退化成「整个会话随便搜」。

不采用另外三条路。

只预注入。 用户问法和归档用词对不上时，自动检索会空。工具是补救，也是模型看见「近文不够」之后的显式动作。

只靠 Agent 决定搜不搜。 多一轮 ReAct，首字延迟和工具配额都更贵。预注入把「很像在问旧事」的常见情况挡在循环外。

把 grade / rewrite 做成记忆子图。 第 3 篇的 RAG 子图要对付文档噪声和拒答。会话记忆的候选本来就是自己说过的话，重写加 hybrid 够用；再套一层打分，是在为少见的脏召回付固定税。

2.5 分支：turn_key 而不是 turn_index

对话页允许重生成。压缩、归档、检索如果按下标对齐，切到兄弟版本就会拿错摘要、搜到旁支里的结论。

三处都改挂 turn_key：

环节 怎么用
压缩 compact_states[].covered_turn_keys 必须是当前路径前缀；匹配最长的那条摘要
归档 chunk_id = mem_{digest}_k{turn_key}_c{ci}；已在集合里的 key 跳过
检索 archived_turn_keys_on_path = 当前路径 ∩ 已归档集合

共享前缀只摘要一次、只嵌入一次。旁支轮次可以继续躺在 Milvus 里，但过滤表达式进不去。切回那条分支继续聊，归档会从当时的窗口外接着做。相关行为钉在 tests/chat/test_branch_tree.py：前缀匹配、非前缀拒绝、空白名单命中不到任何行。

3 优化

脚手架能跑，还不等于长对话好用。下面这些是已经落地的，不是规划。

3.1 体验与延迟

预注入和选档并行。 流式路径里两段都要调子模型、都可能打外部服务。iter_chat_stream_events 用 asyncio.gather 包起来，少一段串行等待。第 3 篇写选档时提过同一处。

归档不挡 SSE。 助手正文先落库、先推给前端，再 schedule_archive_session_memory。默认 CHAT_MEMORY_ARCHIVE_ASYNC=true，daemon 线程跑嵌入和 insert。用户看见回复的时刻，不该排队等旧轮向量化。

思考区看得到记忆。 预注入、压缩、工具检索都会 emit_rag_step：预注入的步骤叫「会话记忆预注入」，压缩的步骤叫「会话压缩」（detail 是「已摘要较早对话，原文自轮次 N 起」），工具检索叫「会话记忆检索」。界面不是「后台悄悄丢了几轮」，而是能看到每一步。

3.2 性能与成本

热路径不再 describe collection。 ChatMemoryMilvusManager 在进程内记住 _init_done 和 _has_bm25。检索是对话热路径，不能每问都问 Milvus 一遍 schema。旧集合缺 BM25 时只走 dense，并打日志提醒跑 python -m app.chat.migrate_memory_bm25。迁移脚本拷标量和已有 dense，不重调 embedding。

同一轮 metadata 只读一次。 归档链路把 get_session_metadata 的结果传给 verbatim_keep_from_for_session 和已归档集合计算，避免压缩边界和水位线各查一遍库。

打杂不占主人格。 压缩摘要和记忆查询重写走 _sub_llm_config_from_ua，和第 1 篇的选档、RAG 打分同一套子模型配置。子 Key 配不齐就整份回退主配置，不混搭 endpoint。

配置旋钮集中在 app/settings/config.py，默认值本身就是在讲策略：总开关打开、压缩优先于滑窗、触发远大于保留、预注入比工具更窄、归档默认异步。

3.3 检索质量与降级

服务端 BM25 替换进程内词表。 旧实现把稀疏向量算在本地，进程重启词表会漂、IDF 会歪。现在和知识库一样，用 Milvus 的 bm25_fn。查询侧直接传文本。

单块不要太长。 1400 字的上限是在「一轮太长会变成一条什么都像的向量」和「切太碎会丢掉邻句」之间折的。Tool / AI 在入库前先截断，避免一次工具回注把整块占满。

失败必须可继续。 重写失败用原 query；压缩失败本轮只截断，下一轮再试摘要；没有嵌入密钥则预注入返回 None、工具返回「未配置嵌入服务」、归档直接 return。记忆是增强，不是对话的前置条件。

没有 TTL，也没有重要性衰减。遗忘的单位是会话：删会话，向量按 memory_scope 整段清掉。这和「作用域是会话」是同一条合同。

4 对照与收束

把教科书标签和 Kura-AI 实装置在同一张表里，会更清楚「我选的是哪一层，改的是哪一层」：

维度 教科书 / 常见做法 Kura-AI 实装
短期记忆 State + thread_id + Checkpointer 当前路径消息树 + 字符预算压缩视图
长期记忆 跨线程 Store / 用户画像 仅当前会话的 Milvus 归档，按 memory_scope 隔离
上下文治理 裁剪 / 删除 / 摘要三选一 原文永不因压缩删除；摘要进 metadata；旧轮原文另存向量
写入时机 「请记住」实时写，或后台抽偏好 离开原文窗口才增量归档，摘要本身不入库
读出时机 每次把 Store 全倒进 prompt 预注入 top 3 + 每轮最多一次工具
分支 通常假设单线程线性历史 turn_key 前缀匹配，旁支不可检索
与知识库 有时混进同一个向量库 独立 collection，生命周期跟会话走

三句话收束。

作用域先于数据库。 先回答「这条信息属于这场对话还是这个用户」，再选 PostgreSQL 还是 Milvus。Kura-AI 选了会话。

原文树和模型视图必须拆开。 UI、重生成、惰性重归档依赖完整树；主模型只能看见预算内的摘要加近文。用 Checkpointer 把两者捆成一份快照，分支会先裂开。

窗口外的事实用检索补，不用把历史全塞回 prompt。 摘要保目标，向量保细节，工具保漏网。三层叠在一起，才是项目里现在这套长短期记忆。

Agent 怎么推理、知识库怎么建、开了库之后怎么搜，前三篇已经写过。这一篇要收住的是：同一场对话变长以后，什么留下、什么归档、什么按需回来。
