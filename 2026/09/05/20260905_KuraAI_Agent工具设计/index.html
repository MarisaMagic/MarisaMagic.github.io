「Kura-AI」Agent 工具设计

0 前言

这篇文章讲的是 Kura-AI 对话智能体的工具怎么设计。

工具对模型是一份契约：LLM 决定调用什么工具、填写什么参数。首先是需要大模型拥有原生的 Function Calling 能力，其次还需要工具函数有完整的 name、description 和 args_schema。模型只负责决定调哪个工具、参数填什么。工具内部具体执行逻辑、次数上限、接口凭据都在服务端，模型既看不到，也改不了。

每个部分告诉模型「这轮该不该调工具」，分工是这样的：

  • System：主要包括预定人设和长期纪律。知识库开着时，它会告诉模型：引用要怎么标，工具报了错误码时该怎么跟用户说。
  • 本轮 Human：主要包括当前这轮对话允许调用哪些工具。如果有知识库检索，会展示只传 query 的提示和已经圈定的检索文档范围（由轻量级子模型调用得到）。这些部分会临时拼接到当前这轮对话 Human 消息的后面，但是不会持久化存储到数据库。
  • 工具 description / schema：主要是工具的说明书，包括什么时候该调、什么时候不该调、参数怎么填写。特别的，知识库检索工具没有 file_key 参数，文档检索范围在智能体启动前，就会通过一次轻量级子模型调用提前注入 RAG 检索流程。
  • 工具函数：LLM 如果调用了不该调用的工具，工具会返回 TOOL_DISABLED_THIS_TURN 或 TOOL_CALL_LIMIT_REACHED。

工具列表始终挂着，本轮能不能用靠返回值拦住。挂载策略不在这里展开。挂到 create_agent 上的工具分两类：系统自己带的，以及按智能体配置加载的 MCP。

系统工具

智能体的配置中启用了哪些 MCP 远程服务，就作为 extra_tools 追加进来；也可以自己填一个远程地址。下面是预置商店里已经接好的服务，一键添加即可。名字和参数表跟远端走，和系统工具重名就跳过。共享会话默认不加载属主的 MCP。具体怎么容错、怎么确认，第 4 节再写。

特别的，知识库检索范围选档、相关长期记忆预注入、附件图片的读取和内容理解，这些发生在智能体启动之前，不是工具。

1 大模型看见什么

1.1 策略选择

Kura-AI 把工具说明书写成两截。description 写清何时用、何时不要用、本轮有什么约束；schema 只留模型该填的字段。范围、开关、属主知识库是哪一个，都不交给模型。

本轮开了知识库的话，模型看见的 search_knowledge_base 只有一个参数：query。该查哪几份文档，对话开始前就已经由选档子模型圈好，写进本轮 Human，并注入工具闭包。主模型第一跳只需决定「要不要搜、搜什么词」。

1.2 如何实现

工具在 build_model_and_agent 里一次性拼好，按名字排序后交给 create_agent。该让模型填的字段就留在参数表里，不该填的关在闭包里。

以 web_search 为例，参数表中保留的参数除了 query，还有 freshness、site、extra_query。extra_query 写得很直白：同一意图的第二种说法，并行搜完再合并，不要为同一意图再调一次。

以知识库为例，make_search_knowledge_tool 的注释写明：前置选档注入 knowledge_base_document_filter，避免和前置范围冲突。模型看见的参数表只有 query。

description 会再补一句：「本回合可检索的文档范围已由系统预先确定，你只需传 query，不要尝试指定文件名或换库。」本轮 Human 里也会写同一句话，并列出已经圈好的 file_key。两处都是软约束；硬约束是 schema 里根本没有这个字段。

1.3 为什么这样做

少一个参数，就少一次幻觉。如果让模型自己填 file_key，它很容易编一个已经卸掉的文件名，或者跟前置选档对着干。范围放进闭包，主模型第一轮就可以直接搜，不用先空转一轮去试「该查哪几份文档」。

description 是模型选工具时真正会读的说明书。web_search 把「何时不要用」写进去，包括「知识库已经开了就别搜网」这个互斥的系统约束；search_session_memory 把「答案已经在近轮里就别调」写进去。这些话 System 里未必点得这么操作化，工具自己说更准。

1.4 其它方案

  1. 把 file_key / 本轮开关做成模型参数。

    • 优点：一张 schema 看起来更「完整」，调试时能看见模型想查哪几份。
    • 缺点：模型会填错范围、编文件名，或者跟前置选档打架。开关一旦交给模型，本轮互斥就从硬约束变成软请求。

  2. description 只写「搜索知识库」。

    • 优点：短，省一点 token。
    • 缺点：模型不知道何时不该调、调完该怎么引用、图片行能不能改写。这些细则只好全堆进 System，人设会被操作手册撑得很长。

2 返回值是给模型的下一句指令

2.1 策略选择

工具一律回字符串。其中知识库检索调用成功时带编号来源，失败时带稳定错误码。循环不会因为一次禁用或空结果停掉，模型被要求据此改口，而不是再猜一遍。

「GPT Plus 年费怎么退？」如果知识库里真没有退款说明，工具不会丢一段低相关摘录让模型硬编。二次检索和逐块打分都过不了，就回 KNOWLEDGE_BASE_NO_RELEVANT_INFO，并写明：如实告诉用户没有资料，不要引用片段，也不要编知识库结论。

2.2 如何实现

工具禁用和工具调用次数用完，文案出在 app/chat/tools.py。

知识库关掉时，知识库检索工具被禁用，此时如果调用知识库检索函数，会直接返回：

已经成功占用过一次再调，则是 TOOL_CALL_LIMIT_REACHED，并要求用已有结果作答。以图检索是个例外：超额码写成 TOOL_CALL_LIMIT（没有 _REACHED），上限等于当前会话里图片附件的张数；没有图片附件，第一次也会被拦住。

空结果也有稳定前缀。知识库二次门控失败是 KNOWLEDGE_BASE_NO_RELEVANT_INFO；联网搜不到是 WEB_SEARCH_NO_RESULTS，读页失败是 FETCH_URL_FAILED，搜图失败是 WEB_IMAGE_SEARCH_FAILED。这些码和 agent_prompt.py 里的联网纪律、知识库纪律点名对齐——System 要求模型按字面转述给人，不得编造来源。

成功时，知识库走 format_knowledge_retrieval_tool_output。正文按 [i] 文件名 (Page n) 编号，图片块额外给一行现成的 Markdown，括号里是带 exp 和 sig 的 /api/v1/media/ 地址。前端用来展示的 kb_sources，编号和这段正文一致。整段成功输出会包进非可信隔离；联网三件套和 MCP 字符串结果同样会隔离并截断。会话记忆的成功输出目前不包这层。

工具内部的异常也不会砸进 Agent 循环。检索出错时返回 知识库检索出错：{e} 这类字符串，循环继续，模型还有机会对人说一声失败。

2.3 为什么这样做

错误码是写给模型的下一句指令，不是写给日志的。Do not call ...、不得编造任何搜索结果，和 System 里点名的码对上，模型才知道该停、该改口、该如实说「没找到」。

编号来源是给引用用的。模型不必自己发明 [来源1]，也不必改写图片地址。图片行如果让模型拼接，它很容易把文档名、页码或 stored_relpath 填进括号里；工具把可复制的那一行写死，引用纪律才执行得下去。

返回字符串而不是抛异常，循环才能把这句话收成 ToolMessage。对话要的是「这轮不能搜 / 库里没有」，而不是前端一个 500 错误。

2.4 其它方案

  1. 失败就抛异常，拆掉 create_agent 循环。

    • 优点：服务端最省事，一次停干净。
    • 缺点：用户看不到「为什么没搜到」。对话要的是一句人话，不是把整轮打掉。

  2. 成功和失败都回 JSON，让模型自己拆。

    • 优点：程序好解析，字段整齐。
    • 缺点：模型还要再理解一套结构；流式路径上，一段带「下一步该怎么做」的纯文本反而更稳。前端需要的来源列表，走 _set_last_rag_context 这条侧信道就够了，不必塞进模型该读的那一串。

  3. 成功结果不编号，只丢原始片段。

    • 优点：格式简单。
    • 缺点：[来源N] 对不上，模型更容易改写链接或漏标出处。

3 工具函数自己检查开关和次数

3.1 策略选择

每个工具函数是同一套路：先问本轮开没开，再看次数还够不够，最后才跑检索或外部 API。这些检查写在工具函数里，不写在 LangGraph 图外，也不靠模型自觉。

3.2 如何实现

以 _search_knowledge_base 为例，开头先做两步检查：

过了这两关，才调用 run_rag_graph。联网三件套同样：先 is_web_search_allowed_this_turn()，再 try_acquire_*。知识库和记忆每轮只许成功占用 1 次；web_search 默认 2 次，web_image_search 默认 2 次，fetch_url 默认 3 次；以图检索跟会话里图片附件的张数走。附件三件套和 MCP 远程调用本身没有这套次数槽——MCP 高风险确认另有每轮上限。

这些计数挂在 _RequestState 上，经 ContextVar 按请求分发。并发对话互不可见，不会把别人的检索次数或 RAG 上下文串过来。每轮入口会清零计数，再 set_turn_tool_policy 写下本轮开关。没有「新建一个状态对象」的 API，靠清计数和改开关复用当前请求的那一份。

选档、记忆预注入、读图都发生在智能体启动之前。主模型看不见选档过程，也传不了 file_key。读图是两阶段 caption，不是再挂一把 read_image。

3.3 为什么这样做

函数里的检查和说明书必须对得上。description 写了「每轮最多一次」，函数就真的只允许成功一次；Human 写了「不要调 web_search」，函数就真的回禁用码。软约束负责指路，硬拦负责兜底。模型仍可能发出一次不该发的 tool_calls，但检索不会跑，外网也不会被刷。

状态按请求隔离，是因为工具函数可能跑在 to_thread 或执行器里。ContextVar 会把同一份 _RequestState 带过去，同步路径又在单线程内，所以跨用户串扰被挡住了。如果做成进程里一个全局计数器，两个人同时问「年费怎么退？」就会抢同一把槽。

3.4 其它方案

  1. 用 LangGraph middleware 统一计数。

    • 优点：工具函数更「纯」，只负责检索。
    • 缺点：不同工具的上限规则并不一样（知识库 1 次，以图检索跟附件张数走，联网走配置）。规则散落在中间件里，反而离 description 更远。Kura-AI 把规则放在函数里，和返回给模型的那句话写在一起。

  2. 进程级全局计数器。

    • 优点：实现短。
    • 缺点：并发请求会互相踩额度，RAG 上下文也可能串到别人的对话里。

4 MCP：同一套约定的外延

4.1 策略选择

外部工具也必须遵守这份契约：列表尽量稳定，失败回字符串，高风险先停下来。MCP 不是另一套 Agent，只是 extra_tools。单服务挂了不能把整张表拆掉，也不能让共享用户的一句话去驱动属主凭据。

4.2 如何实现

加载在 load_agent_mcp_tools。只拉该智能体已启用的服务；连不上时记下错误，对话继续。若缓存里还有上次成功的 schema，就挂一层 stub，调用时返回 MCP_UNAVAILABLE，名字和参数表还在。没有缓存，这个服务跳过，别的继续。工具名和内置九个名字冲突，或者彼此重名，直接跳过，避免把 web_search 换掉。

每把远程工具还会再包两层。_guard_mcp_tool_output 把字符串当非可信内容隔离、截断。wrap_mcp_tool_with_confirmation 看这是不是高风险写操作：annotation 里 destructiveHint 为真，或名字、描述命中 create / delete / push 这类词，就先不执行，返回 MCP_CONFIRMATION_REQUIRED pending_id=...，让模型停下来请用户确认。同一参数重复提交会复用已有 pending；本轮确认条数到顶，则回 MCP_CONFIRMATION_LIMIT_REACHED。

共享会话默认不加载属主 MCP。_mcp_tools_allowed_for 写得很清楚：这些工具带着属主预置的请求头，模型会自主调用。共享用户的对话或注入文本一旦能驱动它们，就是在用属主身份做事。默认关着，可用 SHARE_CHAT_ALLOW_OWNER_MCP_TOOLS 打开，但不推荐。知识库正好相反——共享会话仍检索发布者的库，只是不加载发布者的 MCP。

4.3 为什么这样做

模型已经见过这些工具名。服务抖动时如果整表消失，下一跳它仍可能编一个刚卸掉的名字。stub 留下 schema，回来的是一句带错误码的人话，和内置工具的禁用码是同一思路。

高风险确认把「先执行再解释」改成「先停再问」。远程工具的副作用在 Kura-AI 进程外面，回滚不了；返回确认码、等 pending_id 批准后再跑一次，比在 System 里写「请谨慎调用」要硬。

输出当非可信内容，是因为 MCP 回的是外部文本。它和知识库原文、网页正文一样，不能被模型当成新的系统指令。记忆检索目前没有这层包裹，因为它来自本会话已经归档的对话，不是外部服务。

4.4 其它方案

  1. MCP 挂了就从列表拿掉。

    • 优点：表里只剩活着的工具，模型不会点到死服务。
    • 缺点：相邻两轮工具集合来回变，模型更容易幻觉一个刚消失的名字。有缓存时挂 stub，比整表消失更稳。

  2. 所有 MCP 都弹确认。

    • 优点：副作用被一刀切拦住。
    • 缺点：只读查询也会打断对话。现在按 annotation 和写操作词表区分，只读的 get / list 不必每次停下来。

  3. 共享会话也加载属主工具。

    • 优点：被分享的人能用同一套外部能力。
    • 缺点：属主请求头会跟着模型走。对话内容或工具返回里的注入文本，就能以属主身份打到外部服务。默认关掉，就是为了挡住这条路。

收束

工具对模型是一份契约。模型只负责决定调哪个工具、参数填什么。参数表管能填什么，返回的字符串告诉模型下一步怎么接，检索范围和凭据焊在服务端，模型改不了。提示词只负责指路；不该调的工具真被点到了，由工具函数自己检查开关和次数，拦住以后检索不会跑。
