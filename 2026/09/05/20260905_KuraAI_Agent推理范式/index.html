「Kura-AI」Agent 推理范式：为什么用 Tool-Use-Loop

0 前言

这是 Kura-AI 专题的第 1 篇。后面每篇会拆一个功能点或技术点，讲我自己的项目：当初怎么想、为什么这么做、后来补了哪些优化。

Kura-AI 是一个知识库对话智能体平台。用户可以给智能体配模型、提示词、知识库和 MCP 工具，然后在多轮对话里让它按需检索、联网、读附件、调外部工具。产品形态一句话就能说清，推理层却必须先回答一个更硬的问题：智能体到底按什么逻辑「想」和「做」？

我之前写过一篇理论向的整理：《「AI Agent」Agent 的三大范式：ReAct、Plan-and-Execute 与 Reflection》。那篇把三种范式放在不同层次上看：ReAct 管单步灵活度，Plan-and-Execute 管长任务不跑偏，Reflection 管输出质量。落到自己的项目里，选型就不能再停在「三种都很好」——对话路径必须灵活，又不能无限烧 token，更不能编造检索结果。

Kura-AI 的选择很明确：主干是 Tool-Use-Loop（ReAct 的结构化后代），循环外包一层回合编排；局部借用轻量规划和人工确认，不上完整的 Plan 图，也不上终答级 Reflection。

1 想法与设计：先定「决策和执行的关系」

三种范式真正比的不是谁更先进，而是决策和执行怎么接在一起。Kura-AI 要接的是多轮对话，不是一条写死的流水线。

1.1 产品形态决定范式

用户丢进来的，可能是「这个文档第 3 节怎么说」，也可能是「帮我看看这张图是谁，再找几张类似的」，还可能中途改口、补一张附件、打开联网开关。工具集本身也不是固定的：知识库和联网按本回合互斥，MCP 按智能体配置动态挂上。

这种场景里，「先写出一份完整计划再逐步执行」往往是假需求。闲聊、单跳检索、搜图、读附件，经常走完一步就该收束；硬拆成五步计划，只会多一次强模型调用，换不来更可控的结构。走一步看一步、每步根据工具结果再决定下一步，才对得上真实对话。

所以主干选 ReAct 的现代形态：模型用原生 tool_calls 决定「继续行动」还是「给出最终答案」。README 里写的「基于 Tool-Use-Loop 自主规划」，指的就是这件事——规划发生在每一步的工具决策里，不是单独的 planner 节点。

1.2 为什么不上完整的 Plan-and-Execute

Plan-and-Execute 适合「写一份竞品报告」「把需求拆成开发清单」这类长流程：先定结构，再分步执行，规划与执行可以换不同模型。Kura-AI 当然也能接到这类任务，但它的主路径是对话回合，每回合的目标、可用工具、甚至检索范围都可能变。

如果每回合先让模型出一份计划再执行，我会立刻碰到三个问题：

  • 多数回合只有一两次工具调用，计划阶段的延迟是纯开销；
  • 计划刚写完，用户下一句就改了目标，计划作废；
  • 知识库范围、联网开关、MCP 是否批准，都是回合级事实，不该提前写进一份「全局计划」。

我没有把「规划」整个扔掉，只是把它降到更便宜、更局部的位置：回合开始前，用子模型做一次知识库选档，把检索圈进若干 file_key；模型在循环里自己选工具。这不是 planner / executor 两张图，是循环外的路由。

1.3 为什么不上完整的 Reflection

Reflection 能抬质量，代价也清楚：至少多一次评估调用，首字延迟和费用一起涨。Kura-AI 的对话要流式出字，思考区还要把检索步骤实时推给前端。再套一轮「生成 → 评估 → 重写」，体验上很难接受。

质量我改用更便宜的约束：

  • 系统提示里写死引用纪律和失败码处理，搜不到就说搜不到，禁止把常识冒充检索结果；
  • 工具返回 TOOL_CALL_LIMIT_REACHED / TOOL_DISABLED_THIS_TURN / KNOWLEDGE_BASE_NO_RELEVANT_INFO，把模型推回最终回答；
  • 知识库工具内部另有一套打分 / 改写 / 再检索的小图，那是检索质量环，不是对终答做自我批评。

一句话：前两者的核心是「把事做完」，Reflection 的核心是「把事做好」。Kura-AI 先保证回合能稳稳做完，质量靠纪律和守卫，而不是再请一个评审模型。

1.4 真正做的「规划」

如果一定要给 Kura-AI 的推理层贴标签，我会写成三层，而不是某一个教科书名词：

「自主规划」落在内层：模型看工具 schema 和本轮上下文，自己决定调不调、调哪个。外层是系统替模型做的事，避免把选档、压缩、读图都塞进同一个 ReAct 循环里空转。MCP 高危工具则停下来等人点一次，再带着批准记录续跑——这是人在环上，不是动态 Replan。

2 实现思路：一轮对话怎么跑完

2.1 先看整条链路

前端主路径走 Job + SSE：POST /api/v1/user-agent/chat/jobs，再订阅事件流。真正干活的是 iter_chat_stream_events；同步接口走同一套准备逻辑，只是最后 invoke 而不是 astream。

flowchart TD
  userMsg[用户消息] --> policy[本轮工具策略 KB与联网互斥]
  policy --> prefetch[并行预取: 知识库选档 + 记忆预检索]
  prefetch --> vision[可选两阶段读图]
  vision --> compact[压缩或滑动窗口]
  compact --> turnCtx[本轮上下文并入最后一条 Human]
  turnCtx --> loop[create_agent Tool-Use-Loop]
  loop -->|tool_call| tools[内置工具或 MCP]
  tools --> guards[每轮次数守卫]
  guards --> loop
  loop -->|final_answer| stream[SSE: thinking_item / content]
  stream --> persist[落库 thinking_items / sources]

读图不进主循环：先无工具看图，写出一段描述，再让 Agent 吃纯文本往下走。这样后面每一跳工具调用都不必再带原图。

2.2 回合策略：工具始终挂上，用政策开关

知识库和联网在请求里互斥。实现上我没有按开关动态删工具——每轮重绑 schema，模型侧的工具列表会抖，也更难复用缓存。做法是工具始终挂载，本轮禁用时由工具函数返回 TOOL_DISABLED_THIS_TURN，同时在最后一条 Human 里写明「本轮允许 / 不要调用哪些」。

系统提示本身很克制：人设来自智能体配置的 system_prompt，空则回退 You are a helpful assistant.；只有打开对应开关，才追加联网纪律或知识库纪律。没有手写 Thought: / Action: / Observation: 文本协议。「怎么想」主要靠 tool schema、本轮上下文和失败哨兵。

2.3 组 Agent：把循环交给 create_agent

构建入口在 build_model_and_agent。模型用 OpenAI 兼容的 init_chat_model，再交给 LangChain 1.x 的 create_agent。底层是 LangGraph 的原生 tool-calling 图：有 tool_calls 就进工具节点，没有就结束。

挂上去的能力可以分成五类，点到职责即可：

  • 知识库：search_knowledge_base、search_knowledge_by_image
  • 联网：web_search、fetch_url、web_image_search
  • 记忆：search_session_memory（窗口之外的归档轮次）
  • 附件：检索片段、读正文、列清单
  • MCP：按智能体已启用服务动态加载；共享会话不加载属主凭据，避免别人的对话驱动你的钥匙

循环本身的硬上限写在 invoke config 里：

没有经典 AgentExecutor 那种 max_iterations。模型不再发 tool_calls，图就停；万一它在配额里换着 query 空转，30 步会被 LangGraph 打断。

2.4 组上下文：压缩、记忆、本轮块，都不落进「用户原话」

送给模型的消息，不是数据库里的原文照搬。_prepare_to_invoke_messages 按这个顺序准备：

  1. 开了会话记忆和压缩，就按字符预算做会话摘要，旧轮变成一条「【会话压缩摘要】」；否则退回滑动窗口。
  2. 用当前问题做一次记忆预检索，把较早轮次的摘录拼进本轮上下文。
  3. 需要带图时展开多模态；两阶段读图成功则不再带原图，只带 caption。
  4. 把「本轮上下文」并进最后一条 Human。这块只对当前 invoke 有效，不写回消息表。

本轮块里会写清：知识库和联网谁开谁关、选档后的 file_key、附件列表、读图描述、记忆摘录、以及「用户刚批准了某个 MCP 工具，请立刻调用一次」。系统提示保持稳定，回合差异全部压到最后一条用户消息上——这是有意的：人设不该每回合改写，政策却必须每回合生效。

流式路径里，选档和记忆预检索会 asyncio.gather 一起做，避免用户干等两段串行 LLM。

2.5 循环内：原生 function calling，项目只做分流

继续还是结束，项目没有再包一层 router。规则就是模型自己的 tool-calling：

  • 返回带 tool_calls 的 AIMessage → 执行工具，结果变成 ToolMessage 再进模型；
  • 返回没有 tool_calls 的文本 → 图结束，这段文本就是终答。

项目侧要处理的是展示。流式消费 agent.astream(..., stream_mode="messages") 时，一旦某条 chunk 带上 tool_call_chunks，此前当正文流出的过渡句会从答案里搬回思考区（moved_from_content）。用户看到的是「先出现一句『我先去知识库查一下』，随后这句话收进思考胶囊，正文只留最终回答」。

思考区本身是一条有序时间线 thinking_items：选档、记忆预注入、MCP 加载、读图、检索步骤、工具前导句，按发生顺序交错。历史回放优先读落库的这条时间线，而不是事后拼 rag_steps + thinking_text。它是过程可观测，不是模型隐藏的思维链——API 的 reasoning token 不会进这个区域。

2.6 结束：来源、确认、落库、归档

循环停下来之后，还会做几件循环外的事：

  • 知识库和联网的来源合并进统一的 sources，前端用来画引用；
  • 高危 MCP 若被拦截，SSE 打出 mcp_confirmation_required，本轮先停。用户点允许后，带着 mcp_approved_pending_id 再开一轮 regenerate，提示词里写「请立即调用该工具一次」；
  • 助手消息连同 thinking_items、rag_steps、sources 落库；
  • 被挤出原文窗口的轮次，后台切块写入会话记忆，供下一轮预注入或 search_session_memory 召回。

到这里，一轮对话才算完整。内层循环负责「想下一步」，外层负责「这一轮的边界、上下文和人机交接」。

3 优化：把 ReAct 的已知毛病补上

理论文里 ReAct 有两个经典坑：长流程走着走着忘了目标，以及在某一步陷入无效循环。再往工程上推一步，还有第三件事——历史一长，每步都把完整上下文带上，token 按步数线性涨。Kura-AI 没有换范式，是在同一条 Tool-Use-Loop 上补约束。

3.1 防空转：配额比「再检测一次循环」更管用

没有做「相同工具 + 相同参数」的通用循环检测。更有效的是每工具每轮配额，到上限就返回哨兵，让模型改去写最终答案。

工具 每轮上限 用意
search_knowledge_base 1 检索一次，带着结果作答
search_session_memory 1 窗口外记忆补一刀即可
web_search / web_image_search 2 防 ReAct 刷搜索限流
fetch_url 3 允许精读，但不许连环打开
search_knowledge_by_image 不超过会话图片数 有图才有额度
MCP 待确认 最多 3 条 同一 (tool, args) 去重

联网搜索的注释写得很直白：限制次数是为了「防 ReAct 循环刷限流」。配额用完不是杀进程，是把球踢回模型——再配上 recursion_limit=30，最坏情况也有硬切。

3.2 防上下文爆炸：压缩窗口，原文只增不改

存储层保留当前对话分支的全文，裁剪发生在调用模型之前。默认按字符预算压缩：旧轮收成稳定摘要，最近一段原文留下；压缩失败则本轮硬截，不写坏 metadata。关掉压缩时，退回最近若干轮滑动窗口。

被挤出窗口的内容不是扔掉。回合结束后异步归档到向量记忆，下一轮用预注入和工具两条通道召回。预注入最多带几条摘录，不够再让 Agent 自己调 search_session_memory。这样 ReAct 每一步看到的是「摘要 + 近文 + 必要时的记忆命中」，而不是越聊越长的全文。

3.3 成本：主模型跑循环，杂活用子模型

Plan-and-Execute 有一个隐藏优势：强模型规划、弱模型执行。Kura-AI 没有拆成两张图，但把同一思路用在循环外的杂活上。智能体可以单独配 sub_model：选档、会话压缩、记忆查询重写、RAG 打分和改写，都走子配置；缺省再回退主模型。主模型只负责 Tool-Use-Loop 里那些「下一步调谁、最终怎么答」的决策。

首包延迟也按这个思路削：选档和记忆预检索并行；读图从循环里拆出去，避免后面每一跳工具调用都带着原图。出过 ToolMessage 之后，模型输入会去掉 image_url，带图对话才不至于在第二轮工具调用时把上下文打爆。

3.4 可观测与可中断

对话页上的思考胶囊，不是装饰。thinking_items 按时间线落下，刷新历史还能展开当时的选档、检索和读图。调试时还可以打开完整 LLM 入参打印，但那只进终端，不进用户界面。

取消也不能只看文本 chunk。工具执行阶段往往没有新 token 流出，所以另有一个看门狗周期探取消标记，命中就取消生成任务。用户点停止卡在「正在搜」里，是 ReAct 产品里很常见的体验坑，必须在循环外补一刀。

MCP 则是另一类中断：读操作可以自动跑，写操作和高危工具默认先拦截。确认策略按服务配置，也可以全局关掉。这和 Cursor Plan 模式里的人工闸门是同一类东西——不是换范式，是给行动加上批准。

3.5 检索幻觉：失败也要有协议

工具循环最容易演变成「没搜到就编一个」。Kura-AI 把失败变成协议，而不是让模型自由发挥。联网纪律要求：看到 WEB_SEARCH_NO_RESULTS / FETCH_URL_FAILED 这类哨兵，必须如实告诉用户没找到或打不开，不得编造链接和正文。知识库纪律同样：无资料就说无资料，常识推断不得冒充知识库结论。引用必须带 [来源N]，编号和工具返回对齐，图片地址还要求原样复制，禁止改写成另一套 URL。

这些约束写进 system prompt，看起来像「提示词工程」，实际是在补 ReAct 没有的验收标准：行动可以失败，失败之后的话术不能失败。

4 收束：生产里的混合，不必堆满范式

如果把 Kura-AI 硬套回三种范式的选型表，我会这样填：

  • 单步行动：ReAct / Tool-Use-Loop，用 create_agent 落地；
  • 轻量规划：没有全局 Plan 图，但有回合前的知识库选档，以及工具内部的 RAG 改写；
  • 质量：没有终答 Reflection，用引用纪律、失败哨兵和次数守卫代替；
  • 意外与权限：MCP 确认是 HITL，不是动态 Replan。

这和我在理论文末尾写的「生产级混合」并不矛盾。那句话是「全局计划 + 单步 ReAct + 整体 Reflection」。Kura-AI 按产品形态做了裁剪：单步 ReAct 留下，全局计划收成选档，整体 Reflection 先不加。 工程开发永远是够用就好——先让循环稳、可见、可停，再根据真实延迟和费用决定要不要加更重的结构。

后续几篇会沿着这条循环往外拆：会话记忆怎么归档和召回、MCP 确认如何回到同一条对话、知识库选档为什么要放在 Agent 之前。那些是这条范式上的零件，不是另一套大脑。
