「Kura-AI」项目中 Agentic RAG 是如何设计与实现的

⭐ Kura AI 项目链接：https://github.com/MarisaMagic/Kura-AI

0 前言

这是 Kura-AI 专题的第 3 篇。第 1 篇写的是对话 Agent 的推理范式：主干是 Function-Calling ReAct，知识库检索藏在 search_knowledge_base 的 LangGraph 子图里。第 2 篇往上游走，写多模态知识库怎么建——L1 / L2 / L3 文本树、独立 L4 图片、Milvus hybrid、先处理后替换。这一篇停在在线路径：用户开了知识库开关之后，一次提问如何变成「可拒答、带来源的回答」。

入库细节和第 1 篇的主循环范式只引用、不展开。

先把结论放在前面。Kura-AI 的 Agentic RAG 不是教科书里那种每问必 embed、必 top-k、再拼进 prompt 的 Naive RAG，也 不是 Self-RAG / CRAG 那种把 grade、rewrite 拆成主循环里的一串工具。它是两层：

  • 外层：主 Agent 只决定「要不要搜、用什么 query」。每轮 search_knowledge_base 最多成功一次；选档范围在进循环前锁定，工具没有 document_filenames 参数。
  • 内层：app/kb/rag_pipeline.py 固定子图负责检索质量——hybrid 召回 → 可选 rerank → Auto-merge → 逐块打分 → 必要时改写再扩检 → 二次门控拒答。
  • 旁路：search_knowledge_by_image 是轻量子图（解析附件 → dense 以图检索），额度与以文检索独立。

Kura-AI 是用户可配置的知识库对话智能体：模型、提示词、知识库、MCP 都由用户自己配。知识库和联网同轮互斥。闲聊、改口、补图是常态。这种产品要两件事同时成立——不该搜的时候别硬搜，搜了就必须能诚实说「库里没有」。

flowchart TD
  user[用户提问] --> switch{本轮开知识库?}
  switch -->|否| reactNo[ReAct 不调 KB 工具]
  switch -->|是| preselect[前置选档]
  preselect --> react[create_agent: 要不要搜]
  react -->|调 search_knowledge_base| subgraph[LangGraph RAG 子图]
  subgraph --> initial[retrieve_initial]
  initial -->|有结果| grade1[逐块打分]
  initial -->|空| rewrite[改写策略]
  grade1 -->|任一相关| format[格式化片段加来源]
  grade1 -->|全不相关| rewrite
  rewrite --> expand[HyDE 或 Step-back 扩检]
  expand --> grade2[二次门控]
  grade2 -->|通过| format
  grade2 -->|仍无关| refuse[KNOWLEDGE_BASE_NO_RELEVANT_INFO]
  format --> answer[主模型终答加来源N]
  refuse --> answer

1 功能设计：这一轮知识库问答要完成什么

谈子图之前，先把「开了知识库的一轮对话」当成产品合同写清楚。实现入口是 app/kb/search_tool.py 的 make_search_knowledge_tool（工具）和 app/kb/rag_pipeline.py 的 run_rag_graph（子图）。进循环前的选档在 app/chat/agent_service.py 的 _run_kb_document_preselect_with_context，真正圈 file_key 的是 app/kb/kb_document_preselect.py。

1.1 边界

  • 能做什么：按需以文检索本智能体知识库（叶子 L3 文本 + L4 图片）；可选以会话附件做以图检索；回答带来源编号，图片给出可原样复制的签名 Markdown。
  • 不能做什么：知识库与联网搜索同轮互斥，对话页开关决定，后端也会校验。共享（非属主）用户能问不能改库。模型不能在 ReAct 循环里改检索范围。以文检索每轮最多成功一次。
  • 必须让位：两次检索加逐块打分仍无关，必须返回拒答码，禁止在低质量片段上硬编知识库结论。
  • 什么算成功：思考区能看到选档、召回、Auto-merge、打分、改写；正文用 [来源N] 对齐工具编号；无资料时用户看到「知识库中没有相关资料」，而不是一段像模像样的胡话。

这四条决定了后面所有设计。召回再漂亮，每问都塞一堆无关片段、模型把检索范围改飞、没资料还硬编出处，都不算做成。

1.2 三道门，而不是每问必搜

Naive RAG 只有一道门：来了问题就检索。Kura-AI 在主模型看到工具之前，已经过了两道确定性门；第三道才交给它。

第一道：本轮开关。 use_knowledge_retrieval 为假时，工具仍挂在 create_agent 上——第 1 篇写过「始终挂载、用返回值禁用」——但函数里直接返回 TOOL_DISABLED_THIS_TURN：

模型「看得到」Schema，调用会被策略挡住，并得到一句可机读的观察：「这轮别调这个」。知识库开着、联网关着时，本轮 Human 上下文会把这件事再说一遍；反之一样。两套检索工具同轮互斥，不是靠模型自觉。

第二道：前置选档。 流式路径里，选档和会话记忆预注入 asyncio.gather 并行，不挡在同一条串行链上。选档本身是确定性函数，不是 Agent 的一步：

规则压成四条：

库里有几份文档 行为
0 全库（空结果）；不阻断对话
1 自动限定到这一份，不调模型
多份 子模型 temperature=0 结构化输出 file_keys，最多 10 个（KB_MAX_DOCUMENT_FILTER）
关闭 / 无 Key / 模型失败 / 空数组或对不上白名单 回退全库

选档提示里写得很直白：前序对话只用来消解指代，仍以当前用户问题为主；拿不准就返回 []。圈出来的 file_key 必须从列表原样复制，再和 PostgreSQL 里的文件名集合求交。过不了白名单的字符串直接丢掉。

第三道：主模型决定要不要搜。 工具只收一个参数：

没有 file_key，没有 top_k，没有「换一个库」。范围已经由第二道门锁进闭包 knowledge_base_document_filter。主 Agent 要做的，只是「这轮要不要调、query 写成什么」。调成功一次之后，再调会拿到 TOOL_CALL_LIMIT_REACHED，提示用已有结果终答。

三道门叠在一起，才是「Agentic」在这个项目里的含义：不是模型无限次检索，而是系统先框死范围和次数，模型只在框里决定搜还是不搜。

1.3 子图合同：工具内部的固定流水线

主 Agent 调了 search_knowledge_base 之后，质量不交给它「再想想」。run_rag_graph 跑一张编译好的 LangGraph，节点和边是写死的：

注意图里没有真正的 generate 节点。generate_answer 指向 END：子图只产出 docs、context、rag_trace 和可选的 no_answer。最终回答仍由外层 ReAct 读 ToolMessage 之后生成。这和「把 RAG 做成一条 RetrievalQA 链、生成也包在链里」不是一回事。

初检走 retrieve_documents。默认 top_k=5，先召回 candidate_k = max(top_k * 3, top_k) 再截断。过滤表达式绑死 kb_scope，叶子层是 L3 文本加 L4 图片；若选档给了文件名，再加 filename in [...]。向量侧是第 2 篇建好的那套：dense HNSW（内积）+ 服务端 BM25，RRF 融合；失败降 dense_retrieve。命中文本块后，可按 related_text_ids 并入同页关联图，再可选 DashScope 多模态 rerank，再 Auto-merge 上卷父块。RERANK_MIN_SCORE 若配了且最高分不够，初检结果会被清空，后续按无资料处理。

打分是一次 structured output 覆盖全部候选块，不是对每块单独调模型：

图片块没有正文，提示里标成「图片片段，无文本」，避免 grader 把空字符串当成「完全无关」一刀切掉——也避免它幻想图里写了什么。

改写节点用另一个 structured output 在 step_back / hyde / complex 里选。complex 默认被 RAG_ALLOW_COMPLEX_STRATEGY=False 降成 step_back。扩检之后再打一次分：KB_GRADE_REFUSAL_ENABLED 默认开，全不相关或仍无结果就置 no_answer=True。

1.4 回注契约：给模型看什么，给前端看什么

子图结束不是把原文塞进 system prompt。format_knowledge_retrieval_tool_output 把 docs 编成工具字符串，再经 guard_untrusted_content 包进 <untrusted_external_content>。模型拿到的是一条 ToolMessage，不是「系统又说了一遍」。

文本块长这样：[i] filename (Page n) + 正文 + 分数。图片块除了尺寸信息，会单独给一行现成的 Markdown：

工具描述和 system 纪律都要求：配图必须把这一行原样复制，不得改括号、不得换成绝对 http、不得填 stored_relpath。这是第 2 篇「同源相对路径 + 签名」在对话侧的合同。

同一套编号写进 kb_sources，落库后前端做成来源胶囊；[来源N] 和 chips 对齐。rag_trace 记下 query、策略、打分、rerank、Auto-merge，给思考区回放，不进模型下一轮的「证据」。

拒答不走空字符串。二次门控失败时，工具返回可机读指令：

_KB_ANSWER_DISCIPLINE 点名这条码。模型收到的是观察，不是「你自己看着办」。

以图检索是旁路，不是主图的一个分支。search_knowledge_by_image 收 attachment_id、focus（text / image / mixed）和 top_k，内部跑 rag_image_pipeline：解析本会话图片附件 → retrieve_documents_by_image（只 dense，skip_rerank）→ 同样的格式化出口。额度按会话里图片附件数量计，和以文那 1 次槽位互不占用。

2 实现思路：为什么是这套，而不是其它

2.1 为何不是 Naive RAG

Naive RAG 的合同是：每个问题都 embed、都 top-k、都拼进 prompt，然后生成。实现简单，评测也好做。Kura-AI 没走这条路，是因为产品不是「一个只回答知识库的问答框」。

同一套对话里，用户可能闲聊、问附件、调 MCP、或者把检索开关关掉。每问必搜会做成三件坏事：首 token 多等一轮向量和可能的打分；无关叶子块挤占上下文；没资料时模型仍会顺着噪声编。第一道门和第二道门存在的理由，就是把「检索」从默认动作改成可选动作。

主 Agent 保留「不搜」的权利，和第 1 篇选 Function-Calling ReAct 是同一条约束：任务形态开放，进门时画不死「这一问必须走检索」。把 Naive RAG 焊进主路径，等于把灵活度先交出去。

证据也不进 system。检索结果走 ToolMessage，还套隔离块。知识库文档是用户上传的，里面完全可能夹着「忽略以上指令」之类的句子。Naive RAG 常见的「system 里贴检索上下文」，在这个产品里是注入面。

2.2 为何不把 grade / rewrite 做成主循环工具

另一头的常见做法是 Self-RAG / CRAG：检索、打分、改写都做成 Agent 可调的工具，主循环自己决定「再搜一次、换个问法」。表面上更 Agentic，落地会散。

第一，延迟。主循环每多一次工具往返，就是一次完整的模型调用加流式分发。grade 和 rewrite 步骤固定，不需要「走一步看一步」的灵活度，却会按灵活度的价格付账。

第二，配额和思考区会对不齐。以文检索每轮只许成功一次，就是为了防 ReAct 刷检索。若 grade 失败后模型再调一次 search_knowledge_base，不是被限额挡住，就是得把限额放宽——放宽之后，「再搜一次」可以递归到停不下来。思考区的 emit_rag_step 也会从一条连续流水线，变成模型爱怎么插就怎么插的碎片。

第三，和第 1 篇同一句话：LangGraph 用在步骤固定、需要条件路由的地方。初检 → 打分 → 必要时改写再扩检 → 二次门控，边是确定的。主对话如果为了 RAG 再画一张大图，用户自定义的 MCP 更没法预画。

所以拆法是：主循环保持「调一次、拿观察、终答」；质量环封进工具。generate_answer 只是子图的出口标签，不是子图里再调一次聊天模型。

2.3 为何选档在循环外，工具不暴露文件参数

看起来最「Agentic」的做法，是让 search_knowledge_base 带一个 document_filenames，模型自己挑文件。Kura-AI 反着做：选档在 create_agent 调用前结束，工具 Schema 只有 query。

模型若能改范围，第二道门就只是建议。多文档库里，一次 hybrid 的噪声主要来自「搜了不该搜的文件」，不是 top-k 少 1。把范围锁在闭包里，是用代码收口，不是靠它自觉。

选档失败回退全库，而不是中断对话。选档是优化，不是正确性的前提；子模型超时、空数组、对不上白名单，都不该让用户看到一次 500。1 份文档自动限定，则是省掉一次没意义的 LLM。

选档提示最多列出 100 个文件名（KB_PRESELECT_MAX_DOC_LINES）。评测包里 2doc / 3doc 会超过这个数，tests/RAG_test/README.md 写明了：要么关选档，要么接受「未圈定则全库」。这是已知折中，不是漏写。

2.4 为何改写是 step_back / hyde，complex 默认关掉

查询扩展只在首次检索空、或打分全不相关时发生。路由提示把三类问题对上三种策略：

  • step_back：问句带专名、日期、代码，先退到更一般的概念再检索
  • hyde：模糊、要定义或解释，先写一段「假想中的资料」再用这段去搜
  • complex：多步、要综合；实现上等于 HyDE 检索再加 Step-back 检索

complex 默认关，路由即使选出也会降成 step_back：

聊天对首字延迟敏感。HyDE 已经是一次生成加一次检索；再叠加 Step-back，最坏是三次向量检索加两次 LLM。retrieve_expanded 里还有一条短路：complex 且 HyDE 路已经 0 条，跳过 Step-back，避免第三次白跑。

Step-back 默认只生成退步问句，拼进 expanded_query，不先让模型答那个退步问题。RAG_STEP_BACK_ANSWER_ENABLED 打开才会多一次答题调用。对对话产品，少一轮打杂 LLM，比「退步答案可能稍微准一点」更划算。

路由模型失败则策略固定为 step_back，子图不会因为 JSON 解析挂掉而整轮报错。

2.5 为何打分是「任一相关即过」，扩检后才拒答

首次打分的阈值很松：一块 yes 就 generate_answer。这不是漏检，是故意把「query 措辞不对」和「库里真没有」分开。

用户问法常常和文档标题对不齐。第一次全不相关，更可能是问句太窄或太口语，值得改写一次再搜。若首次就拒答，HyDE / Step-back 永远走不到，召回上限被问句锁死。

第二次仍全不相关，或扩检仍是空的，才置 no_answer。两次机会用完，合同从「再试试」变成「如实说没有」。KB_GRADE_REFUSAL_ENABLED 关掉会回到旧行为——改写后直接生成——默认开着，是因为硬生成比多一次打分更伤信任。

打分失败（网关、JSON、超时）走另一条：grade_error 记进 trace，路由放行生成。注释写的是「避免检索链路整体报错」。无 grader（没 Key）时，首次当「需要改写」，二次（仍无模型）放行，不在没裁判的情况下直接拒答。这些降级都偏向「对话还能结束」，而不是「宁可不回」。

tests/kb/test_rag_pipeline_routing.py 把这张路由表钉死了：空结果、无模型、全不相关、打分异常、拒答开关，各走哪条边。LLM 全桩，零网络。子图的合同是测过的，不是只靠提示词。

2.6 为何以图检索另走轻量子图

以图查询没有可用的自然语言。BM25 腿没文本可算，HyDE 要先写假想文档，文本 rerank 也没有 query 可打分。把这些节点硬接进主图，只会得到一串「跳过、跳过、再跳过」。

所以 rag_image_pipeline.py 只有三个节点：解析附件 → dense 检索 → 组装 trace。retrieve_documents_by_image 按 focus 过滤 L3、L4 或两者，skip_rerank=True。格式化出口和以文共用，来源编号、图片 Markdown、隔离块不必做第二套。

额度按会话图片附件数计，而不是也砍成 1。用户可能连传两张图问「这两张分别像库里的哪一页」；和「同一句文本再搜一遍」不是一类滥用。没有图片附件则直接限额失败，避免模型拿一个不存在的 attachment_id 空转。

检索器内部其余部分——hybrid、rerank、Auto-merge、关联图扩展——沿用第 2 篇的索引，不在这里重讲 schema。在线侧只需记住：叶子负责被找到，父块负责被读懂，图在命中文本之后按已写好的 related_text_ids 并进来。

3 优化：性能、体验、可靠性

子图能跑，还不等于能用。下面这些是已经落地的，而且偏 RAG；主循环那套 Job SSE、取消节流、会话压缩，第 1 篇写过，这里不重复。

3.1 性能与成本

主模型只跑 ReAct，打杂交给子模型。 选档、逐块打分、HyDE、Step-back 问句都不需要聊天人格，走 sub_model_name / sub_api_key；配不齐就整份回退主配置，不混搭 endpoint。第 1 篇的子模型机制，在 RAG 这条链上用得最勤。

少一轮循环，比在循环里省 token 更划算。 以文检索每轮 1 次成功槽位；扩检发生在工具内部，不占第二次 ReAct。complex 与 step-back 答题默认关，是把最贵的那几跳先砍掉。

rerank 是可选能力，不是硬依赖。 RERANK_MODEL、RERANK_API_KEY、RERANK_BINDING_HOST 三者齐才启用，否则按向量分排序。HTTP 用模块级 requests.Session，超时默认 15 秒，候选上限 30，单图超过 4MB 不参与重排。没配 rerank 的部署，检索链照样能结束。

召回先宽后窄。 candidate_k = top_k * 3，hybrid 两腿各自 limit=top_k*2，再 rerank、merge、按图片槽位截断。最终给模型的仍是大约 5 段，贵的打分和生成只打在短名单上。KB_MIN_IMAGE_SLOTS 默认 2：有图可给时，不让纯文本按分数把图挤光。

选档和记忆预注入并行。 流式路径 asyncio.gather，少一段串行等待。选档文件名列表按 kb_scope 缓存一小时，不每轮扫一遍 PostgreSQL。

3.2 体验

ReAct 对用户最不友好的一点，是「它在搜，但界面像卡死」。RAG 子图每个节点都 emit_rag_step：选档、叶子层召回、Auto-merge、打分、改写策略、扩检、拒答。这些步骤进思考区，和工具调用前的过渡句按时间交错。rag_trace 随 trace 事件出去，折叠面板里还能看到 mode / stage / grade。

来源走统一的 sources 通道。知识库和联网互斥，同一条回复不会出现两套编号抢 [来源N]。前端把引用收成胶囊，点一下滚到来源 chips。图片必须是工具给的那行签名 Markdown，CSP 才放行。

拒答也是体验。与其生成一段无法点开的假出处，不如明确说「知识库中没有相关资料，可以上传后再问」。二次门控和 RERANK_MIN_SCORE 都是在给这句话找证据，不是在惩罚召回。

3.3 可靠性

  • 检索降级：hybrid 失败改 dense；dense 也失败返回空列表和 retrieval_mode: failed，由子图走改写或拒答，不把异常抛回主循环。
  • 打分降级：异常放行生成；无模型时首次改写、二次放行。链路以「能结束」为底线。
  • 选档降级：失败、空数组、关开关，全是全库，不是 500。
  • 工具异常：run_rag_graph 外包一层 try，返回「知识库检索出错：…」，并仍写入 rag_trace.error。
  • 非可信隔离：工具输出默认最多 16000 字，外加隔离标记和「不可当指令」的脚注。
  • 请求隔离：RAG 步骤队列、配额、last_rag_context 挂在 ContextVar 上，并发对话的思考区和来源互不串。
  • 评测：路由有单测；tests/RAG_test/ 是从 CRUD-RAG 抽的闭集包，用来看选档、是否调用工具、是否拒答，不是 CI 里的 mock。

4 对照与收束

把常见 RAG 做法和 Kura-AI 实装置在同一张表里，会更清楚「我们选的是哪一层，改的是哪一层」：

维度 常见做法 Kura-AI 实装
是否检索 每问必搜；或主 Agent 无限次搜 开关 + 模型决定 + 每轮以文 1 次
检索范围 工具参数任选文件；或永远全库 循环前选档，工具无范围参数
质量环 无；或 Self-RAG 挂在主循环 工具内固定 LangGraph 子图
查询扩展 每次都 multi-query 仅初检不够时 step_back / hyde；complex 默认关
无资料 硬生成 二次门控 + KNOWLEDGE_BASE_NO_RELEVANT_INFO
证据注入 拼进 system / 用户消息 ToolMessage + 隔离块 + [来源N]
以图 融进主图，或先 OCR 再走文本 RAG 轻量旁路子图，只 dense
生成位置 RetrievalQA 链内生成 子图只检索，终答仍在外层 ReAct

一句话收束：主 Agent 负责灵活度，选档负责缩小搜索空间，子图负责检索质量与拒答。 三者叠在一起，才是 Kura-AI 现在的 Agentic RAG。库怎么建，第 2 篇已经写过；这一轮对话里检索何时发生、失败了怎么办，是这一篇要收住的合同。
