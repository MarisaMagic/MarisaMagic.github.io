「Kura-AI」项目中多模态知识库是如何构建的

⭐ Kura AI 项目链接：https://github.com/MarisaMagic/Kura-AI

0 前言

这是 Kura-AI 专题的第 2 篇。第 1 篇写的是对话 Agent 的推理范式：主循环是 Function-Calling ReAct，知识库检索藏在 search_knowledge_base 的 LangGraph 子图里。这一篇写知识库本身：一份带图的文档是怎么拆开、入库，又在不惊动正在用的旧库的前提下被换掉的。

做这个功能的时候，眼前有好几条「看起来更省事」的路：整篇文档一个向量、图文融合成一条 embedding、向量塞进现成的 PostgreSQL、上传同步解析、重传先删后写。最后落下来的是这套：

  • 文本按页切成 L1 / L2 / L3，只有叶子 L3 进 Milvus；父块放 PostgreSQL，检索时再按 Auto-merge 往上卷；
  • 图片从 PDF / Word 里抽出来，单独做成 L4，和文本 分别 用 qwen3-vl-embedding 写进同一个集合；图和哪段话对应，用 related_text_ids 在入库时写死；
  • 原件进 MinIO，PostgreSQL 只记账。每个智能体一份 kb_scope = u{uid}_a{aid}；
  • 上传丢给后台线程，向量全部算完才替换旧文档。失败、超时、取消，旧的还在。

这些决定不是从「多模态 RAG 应该长什么样」推出来的，是从实际用这个产品会踩的坑倒推的：用户会传带图的 PDF，会同名再传一版，会在上传还没结束时继续对话，共享出去的智能体还不能让别人改库。

flowchart TD
  upload[上传 API 立即返回 task_id] --> job[kb_job 线程池]
  job --> parse[解析文本并抽图]
  parse --> split[L1 L2 L3 分块 + L4 图片块]
  split --> link[同页图文关联 related_text_ids]
  link --> embed[文本批嵌入 / 图片逐张嵌入]
  embed --> swap[替换临界区]
  swap --> milvus[Milvus: L3 文本 + L4 图片]
  swap --> pgParent[PG: L1 L2 父块]
  swap --> pgImg[PG: 图片元数据与关联]
  swap --> minio[MinIO: 原文档 + 图片]

1 先把「一份文档入库」这件事想清楚

入口很简单：app/api/v1/user_agents/kb.py 的 kb_upload 只负责校验和入队，真正干活的是 app/kb/kb_service.py 里的 run_ingest_pipeline_sync。页面在 web/src/views/agents/knowledge-base/index.vue。

1.1 边界：能做什么、故意不做什么、什么绝对不能发生

  • 要能做的：属主给某个智能体传 PDF、Word、Excel、TXT、Markdown（默认 50MB）；能列表、按文件名删、取消正在跑的任务；同名再传就是替换，内容 SHA256 没变就跳过。
  • 故意不做的：共享用户可以问属主的库，但不能改——知识库 API 走 get_owned。没有单独的「重建索引」按钮。独立图片不能作为文档上传，图片只能是文档里抽出来的。Excel 和纯文本不抽图。也没有 OCR：扫描件如果抽不出字，文本这边几乎是空的——这是明知的代价。
  • 绝对不能发生的：解析或嵌入失败，结果把正在对话用的旧库先删掉。
  • 做成的样子：叶子能被以文、以图搜到；父块能合并回去；命中一段文字能带上旁边的图；进度看得到、任务停得住；删文档或删智能体时，向量、父块、图片、原件一起走。

后面所有「为什么不换一种做法」，基本都是这几条在挡路。

1.2 任务在 Redis 里跑，进了 PG 才算入库成功

没有给文档做 pending / processing / ready / failed 状态机。处理中只活在 Redis 任务快照里，列表里能看见的文档就是已经落稳的。

上传接口把文件读完、核对扩展名和魔数，立刻还一个 task_id：

任务记在 kb_upload_job:{task_id}:meta，状态是 queued → running（parsing / chunking / embedding / writing）→ completed / failed / timeout / cancelled。前端每 500ms 来问一次进度。

这里和第 1 篇的对话 Job 不一样。对话要续传思考过程和正文，所以走 Redis SSE；知识库上传只关心「现在到百分之几了」，一份快照就够。mg_kb_documents 要等替换落库成功才写一行。向量还没算完之前，同名旧版完整留着，Agent 还能搜到；真正换库只发生在最后那几秒的临界区，先删旧再写新，会有一个很短的空窗。别的文件全程不受影响，新传的文件在落库成功前不会出现在列表里。

隔离键是用户加智能体：

智能体表上没有知识库外键。Milvus 过滤、对象存储路径、PG 行，都认这串 scope。对话侧固定用属主的 scope，所以智能体发布出去以后，别人问到的还是属主建好的那份库，只是改不了。

1.3 为什么切成四级，而不是一刀切完就入库

MultimodalDocumentLoader 用三组 RecursiveCharacterTextSplitter 做 L1 / L2 / L3，图片单独做 L4。默认 chunk_size=900、chunk_overlap=90，三层大概是 1800 / 900 / 450，重叠 240 / 120 / 60。分隔符里放了中英文句读，免得中文被按空格切得乱七八糟。

层级 存放位置 检索时的用途
L1 / L2 文本 PostgreSQL mg_kb_parent_chunks，外加 Redis 缓存 不直接做 ANN，给 Auto-merge 往上卷
L3 文本 Milvus：dense + 服务端 BM25 默认检索粒度（LEAF_RETRIEVE_LEVEL=3）
L4 图片 Milvus 的 dense + PG mg_kb_images + MinIO 原图 以文搜图、以图搜图；text 留空，不走 BM25

chunk_id 用展示文件名的 SHA256 前 16 位做指纹，路径里那些奇怪字符就进不去了。L1–L3 的序号是页内该层计数；L4 用的是整篇文档的全局序号，后面还会跟一个 ::i0——当前实现里图片序号恒为 0，真正把各张图分开的，是前面的全局序号和内容哈希文件名。

入库时按层级拆开，只有叶子进向量库：

各格式的处理方式：PDF 用 PyPDFLoader 抽分页文本，PyMuPDF 抽内嵌图和位置；Word 用 Docx2txtLoader 加 python-docx 抽段落里的图；Excel 一张表转成一块 Markdown（隐藏表跳过）；TXT / MD 整篇当作一页。不认识的扩展名直接拒。

PDF 里小于 100×100 的图当作图标丢掉。Word 没有页的概念，只能用段落序号顶上，纵坐标按 para_idx * 100 估一个。扩展名允许 .doc / .xls，魔数也认 OLE，但 loader 实际吃的是 OOXML——老格式能过校验，解析却大概率失败，这是已知的代价。

1.4 向量、正文、像素拆开存

层 放什么
MinIO 原始文档 user_agent_docs/；抽出的图片 user_agent_images/user_{uid}/{aid}/{fingerprint}/
PostgreSQL 文档行（content_hash、叶子数）；L1/L2 全文；图片元数据和 related_text_ids
Redis 上传进度、同名替换锁、父块缓存、选档用的文件名列表
Milvus kura_ai_kb L3 / L4 的 dense；文本块另外有服务端算好的 BM25

Milvus 里图片块的 text 故意留空，image_path 只是相对路径。像素不进向量库。base64 只在检索做 rerank 时才现读——入库路径不生成 caption，KbImage.caption 字段只是预留，模型里的注释写的就是「预留，默认空」。对话侧的读图是另一件事，第 1 篇写过。

2 实现思路：为什么是这套，而不是其它

2.1 先处理，再替换

run_ingest_pipeline_sync 的注释就是当初的设计备忘：

实际顺序是：

  1. 同名且 hash 相同，直接回 unchanged，连解析都不做；
  2. 临时目录里抽图、切块、把图和 L3 对上；
  3. embed_documents 只算向量，不写 Milvus；
  4. 向量齐了，才把图片和原件上传到对象存储，并把 image_path 改成相对路径；
  5. 拿 Redis NX 锁，删旧、写父块、按算好的向量插入、写 KbDocument。

第 3、5 步拆开，是为了临界区里不再调嵌入 API。那一小段只有读写，几秒就结束。同名一起传的时候，锁保证落库串行，后做完的生效；图片文件名带了内容哈希后 8 位，删旧图时用 exclude_image_rels 护住「新旧其实是同一张图、key 撞车」的情况。

为什么不先删后写？嵌入是分钟级的，PDF 里几十张图还得一张一张打 HTTP。先删的话，用户点一次重传，对话马上搜空，失败了还回不去。为什么不做块级增量？一份文档的层级树、图文关系和 BM25 统计是整份一起算的，局部打补丁省不了多少，对不齐的风险更大。所以现在的粒度就是整份文档换掉。

2.2 图和文分开 embed，不用融合向量

MultimodalEmbeddingService 里其实写过 get_multimodal_fusion_embeddings，后来没用，全仓库也没有调用方。生产路径按 content_type 拆开：

图片写入时 text 为空、chunk_level=4：

融合一条向量看起来干净，但后面的检索对不上这套。以图搜图需要图片自己的向量；用户问到某段说明时，检索侧还要把旁边的图拉进来，这靠的是 related_text_ids，不是一次融合能代替的；给模型看的时候，文本和带签名的 /api/v1/media/ Markdown 也必须分开。BM25 只认 text，融在一起会把关键词计分搅乱。

文本和图片交给同一个 qwen3-vl-embedding、写进同一个 dense_embedding 字段，查询文本就能直接和图片块做 IP 内积。这条路要成立，前提就是模型把文本和图像对齐到了同一个向量空间——代码里没有哪一行专门写这件事，但整套设计就是按这个假设用的。模型已经把跨模态对齐做了，自然没必要再上 CLIP 双塔。

2.3 叶子进 Milvus，父块进 PostgreSQL

细叶子召回准，拿短句子当最终上下文又碎。Auto-merge 的实现是：Milvus 只索引 L3，同一 parent_chunk_id 下命中够多（默认 3 块）就用 PG 里的 L2 / L1 换上去，做两轮，L3 → L2 → L1。所以构建时必须把树写完整：parent_chunk_id、root_chunk_id、chunk_level、页内起止位置。

父块不建成向量。Auto-merge 是按 id 取全文，不是再搜一次。这种点查用 PostgreSQL 更合适，外面再套一层 Redis。如果把 L1 也丢进 Milvus，大段重复文本会把检索冲掉，过滤也不好写。

L4 不走文本切分器。图片是文档里嵌着的资源，不是切出来的句子；关联阶段把它的 parent_chunk_id 指到某个 L3，不是 L2。

2.4 图和文怎么对上：能算几何就算，算不了再按顺序

图文配对不拖到检索时再猜，更不能图省事把「同一个文件名」直接当配图。构建时就要把 L3 和图片绑上。PDF 这边走过弯路：最早把字符下标和页面纵坐标混在一起比，后来才改成现在这套——能定位到页面框时，优先把「在这张图上方」最近的那块文本给它；这张图上面没有 L3，就改绑纵向距离最近的那块。只有整页都框不住、或者 PDF 打不开，才退回按阅读顺序和图片从上到下 zip。Word 没有同一套坐标系，直接按顺序配，不再拿字符位置和 y 坐标比。

内存里两边都会记一笔：图片有 related_text_ids，文本块有 related_image_ids。真正留下的只有 PG 里 KbImage.related_text_ids。Milvus 不管这张关系表——它负责「像不像」，关系表负责「这张图属于哪段话」。

为什么不上 OCR？想让 VL embedding 直接看像素，少一条识别错了再往下传的管线。代价也很清楚：扫描件几乎没有有效 L3，只能碰图片这边的向量。caption 不在入库时生成，也是同一想法：上传这条关键路径上，不再塞一次视觉模型调用。

2.5 为什么是 Milvus

按社区通常的说法：原型用 Chroma，中规模用 Qdrant，上了千万、要分布式再上 Milvus。Kura-AI 这点体量，pgvector 或 Qdrant 其实都跑得动。最终还是选了 Milvus，看的是另一件事：同一个 collection 里，dense、服务端 BM25、按字段过滤，是不是一等公民。

当时要同时成立的三件事，都写在 app/kb/milvus_client.py：

文本既要语义近，也要词能对上。 hybrid_retrieve 用 HNSW / IP 搜 dense_embedding，同时把用户原话丢给 bm25_sparse，再用 RRFRanker(k=60) 揉在一起。图片块 text 是空的，BM25 覆盖不到图，以图检索只走 dense。中文单字召回靠 dense 兜底——Milvus 2.5 的 BM25 Function 还不让配 analyzer，只能用内置 standard。

查询时 BM25 直接传文本，不用在客户端再算一遍稀疏向量：

BM25 交给库在写入时算，不自己养词表。 最早那版是进程内词表，重启一次 IDF 就漂。migrate_bm25.py 把旧集合的 dense 原样拷过去，稀疏改成服务端 Function，没有再付一次 embedding 的钱。这也是 compose 里钉死 milvusdb/milvus:v2.5.14 的原因。

图和文挤在同一个集合里过滤。 检索表达式是 kb_scope、可选的 filename in [...]、chunk_level == 3 || 4。会话记忆另开了 kura_ai_chat_memory，不跟知识库抢字段。多模态在这里不是两个库，是一张表里用 content_type 分开。

其它选项的取舍：

  • pgvector：父块、图片元数据已经在 PostgreSQL 里了，向量不塞进去。父块只要按 id 取全文；叶子要 hybrid、RRF、服务端 BM25。pgvector 通常还得再接一套全文检索，过滤和 hybrid_search 也没有现成的这一套。全塞进一张关系表，合并和 ANN 会搅在一起。
  • Chroma：原型好用。这里需要的是「每个智能体一个 scope、选档按文件名、图文混着滤」，它吃力，也没有写入就算 BM25 这件事。
  • Qdrant：中规模很能打，也有稀疏向量。但这条路径已经绑在 Milvus 2.5 的 Function 上了，standalone（etcd + 专用 minio + milvus）也 docker 好了。换过去要重写 schema、混合检索和迁移脚本，以现在的体量不划算。
  • Elasticsearch：向量是后补的。想要的是 ANN 原生，BM25 顺便带上，不是倒过来。

本地 compose 跑 standalone，云上可以填 MILVUS_TOKEN 接 Zilliz。部署细节就不在这篇展开了。

2.6 为什么丢进后台线程，而不是上传接口里当场解析

抽图、批文本 embedding、逐张打图片 HTTP，几十秒到几分钟都正常。丢在 FastAPI 路由里会堵住事件循环，对话那条 Job 也要排队。所以知识库单独开了 ThreadPoolExecutor（默认 8 个工人），worker 里跑同步流水线，而且每个任务自己 new 一个 MilvusManager，不跟别的线程抢同一个客户端。

进度条按阶段加权：parsing 0–10，chunking 10–12，embedding 12–85，writing 85–100。嵌入占了绝大多数时间，所以这一段给得最宽；要是四段平分，前几秒进度就冲过一大截，然后几分钟纹丝不动，用户只会以为卡死了。百分比只前进不回退，每次上报取 max。超出并行上限的任务停在 queued。单次嵌入 HTTP 默认 90 秒，避免 SDK 默认 300 秒把工人占死；整单 900 秒封顶。

2.7 存的时候就要想着后面怎么搜

检索怎么打分、怎么改写，留给后面的专题。构建这边只要记住：存错了，后面补不回来。

  • 只存纯文本：没有 L4，以文搜图、以图搜图、按关联拉图全没了，工具也给不出带签名的图片 Markdown。
  • 不写 related_text_ids：问到说明文字之后，只能碰运气看向量会不会撞上旁边那张图。
  • 没有 parent_chunk_id 和 PG 父块：Auto-merge 卷不上去，上下文永远是碎片。
  • filename 必须稳：前置选档和 Milvus 的 filename in [...] 用的是同一串字。模型不能在工具参数里自己改范围，这件事第 1 篇写过，选档在 Agent 调用前就做完了。
  • 原图和向量分开：rerank 需要时再从对象存储读成 Data URI，构建期不把像素塞进 Milvus。

3 优化：性能、体验、可靠性

能跑和能用不是一回事。下面这些是已经写进代码的，不是下一步计划。

3.1 性能与成本

文本按 EMBEDDING_BATCH_SIZE（默认 10）一批一批走，图片受 DashScope 限制只能一张一张来，但每张之前会 checkpoint()，取消和超时不用干等到当前这张图的 HTTP 结束。同名同内容直接跳过，这是唯一的「增量」——没有块级补丁。

换 BM25 实现的时候，dense 原样拷，没有重调 embedding。父块是检索热路径，写入时就放进 Redis；选档用的文件名列表按 scope 缓存一小时，文档有变动再主动丢掉。

3.2 体验

知识库页做了两层进度：HTTP 上传百分比，和后台 parsing → embedding → writing。多文件就多个 task_id、各自轮询，总进度取平均。做到一半刷新页面，sessionStorage 里还记着，回来能接着问。

取消不是摆设。标记写进 Redis，worker 跑到一批的边界就停；嵌入还没进替换区就失败的话，旧文档还在。超时会告诉你 900 秒到了。同内容再传，前端会明说「内容未变化，已跳过重建」，免得以为卡住。

聊天里的知识库图片走同源 /api/v1/media/...，带 exp + HMAC sig。media 接口的注释写得很直白：签名读取，无需登录——签名本身就是这张图的凭证，文件本体存对象存储，验签后由后端流式中转，到期自动失效。地址默认只拼相对路径（sign_media_url 的 absolute 参数默认就是 False），浏览器按当前域名解析，前端代理换到哪台后端都不用手动改。构建时把像素放进对象存储、检索时再签发，就是为了聊天页能把图亮出来。

3.3 可靠性

解析、嵌入失败只清临时目录，旧的 Milvus / PG / 对象存储不动。真正危险的是已经进了替换锁、旧数据删掉之后又失败——这个窗口很窄，新上传的对象会尽量清掉，而且同名再传一次就能自愈。

图片单张 embed 失败，用零向量顶上，不让一张坏图毁掉整份 PDF；文本向量条数对不上就整单停，因为 BM25 和 dense 必须对齐。PDF 整页都框不住 L3、或者文件打不开，才退回按顺序配，不阻断入库。

进度查询会核对 meta.user_id，不能拿别人的 task_id 看任务。Milvus 过滤里的 scope 和文件名会做转义，避免文件名里的引号把表达式打穿。

4 对照与收束

对照那些更常见的做法，最终留下的是这张表：

维度 更常见的路 Kura-AI 里的做法
文档表示 整篇或整页一个向量；图文融合成一条 L1/L2/L3 文本树 + 独立 L4；分别 embed
图片 OCR 进文本；或整页截图 抽内嵌图，让 VL embedding 看像素；入库不 OCR、不写 caption
图文关系 检索时按页猜 入库时写 related_text_ids，命中文本再带图
切分 单层 chunk 直接检索 叶子进 Milvus，父块进 PG，再往上卷
向量库 全部塞进 pgvector 或 Chroma Milvus 做 hybrid；PG 只放父块和关系
原图 base64 跟向量绑在一起 MinIO + 相对路径；rerank 时再读
更新 先删后写，或同步解析 后台 Job，先处理完再替换；hash 相同就跳过
隔离 全局一个库 一个智能体一份 scope；共享只能问

一句话收束：文本负责被问到，图片负责被看到；关联在入库时写死，检索时再拼回来。 Milvus 管「像不像、词能不能对上」，PostgreSQL 管「这段话的父块和旁边那张图」，对象存储管像素。三者叠在一起，才是现在这套多模态知识库。
