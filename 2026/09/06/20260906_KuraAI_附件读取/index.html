「Kura-AI」附件读取工具设计

⭐ Kura-AI 项目链接: https://github.com/MarisaMagic/Kura-AI

0 前言

这篇文章讲的是 Kura-AI 会话附件怎么被模型读到：名单从哪里来，长文档怎样定位中间的段落，短文档怎样抽出文首正文，以及图片为什么不走这三把工具。

外层 Agent 只决定调 list_session_attachments_brief、search_session_attachment 还是 read_session_attachment，以及 attachment_id / query 填什么。抽正文、分词打分、从文首截断、按会话隔离，都在工具函数里做完。三件套在组 Agent 时始终挂上，没有「本轮用附件」这种开关，也没有次数槽。知识库每轮只许成功一次，联网搜索、读页、搜图各自有上限；附件读的是本会话已经落盘的文件，拦的是权限和体积，不是外网配额。

Function Calling 机制：「Agent Tool」什么是 Function Calling？原理是什么？。
工具注册：「LangChain」LangChain 如何为 Agent 注册工具？。

四条边界先说清楚。第一，循环开始前，本会话附件的元数据已经写进本轮 Human，list 只是这份名单不够用时的兜底。第二，历史里文档是 file_ref，图片是 image_ref，不内联正文。第三，图片不走这三把工具：后面还要选检索类工具时，先单独看图；只聊天、不检索时，图直接进多模态。第四，本会话刚传的文件不会自动进向量库。属主库里预先入库的退款说明，走 search_knowledge_base；公开网页上的报价，走联网三件套。用户刚上传的 GPT-Plus订阅说明.pdf，才是这三把工具的事。

1 list_session_attachments_brief：名单已经在本轮里

1.1 策略选择

循环开始前，先把本会话已上传附件的元数据写进本轮 Human。list 只在「多份文档里要挑目标，而本轮块又不够用」时才调。本轮块里已经有同一份名单，就不要为相同信息再调一次。

模型填不了范围。user_id、agent_id、session_id 关在工具闭包里。list 没有参数；search 和 read 只留 attachment_id 和检索词。attachment_id 必须来自这份名单，不能让模型自己编一个 UUID。

1.2 如何实现

上传是先落盘再发消息。POST /user-agent/chat/attachments/upload 做完扩展名白名单和魔数校验，写入 MinIO 前缀 user_agent_uploads/user_{id}/agent_{id}/{session}/，并在 mg_chat_attachments 记一行。单文件默认 15MB，会话合计 80MB，每会话最多 80 个。随后聊天请求带上 attachment_ids。历史里文档写成 file_ref，图片写成 image_ref，正文不跟进去。

真正给模型看的名单，出在 format_attachment_hint。它只列事实：attachment_id、文件名、kind、字节数。这份字符串由 _format_turn_context_block 拼进最后一条 Human，不入库。刷新页面再 load，历史上只剩用户原话和引用，不会把临时文件清单当成用户说过的话。

make_session_attachment_tools 把当前请求的三元组焊进闭包。读任何一份附件，都先按 user_id + agent_id + session_id 对行；对不上就当无权，不区分「没有」和「别人的」。list 本身没有参数，空会话回「本会话暂无附件。」

1.3 为什么这样做

名单写进本轮 Human，不写进会话历史。 attachment_id 是系统发的十六进制，模型编不出来。跟在用户问句后面，模型看见的是「这一问能用哪几份文件」。写进人设会把一份经常变动的清单抬成长期指令；写进历史，压缩和重新生成时会把它当成用户真的说过的话。

list 只是兜底，不是每次必调。 本轮块里已经有同一份元数据。再调一次，拿到的还是这几行，白白占掉一跳工具调用。多份文档里要挑目标、而本轮块被截短或没带上时，才值得再要一份。

范围关在闭包里，模型只看见 id。 猜到另一个会话的 UUID，也对不上三元组，工具只回「附件不存在或无权访问」。不必把属主、会话这些字段交给模型填。

上传文件不自动进向量库。 会话附件是这一次对话里的私货，生命周期跟会话走。和知识库共用对象存储客户端，但前缀分开：附件在 user_agent_uploads/，知识库文档在 user_agent_docs/。刚传上来的说明如果立刻切块、算向量，用户删掉会话之后，库里还会留下一份不该留下的退款条款。

1.4 其它方案

  1. 每次读附件前都强制调用 list。

    • 优点：模型手里永远有一份刚查过的名单，也不必解释本轮块。
    • 缺点：名单在循环开始前就已经在 Human 里。再调一次只是重复同一段元数据，长对话里会先把工具次数耗在列目录上。

  2. 把全文预读进本轮 Human。

    • 优点：模型第一跳就能看见正文，不必再调 search 或 read。
    • 缺点：一份 15MB 的 PDF 抽出来往往远超上下文。大多数问题只用得到其中一段，把整份说明塞进去，既贵也容易把退款条款淹没在目录和免责声明里。

  3. 用户一上传，就按知识库流水线入库。

    • 优点：附件和属主库走同一套检索，也不必维护三件套。
    • 缺点：本会话的临时文件和智能体长期资料混在一起。会话删了，向量行还在；别人分享这个智能体时，也可能搜到访客刚传的私人说明。

2 search_session_attachment：长文档先定位

2.1 策略选择

不确定答案在文首还是文尾时，先对 这一份 附件做 关键词检索。search 会抽全文，但只把命中片段回给模型；它是看中间和文尾的主路径，不是给 read 当翻页器。不用于图片，也不替代知识库里的混合检索。

query 由模型按用户意图压成关键词或短语。attachment_id 必须来自本轮名单或 list 的返回。

2.2 如何实现

入口在 search_session_attachment。模型可以填 attachment_id、query，还可以选填 top_k（默认 5，上限 20）和 max_snippet_chars（默认 800，夹在 200–4000）。闭包里的三元组模型看不见。

真正打分的是 search_attachment_text_bm25。先按和 read 同一条路径抽出全文，再切成块长 800、重叠 120 的窗口，对这一次抽出来的语料做 Okapi BM25（k1=1.5，b=0.75）。中文走 jieba，没装 jieba 就按字切；英文按空白切。正文超过 50 万字，只索引前面这一段，并在结果里注明后面没参与检索。命中后左右扩约 200 字，再压到片段上限。PDF 用抽页时记下的 page_starts，给一个大致页码。

还是「刚上传的说明里，开通未满 7 天怎么全额退？」。模型应把 query 写成「开通未满 7 天 全额退」，而不是把整句用户问题原样塞进去。命中大致长这样：

最后那句提示容易让人以为 read 能翻到第 12 页接着读。做不到。read 没有 offset、没有 page、也没有 start_char，再调一次仍然从字符 0 切。第 12 页的连续句子，以这段扩窗片段为准。

图片附件在抽全文时就会被拒绝，回的是「该附件为图片……无法以文本工具读取」。空 query、分词后为空、正文为空，各有一句中文错误，没有 TOOL_* 那种稳定前缀。

2.3 为什么这样做

search 会抽全文，但只把命中片段回给模型。 服务端和 read 走同一条抽取，最多索引前 50 万字；模型看到的是大约 5 条、每条默认 800 字的扩窗，不是整份 PDF。中间和文尾靠这些片段，不靠 read 翻页。退款条款若写在第 12 页，只读默认的 12000 字，模型看见的仍是封面和目录。

只对这一份、这一次抽出的全文打分。 语料当场分块、当场算 IDF，不写进向量集合，也不跨请求复用。应用重启之后，下一次调用会重新抽、重新分词，不会留下旧编号去对一份已经不存在的索引。知识库要服务许多智能体、许多文件，词表必须跟集合走；会话附件没有这个包袱。

不把附件叶子写入知识库集合。 刚上传的说明和属主长期资料不是同一种东西。写进 kura_ai_kb，就要带 kb_scope、算 embedding、还要决定会话删了谁来清向量。为一次对话里的一份 PDF 做这些，比进程内 BM25 重得多。

图片不走这把工具。 截图里的退款条件是画面，不是可分词的正文。抽纯文本会得到空页或乱码，再打 BM25 没有意义。

2.4 其它方案

  1. 只保留 read，不提供 search。

    • 优点：少一把工具，模型不用判断「该搜还是该读」。
    • 缺点：长 PDF 中间的条款永远落在文首窗口外面。问「开通未满 7 天怎么退」，模型只能根据封面胡猜。

  2. 给 read 加上 page / offset，让 search 负责指路、read 负责续读。

    • 优点：命中第 12 页之后，可以抽出更长一段连续正文。
    • 缺点：参数表多两个字段，模型会填错页码或编一个对不上的偏移。当前实现把「看中间」收在 search 的扩窗片段里，read 只负责文首。

  3. 把附件切成叶子，写入 kura_ai_kb。

    • 优点：和知识库共用混合检索，也不必维护一份进程内 BM25。
    • 缺点：临时文件和长期库混盘。会话一删，向量行和对象存储还要对齐清理；访客上传的私人说明也可能进到属主的检索范围。

3 read_session_attachment：按需抽文首

3.1 策略选择

已知 attachment_id，而且需要的是 文首连续正文、短文档或表格 时，再调 read。图片直接拒绝。长文档的中间段落以 search 的片段为准，不要指望 read 按命中位置续读。

3.2 如何实现

参数是 attachment_id，以及可选的 max_chars。默认 12000，运行时夹在 1000 到 50000 之间。先按三元组取行，再按扩展名分流：

类型 怎么抽 额外限制
.txt / .md 对象字节按 UTF-8 解码 无页
.pdf 下到临时文件，PyPDFLoader 按页拼接 记下每页起始下标，给 search 用
.docx Docx2txtLoader 无页
.csv / .xlsx / .xls pandas 读成表再 to_string() 最多 2000 行
kind=image 不抽 返回说明，让模型走多模态

PDF 和 Office 解析库要本地路径，所以先 download_temp，退出后删临时文件。抽完只切 text[:max_chars]；超长追加「…（已截断）」。对象在、库行在、文件丢了，回「附件文件已丢失。」对不上三元组，回「附件不存在或无权访问。」

短文档，比如只有两页的订阅说明，12000 字往往够把退款段一起带上，这时直接 read 比先 search 更合适。说明书也写了这一点：用户只要文首少量内容，不必先检索。

3.3 为什么这样做

历史只留 file_ref，正文按需再取。 一份 PDF 抽出来经常上万字。写进会话历史，压缩、记忆和重新生成都会反复带着它。用户问的是「刚上传的说明里怎么退」，大多数时候只要其中一段，不必把整份文件变成这句话的一部分。

默认窗口从文首切开。 封面、目录、表头和写在前面的条款，12000 字通常够看。再往后不是把默认值加到 5 万，而是先 search。5 万仍然是硬顶，防止模型把 max_chars 填成整份文档的长度。

表格在解析层就丢掉第 2001 行之后。 会话附件不是数据仓库。把整张上万行的费用明细塞进上下文，search 和 read 都扛不住；2000 行够核对表头和前几页数字。

失败回中文句子，不拆循环。 「错误：附件不存在或无权访问。」进 ToolMessage 之后，模型可以改口，不必把整轮打成 500。现况没有 TOOL_* 前缀，和知识库、联网那套稳定错误码不是同一形态，循环照样收得住。

3.4 其它方案

  1. 给 read 加上 page / offset。

    • 优点：search 命中第 12 页之后，可以抽出更长的连续正文。
    • 缺点：模型会填错页码。当前把中间段落交给 search 的扩窗，read 只保证文首这一截是稳的。

  2. 每次发消息都把全文内联进 Human。

    • 优点：第一跳就能引用，也不必解释两把工具的分工。
    • 缺点：上下文被一份临时 PDF 占满。问句还在，退款段却可能已经被截到窗口外面。

  3. 失败也做成 TOOL_* 前缀。

    • 优点：和知识库、联网的纪律可以对齐，System 能点名这些码。
    • 缺点：附件没有本轮开关，也没有次数槽，禁用码和超额码没有落点。现况用中文错误句，模型仍能据实改口。

  4. 允许这把工具读图。

    • 优点：三件套看起来更「完整」，图片和 PDF 走同一入口。
    • 缺点：抽纯文本读不了截图。读图是另一件事，不该塞进按扩展名分流的正文抽取。

4 两阶段读图：caption 不是第四把工具

4.1 策略选择

本轮带了图片，后面还要选检索类工具时，先单独看图，再让主 Agent 只拿描述去调工具。只聊天、不检索时，图直接进多模态，不预读。

这不是第四把附件工具。三件套的 description 写明：kind 为 image 不要调；用户消息里已经附上的图，直接根据图像回答。

4.2 如何实现

门控在 _should_run_vision_caption。四个条件要同时成立：配置 CHAT_VISION_CAPTION_ENABLED 打开（默认开）、智能体 supports_vision、本轮开了知识库或联网或已经加载了 MCP、最后一条 Human 里有 image_ref。只开附件、不开检索类工具，走原生多模态，不跑这一段。

阶段 1 用无工具的视觉模型。System 要求结合用户问题描述画面，把图里的文字、数字、日期尽量转写准确，认不出的专名不要编。同步路径走 generate_image_caption，流式路径走 iter_image_caption_chunks。超时默认 60 秒，描述默认截到约 1200 字。失败则空字符串，退回单阶段带图。

阶段 2 若描述非空：expand_images=False，所有 image_ref 变成短占位；描述写进本轮块，并套上 guard_untrusted_content。主模型看不见原图像素，只看见这段文字。描述不进 Human 的入库内容；思考区会留一份给前端回放，下一轮 load 不会把 caption 当用户原话再喂回去。

用户本会话上传一张退款页截图，问「这张图里退款条件怎么写的？」，同时又开了知识库。阶段 1 可能写出「图中写着开通未满 7 天可全额退」。阶段 2 的主模型用这句话去搜库或作答，不必在同一次调用里既看图又选工具。

未开视觉却传图片，build_storable_human_content 会直接拒绝，进不了对话。

4.3 为什么这样做

「看图 + 选工具」不挤在同一次调用里。 带图的请求本身就慢。再让模型同时决定要不要搜知识库、要不要联网，既容易漏掉图上的字，也会把第一跳拖得很长。先单独看图，主循环就可以是纯文本。

只在后面还要检索时才预读。 用户只是问「这张图是什么」，原生多模态一次就能答。再跑一轮 caption，等于为同一张图付两次视觉调用。门控把知识库、联网、MCP 算进条件，就是为了挡住这条浪费。

描述进本轮块，不进会话历史。 截图里的字是外部内容，隔离之后才能给主模型看。写进历史，压缩和重新生成会把它当成已经确认的事实；图上如果看错了一个日期，后面几轮都会跟着错。

三件套读不了 kind=image。 抽纯文本没有画面。把读图做成 read_image，模型还要再选一次工具，等于把阶段 1 又暴露回主循环。

4.4 其它方案

  1. 始终原生多模态，带图选工具。

    • 优点：少一次预读，实现更短。
    • 缺点：看图和选 search_knowledge_base / web_search 挤在同一次慢调用里。图上的退款数字容易漏，第一跳也更贵。

  2. 挂一把 read_image 给主 Agent。

    • 优点：和 PDF 的 read 对称，模型可以自己决定什么时候看图。
    • 缺点：本轮已经带了图，再调一次才能读，纯属重复。现在把看图放在启动前，主模型第一跳就已经有描述。

  3. 把 caption 写入历史。

    • 优点：下一轮不用再看图，调试时也能看见当时理解成了什么。
    • 缺点：看错的字会变成会话事实。现在只在本轮块里用一次，思考区留给前端回放，入库的仍是 image_ref。

收束

三件套读的是本会话文件，读图是启动前的预读。list 看名单，search 定位中间和文尾，read 抽文首窗口。图片不走这三把：后面还要检索，就先看图再纯文本循环；只聊天，就直接带图。刚上传的说明不会自动进向量库，也没有本轮开关和次数槽。猜错的 attachment_id 对不上三元组，工具回一句中文错误，循环继续。

问「刚上传的说明里，开通未满 7 天怎么全额退？」，名单已在本轮块里，长文档先 search；短文档可以直接 read。问「这张图里退款条件怎么写的？」，不要调这三把工具。
