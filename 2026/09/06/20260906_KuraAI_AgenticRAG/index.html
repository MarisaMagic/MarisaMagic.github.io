「Kura-AI」Agentic RAG 检索设计

⭐ Kura-AI 项目链接: https://github.com/MarisaMagic/Kura-AI

0 前言

这篇文章讲的是 Kura-AI 知识库在线怎么检索：叶子块怎样被找出来，稠密向量和 BM25 两路结果怎样合成一份候选，什么时候再按「问题和这块文档到底有多相关」打一遍分，检索命中的如果只是半句话该怎样回到更大一段，以及第一次问法和资料对不上时，为什么还要再搜一轮。

外层 Agent 只决定要不要调用 search_knowledge_base，以及 query 里填哪一句话。知识库开着的对话通常两轮结束，这一轮里知识库只许成功占用一次。召回质量、查询改写和拒答，都在工具里面的 LangGraph 子图 run_rag_graph 里做完，主模型看不见这些节点。打分、改写路由、生成退步问或假设性文档，都是子图里另起的轻量级子模型调用：复用智能体的接口地址和密钥，任务很短，不带工具，也不直接写出给用户看的回答。

1 先打叶子，融完再重排，够密再升到父块

1.1 策略选择

RAG 检索只会直接检索 L3 文本叶子和 L4 图片叶子。先走 两路召回：稠密向量 看语义是否接近，稀疏向量 BM25 看关键词是否对得上，再用 RRF（倒数排名融合） 合成一份候选。如果配置了 Rerank 重排模型，再按「问题和这块到底有多相关」打一遍分。最后才看构建时留下的父子关系：同一个父块下面叶子足够多，才把 L2、必要时再把 L1 取回来。

RRF 不调用大模型，只看两路结果各自排在第几名，排序比较粗略。Rerank 才会调用专门的 交叉打分接口（例如 qwen3-vl-rerank），Rerank 后的候选 相关度更高、更加精准。

1.2 如何实现

入口是 search_knowledge_base，随后进入 run_rag_graph。过滤条件写在 Milvus 表达式上：当前智能体的 kb_scope，再加上 chunk_level == 3 || 4。选档范围仍是启动前注入的 filename，这里不重写。真正把一批叶子整理成给模型看的那几条，写在 rag_utils.py 的 _finalize_retrieved_docs 里。默认最终只留 5 条（top_k=5），但会先多取一些候选：candidate_k = top_k * 3，也就是 15。L1 和 L2 不会出现在这次近邻搜索里，父块只在后面按 id 从关系库取回。

之所以先取 15 条再截到 5 条，是因为后面还要补同页图片、做重排、并按密度决定要不要换成父块。如果一开始只取 5 条叶子，同一个父块下面很难凑够 3 个子块，Auto-merge 几乎不会触发，同页图片也没有机会进入候选。15 条够给后面几步做事，又不至于把整页都送进重排。

步 做什么 默认规模
两路召回 dense 看语义，BM25 看字面，各取 30 candidate_k * 2
RRF 融合 按排名加 1/(60+名次)，合成 15 条 RRFRanker(k=60)
扩图 命中文本按 related_text_ids 拉同页图 每文本最多 5，总共 24
Rerank 配齐才走；图转 base64 一起排；分覆盖 score 上限 30 条
Auto-merge 同一父块 ≥3 个叶子则回表升 L2，再升 L1 AUTO_MERGE_THRESHOLD=3
截断 尽量留 2 个图片槽，再截到 5 top_k=5

以「GPT Plus 年费怎么退？」为例。稠密向量可能找到写着「全额退款」的叶子，BM25 可能找到带「GPT Plus」的句子。两路分数的量纲不一样，一个是内积，一个是 BM25，不能直接相加。hybrid_retrieve 让两边各取 30 条：稠密一侧用 HNSW 索引、内积度量，搜索参数 ef=64；BM25 一侧直接把这句话交给服务端。然后用 RRFRanker(k=60) 按名次融合。一篇叶子的融合分是它在各路里的名次倒数之和：只出现在一路，就只加这一路；两路都有，就把两项加起来。

RRF(d)=∑i1k+ri(d)\mathrm{RRF}(d)=\sum_{i}\frac{1}{k+r_{i}(d)} RRF(d)=i∑​k+ri​(d)1​

这里 k=60k=60k=60，ri(d)r_{i}(d)ri​(d) 是叶子 ddd 在第 iii 路召回里的名次，从 1 开始数。排第 1 得到 1/611/611/61，排第 2 得到 1/621/621/62，名次越后越小。融合分数只看排名，不看内积或 BM25 的原始值。两路都靠前的叶子会排上去；只在一路里很靠前、另一路完全没有的句子，排名分会低一些。混合检索如果失败，就退回只走稠密向量，对话还能继续。

问「年费怎么退」时，稠密向量可能先碰到「开通未满 7 天可全额退」，BM25 可能先碰到带「GPT Plus」的标题句。RRF 按上面的公式把两路名次加在一起。这一步结束时大约有 15 条叶子，还没有决定要不要换成更大一段。

RRF 融合之后还不是终局。知识库中不仅有文本，还有文本段落关联的图片。后处理顺序写死在 _finalize_retrieved_docs：先给已经命中的图片补上元数据，再按 related_text_ids 把同页图片拉进来，然后才做 Rerank，接着做 Auto-merge，最后尽量留出图片位置再截到 5 条。扩图默认每条文本最多带 5 张、整轮最多 24 张；关联图的分数会略低于源文本（大约是源分数的 0.97），避免一张碰巧出现的图把整份候选顶掉。退款页上的流程图如果和命中句子挂在同一组 related_text_ids 上，这一步就会进来，不必等向量自己命中那张图。

Rerank 要 RERANK_MODEL、RERANK_API_KEY、RERANK_BINDING_HOST 三者都配齐，才走 DashScope 多模态重排（例如 qwen3-vl-rerank）。RERANK_INCLUDE_IMAGES 默认打开，图片会转成 base64 Data URI 一起参加排序，单张超过 4MB 就跳过这张。一次最多送 30 条。成功后用 relevance_score 覆盖 doc.score，原来的融合分挪到 vector_score，后面的 Auto-merge 和图片槽都按重排分排序。如果没有配齐、HTTP 失败、返回空结果，或者根本没有文本块，就按向量分继续往下走。以图检索没有自然语言 query，重排这一步会被跳过。

如果重排开着，只是碰巧有相同词、却答不了退款的叶子会被压下去，然后再决定要不要升成整段 L2。Auto-merge 看的是同一个父块下面有多少叶子。同一 parent_chunk_id 下面至少 3 个叶子，才按 id 把父块全文取回来：先查 Redis kb_parent_chunk:{id}，没有再回 PostgreSQL，并写回缓存。先把 L3 换成 L2；如果升上来的 L2 仍然够密，再升一次 L1。父块的分数取它自己和子块里的较大值。退款页上如果连续几条叶子都在讲开通未满 7 天，就不必只把半句话交给模型。最后尽量留出 2 个图片位置，再截到 5 条。

1.3 为什么这样做

只直接检索 L3 文本叶子和 L4 图片叶子。 检索适合找短叶子，交给模型读则需要更大一段父块。问「GPT Plus 年费怎么退」的时候，向量库里对上的往往是半句「开通未满 7 天」，模型真正要读的却是整段退款规则。这两件事不能用同一次近邻搜索一起做完。

两路召回，再用 RRF 按名次合成一份名单。 只走稠密向量，容易漏掉产品名这类专有名词；只走 BM25，意思相近但用词不同的句子对不上。退款说明里「GPT Plus」靠字面，「全额退」靠语义，两路都要。内积和 BM25 的量纲不同，直接加权还得先归一化。RRF 只看名次，就不用为这两路再调一套权重。k=60 是常见取值：名次差几位，分差不会陡到把一路完全压死。

Rerank 插在 Auto-merge 前面。 RRF 仍然只说明「召回得够不够好」。只是碰巧有相同词、却答不了退款的叶子，还能排得很前。先按「问题和这块到底对不对得上」把噪声压下去，再决定要不要升成整段 L2，免得一个跑题的短句把整段免责声明抬上来。重排接口如果失败，就按向量分继续，对话不会整轮空白。

叶子足够多才换成父块。 阈值默认是 3，是为了避免一个孤零零的叶子就把整段 L2 换上来。父块按 id 回表，不再走一遍向量检索——构建阶段把全文放在 PostgreSQL，图的就是这件事。

最终结果里尽量留 2 个图片位置。 退款页上的流程图经常比半句文字更直接。如果只按分数从高到低截断，图很容易被文本挤掉。

1.4 其它方案

  1. 只走稠密向量，或只走 BM25。

    • 优点：实现更短，少一次融合，也不必解释 RRF 的 k。
    • 缺点：专有名词和同义表达会各伤一边。退款说明里「GPT Plus」靠字面，「全额退」靠语义，两路都要。只留一路，另一边的命中就得靠运气。

  2. 把两路分数加权求和。

    • 优点：看起来能精细调整「更信语义还是更信关键词」，也可以按语料改权重。
    • 缺点：两种分数的量纲不同，还得先归一化，权重也会跟着语料一起变化。换一批文档，「GPT Plus」和「全额退」哪边该更重，又要重调。RRF 不看原始分，少调一组参数。

  3. 不做 Rerank，RRF 结束后直接合并父块。

    • 优点：少一次 HTTP 请求，第一个字出现得更快，也不依赖重排模型的密钥和额度。
    • 缺点：只是碰巧有相同词、却答不了问题的叶子，更容易把父块抬上去，模型看见的是更大一段跑题文字。重排插在合并前面，就是为了先压低噪声，再决定要不要升段。

  4. 把父块和叶子都当成检索单元，或者不合并、直接把碎叶子交给模型。

    • 优点：少一次回表，或者实现更短。
    • 缺点：父块再向量化会和短叶子抢召回，费用也上去；不合并则模型经常只看见半句话。构建阶段把父块放在 PostgreSQL，就是为了按 id 取回全文，而不是再搜一遍。检索阶段不必再改这条路。

2 初检不够，再改写扩一轮，两次无关才拒

2.1 策略选择

检索出结果后的质量评审做成工具里的固定子图，不把打分和改写暴露成主循环上的另一套工具。外层每一轮里，知识库本来就只许成功占用一次；子图内部自己决定要不要再搜、用哪句话再搜，主模型看不见这些节点。打分和改写都是子图里另起的 轻量级子模型调用，不是主 Agent 在思考「还要不要再搜」。这一轮结束时，主模型手里只应拿到一次工具调用的结果：一段可以引用的资料，或者一句拒答。中间换了几次 query、打了几次分，都不该再占用那一次知识库检索调用次数的配额。

LangGraph 子图里固定只走一轮：先做初检，再打分；必要时改写问题，再检索一次，然后二次打分。图上没有真正的 generate_answer 节点，这个名字只表示子图结束，并把检索到的高置信度文档交回去，正式回答仍由外层 Agent 写。子图不会根据打分结果再开一轮循环，也不会把改写后的问句交回主模型，让它再调一次工具。以图检索是另一条子图，不走打分和改写。

2.2 如何实现

节点都在 app/kb/rag_pipeline.py。问「GPT Plus 年费怎么退？」时，大致是这样：

初检如果是空的，边条件 _route_after_initial 会直接去改写，不会先浪费一次打分。打分是子图里一次轻量级子模型调用，由 _grader_model 建出来：可以单独指定 RAG_GRADE_MODEL；没配就用智能体当前这套对话模型，temperature 固定为 0。一次调用覆盖全部候选，用 JSON 逐块给出 yes 或 no：这块能不能真正帮着回答当前问题；只是碰巧共享关键词，应判 no。五条里只要有一条被判为相关，就把这批结果交给外层 Agent，不再改写；全部无关才进入改写。如果没有可用的打分模型（例如智能体没配密钥），也会去改写，这样至少还换过一种问法。打分过程如果异常，就把现有结果交给外层去写回答，避免整条检索链报错。二次打分用的是同一套打分子模型，对着的仍是用户原来的问题。

扩展检索走的是同一套 retrieve_documents：叶子过滤、RRF、可选的 Rerank、Auto-merge 都再跑一遍，只是 query 换成扩写后的句子。新结果会替换 state.docs，不和初检做并集。二次打分仍对着用户原来的问题，不会拿 HyDE 写出来的假文档当标准。KB_GRADE_REFUSAL_ENABLED 默认打开：扩展后仍为空，或逐块又全是 no，才把状态标成 no_answer。工具侧据此返回稳定拒答码，要求如实说没有资料，不要引用片段，也不要编知识库结论。关掉这个开关，改写后会直接生成，回到更老的行为。二次打分如果没有模型，会把现有结果交给外层，不会因此拒答。第一次没有模型时选择改写，第二次没有模型时选择生成，两边不对称，是因为改写的机会已经用过了。

子图到此结束，不在内部写成最终回复。正式回答仍由外层 Agent 根据工具返回的编号来源去写。

2.3 为什么这样做

质量评审做成工具里的固定子图。 外层每一轮里，知识库只许成功占用一次。如果把打分和改写做成主循环上的工具，外层就可能在配额用尽之前来回试。放在子图里，主模型仍然只调一次 search_knowledge_base，中间换了几次 query、打了几次分，都不占用那一次配额。

打分和改写是轻量级子模型调用，不是主 Agent。 子模型复用智能体的地址和密钥，任务很短，不带工具，也不直接写出给用户看的回答。主模型这一轮结束时，手里只应拿到一段可以引用的资料，或者一句拒答。

子图里固定只扩一轮。 第一次检索对不上，常常只是问法不对。用户问「年费怎么退」，库里写的是「订阅未满七日可全额退回」，字面差一点，稠密向量和 BM25 都可能打偏。再搜一次值得；按打分结果在子图里循环下去，延迟会叠上去，正式回答却还没开始写。

两次都无关才拒答。 再让主模型拿着低相关摘录硬写，还不如如实说库里没有。第一次失败还值得换一种问法；第二次失败就不该再假装有资料。

扩展检索用新结果替换，不和初检做并集。 初检里已经判过无关的噪声，不应再混进第二次打分。

二次打分对着用户原来的问题。 用户要听的仍是「年费怎么退」，不是改写后的那句退步问题，更不是 HyDE 写出来的假文档。

打分接口失败时，把现有结果交给外层。 对话要的是一句人话，不是前端一个 500 报错。没有打分模型时先改写再搜，比「没有分数就当成相关」更稳：至少还换过问法。

2.4 其它方案

  1. Naive RAG：检索完直接生成。

    • 优点：链路最短，延迟最低，也不依赖打分模型。
    • 缺点：只是碰巧有相同词、却与问题无关的叶子会直接进入回答，拒答码也就没有落点。用户问退款，库里只有开通说明，模型仍可能硬编一条退款政策。

  2. Self-RAG：把打分和改写交给主 Agent。

    • 优点：模型可以自己判断还要不要再搜，少一套子图。
    • 缺点：知识库每轮只许成功一次，主模型换个 query 再调会被配额拦住。质量判断放在工具内部，不占用那一次调用。主循环通常两轮结束，就是不想在这里再拆开。

  3. 没有打分模型就直接生成。

    • 优点：少一次模型调用，改写之后也能马上开始出字。
    • 缺点：结果为空，或全是噪声时，模型更容易编造。现在的默认是：能打分就打，两次都无关再拒答。关掉 KB_GRADE_REFUSAL_ENABLED 会回到这条路上。

3 改写默认退一步，不默认上复杂组合

3.1 策略选择

初检过不了时，用一次轻量级子模型调用决定怎样扩写查询。路由提示里有三种策略：step-back、HyDE、complex。默认只让 step-back 真正执行；complex 即使被选中，也会降成 step-back。没有路由模型，或者路由失败，同样退回 step-back。路由本身是一次结构化输出，只产出策略名，不在这一步生成检索用的 query。真正的扩写在策略选定之后才发生，仍是子图里另一次短调用，不是主 Agent 换了一个 query。

3.2 如何实现

路由提示写在 rewrite_question_node 里。_router_model 复用智能体当前模型，temperature 为 0，只要一段 JSON 里的策略名。随后生成退步问或 HyDE 文档，走的是 rag_utils.py 里的 _chat_from_config，同样复用智能体的地址和密钥，temperature 为 0.2，只输出一句话或一段假资料。扩写之后只再检索一轮，不会回到第一次打分，也不会在子图里循环。

子图里和主 Agent 分开的聊天模型调用可以摊开成下面这张表。

调用 产出 模型从哪来
逐块打分 每块 yes / no 的 JSON 可单独指定 RAG_GRADE_MODEL；没配就用智能体当前模型，temperature=0
改写路由 只输出 step_back / hyde / complex 智能体当前模型，temperature=0

hyde 模糊、概念性、要解释或定义 一段像资料的假设性文档当 query 只这一路，不用原问再搜一遍 路由选中才走
complex 多步骤、要分解或综合 同时生成退步问 + HyDE 文档 先 HyDE，该路 0 条则跳过 step-back，避免第三次向量检索 关（选出也降成 step_back）

问「GPT Plus 年费怎么退？」里面有产品名，多半会选 step-back：先抽出一句更高层的「订阅制年费如何退款」，再和原问拼在一起检索。RAG_STEP_BACK_ANSWER_ENABLED 默认关着，不会先让模型回答那句退步问题。拼出来的 query 仍带着用户原话，BM25 还能对上「GPT Plus」这种专名；退步问则把「年费 / 退款」这种通用说法补进同一句检索里。

若问「什么是按剩余整月折算」，更适合走 HyDE：先写一段读起来像资料的退款条款，再用这段文字去做 embedding 和 BM25。这段假文档只当检索 query，不会当成知识库原文回给外层 Agent。二次打分仍对着用户原来的问题。库里如果真有「按剩余整月折算」那一节，假设性文档更容易和那段原文落在同一个向量邻域里；用户原问太短、太像定义题时，直接搜往往打不中。

RAG_ALLOW_COMPLEX_STRATEGY 默认关闭。即便路由选出 complex，也会先降成 step-back，两路扩写加两路检索根本不会跑。如果真的打开这个开关，会先按 HyDE 检索；这一路如果一条都没有，就跳过 step-back，避免为一次聊天再做第三次向量检索。扩写节点本身还是会把退步问和假文档都生成出来，真正省下的是后面那一次向量检索，不是改写阶段的模型调用。

3.3 为什么这样做

默认只让 step-back 真正执行。 带具体名称或日期的问题，适合先退回通用概念。问「GPT Plus 年费怎么退？」时，退步问补上「订阅制年费如何退款」，原问仍在，BM25 还能对上产品名。这些子模型调用虽然短，但每次都要等一轮 HTTP，默认路径应尽量短。

step-back 默认不先让子模型答题。 如果先生成一句答案再拿去检索，改写阶段就多一次完整生成；那句答案还可能是子模型自己编的，等于用幻觉当 query。现在只生成退步问句，拼回原问一起搜。

HyDE 只在路由明确选中时才走。 模糊的定义题更适合先有一段读起来像资料的文字再去搜。若把「GPT Plus 怎么退」先改写成一段假条款，检索句子里反而找不到原来的产品名。

complex 默认关掉，选出也降成 step-back。 两路扩写加两路检索，是一次聊天里多付几次子模型调用和向量检索。对话要尽快出现第一个字，这条组合不该是默认。

路由失败，或没有路由模型，同样退回 step-back。 空着不搜，这一轮就白走了。没有可用的子模型时，至少还用原来的问题再走一遍检索链路；有模型时，多数带专名的用户问题也落在这一路上。

路由只产出策略名，真正的扩写是另一次短调用。 这一步不要生成检索用的 query，更不要让主 Agent 换一个 query 再调一次工具——知识库每轮只许成功一次，再调会被拦住。

3.4 其它方案

  1. 只做同义改写。

    • 优点：实现更短，问句还是用户那一句的味道，也不必维护三种策略。
    • 缺点：产品名、日期这类细节改不动层次，概念题也变不成一段可以拿去检索的资料口吻。「年费怎么退」换成「年费如何退还」，BM25 未必多打中多少；「什么是按剩余整月折算」仍然太短，不像一段条款。

  2. 让主模型换一个 query，再调一次工具。

    • 优点：改写和答题用同一个模型，少一套路由。
    • 缺点：这一轮知识库只许成功一次，再调会被拦住。扩写必须发生在这一次工具调用里面。主模型如果把改写写成又一次 search_knowledge_base，配额会直接拒绝。

收束

外层 Agent 只决定要不要搜、用哪句话去搜。工具里的子图负责把叶子找出来、把两路结果融合、必要时重排、够密时取回父块，以及打分和拒答。打分、改写路由、生成退步问或 HyDE 文档，都是子图里的轻量级子模型调用，不占用主循环那一次知识库配额。RRF 只看两路各自排第几，Rerank 才判断问题和文档对不对得上。第一次检索如果对不上，就换一种问法再搜；两次都没有相关资料，就不要拿弱检索硬写。complex 默认关着，step-back 默认不先让模型答题。以图检索走另一条子图，不经过打分和改写。
