「Kura-AI」联网搜索工具设计

⭐ Kura-AI 项目链接: https://github.com/MarisaMagic/Kura-AI

0 前言

这篇文章讲的是 Kura-AI 联网三件套在工具里面怎么工作：文字搜索怎样选引擎、怎样把一堆网页排成五条，指定链接怎样读正文，以及搜图为什么不跟网页搜索走同一条链。

外层 Agent 只决定调 web_search、fetch_url 还是 web_image_search，以及参数里填什么。搜哪个引擎、失败了换哪一档、要不要重排、读不读页，都在工具函数里做完。本轮开了联网，三件套会一起挂上，但各有独立的调用次数上限：文字搜索每轮 2 次，读指定页每轮 3 次，搜图每轮 2 次。超过上限不会把对话打断，工具会返回次数用尽的前缀，要求用已经拿到的结果作答。

Function Calling 机制：「Agent Tool」什么是 Function Calling？原理是什么？。

没有检索质量子图，也不会在工具里改写用户问题再循环打分。换一种说法再搜，靠的是模型在这一次调用里填写 extra_query，而不是工具自己再开一轮大模型。

1 web_search：先召回，再排，再读前几条

1.1 策略选择

文字联网搜索做成一条固定流水线。先按运行环境选搜索引擎，尽量多捞一些候选；同一意图如果模型给了第二种说法，两路并行搜完再按网址合并。然后丢掉明显的词典垃圾页，用博查的语义重排看「问题和这条结果到底有多相关」，再用主机结构信号和发布时间做软加权，最后只留五条给模型。五条里默认再打开前三条网页，把主文摘一段进来；读失败就保留搜索引擎给的摘要。

这条链里没有向量库，也没有倒数排名融合。两路查询是拼在一起去重，不是按名次加权。

1.2 如何实现

入口是 make_web_search_tool 里的 _web_search。模型可以填 query，还可以选填 freshness、site、extra_query。时效如果模型没填，就看服务端配置；配置也是 auto 时，再按问句里的时间词推断：今天对应 oneDay，本周对应 oneWeek，本月或「最新 / 近期」对应 oneMonth，今年对应 oneYear，其余不限。site 只接受主机名，例如 openai.com，不要带协议和路径。

工具注册：「LangChain」LangChain 如何为 Agent 注册工具？。

真正调度引擎的是 web_search_providers.py 的 _run_search。默认 WEB_SEARCH_PROVIDER=auto，超时 15 秒，每路最多召回 15 条（WEB_SEARCH_CANDIDATE_COUNT），最终交给模型的是 5 条（WEB_SEARCH_MAX_RESULTS）。地区配置 WEB_SEARCH_REGION=cn-zh 只作用于 ddgs；博查没有地区参数，必应 HTML 这一档写死中文市场。ddgs 在无代理时默认走 bing 后端，有代理时才交给库自己选。

条件 尝试顺序

无代理，且有博查密钥 博查 → bing_html
无代理，也没有密钥 ddgs（backend 默认 bing）→ bing_html

强制写成 bocha、ddgs 或 bing_html 时不降级，失败就整次搜索失败。auto 才会在这一档结果被词典过滤、去重后变成空列表时，换下一档。

问「今年 GPT Plus 年费多少？」时，时效多半会落到 oneYear。博查在限定时效后如果一条都没有，会再用 noLimit 搜一次，避免「今年」把所有页面滤空。site 在 ddgs 和 bing 上会拼进查询词，形如 site:openai.com；博查走接口的 include，查询词本身不加站点。如果模型同时给了 extra_query「ChatGPT Plus 订阅价格」，_run_searches 最多起两路线程并行搜，按 URL 去重后截到 50 条。一路抛异常不会拖垮另一路。召回之后会丢掉标题里带「组词 / 拼音 / 释义」这类词典垃圾的条目，再交给重排。

流水线可以看成下面这张表。重排和读页都发生在引擎返回之后，主模型看不见中间名单。

网页重排走博查 gte-rerank，密钥和网页搜索是同一把 WEB_SEARCH_BOCHA_API_KEY。开关 WEB_SEARCH_RERANK_ENABLED 默认打开；没有密钥就跳过。送进去的文档是标题、站点、日期和摘要，截到 1000 字。接口失败则按引擎原来的顺序继续。默认最低分是 0.2，低于阈值的单条丢掉；如果全部低于阈值，工具按没有结果处理，返回 WEB_SEARCH_NO_RESULTS。

重排之后还要做一次软加权，写在 apply_authority_ranking 里。权威度只看跨领域成立的结构信号：是不是 .gov / .edu 这类后缀、是不是 https、路径是不是很浅、标题和主机是否对得上查询词。仓库里没有品牌或媒体域名表。问句带时间意图，或者 freshness 不是 noLimit 时，再按 datePublished 加新近度：七天内最高，超过一年明显降低，没有日期记 0.5。默认权威度权重 0.25，新近度权重 0.15，剩下的给相关分。相关分优先用重排分；没有重排分就用当前名单里的位次。两项附加权重加起来超过 0.9 时，会按比例压回去，避免相关分被挤没。

排完截到 5 条，再对前 3 条做自动读页（WEB_SEARCH_READ_TOP_N）。单次超时 8 秒，整轮读页还有 15 秒总时限，最多三个并发。正文最多读 512KB，摘录 2000 字；抽主文时会去掉脚本和页脚，优先看 article / main。抽出来的主文短于 80 字算失败。失败不丢这一条，摘要还在。前几条都读失败时，会往后补，直到成功数够 3，或者名单用尽。只允许公网 http(s)，内网地址过不了校验。无代理时读页走固定出口的客户端；配了代理则请求也走代理，并且不信任环境变量里别的代理设置。

回给模型的是编号摘要：标题、站点、发布日期、URL、引擎摘要，读成功时再加一段正文摘录。引用必须按 [来源N] 标注。整段输出会包进非可信隔离，并再受工具回包的总长度上限约束，避免把整页 HTML 原样塞进上下文。引擎整体失败则是 WEB_SEARCH_FAILED，要求如实说明，不得编造链接。

一条读成功的结果看起来大致是这样。站点、日期和正文摘录不一定每条都有。

1.3 为什么这样做

召回、重排、读页这条链必须在工具里做完。 搜索引擎面对的是整个公开网页，结果里会混进词典、转载和过期报价。主模型每轮只有两次搜索配额，经不起「先搜、再请模型判断、再搜」。这条链里没有向量库，也没有倒数排名融合——公开网页不是本地叶子块。

先按运行环境选引擎，而不是绑死一家。 国内环境经常没有代理。博查提供带时效和站点参数的 JSON 接口，适合做无代理时的主路径；有代理时再把 ddgs 放前面，后端可以走到更多搜索源。解析必应中文版 HTML 是最后一档，不依赖第三方密钥，但页面一改解析就脆。强制单源适合排障，不适合作为对话默认。

同一意图的第二种说法，用 extra_query 收在这一次调用里。 文字搜索每轮只许成功两次，同一意图再调一次会很快顶到上限。问「GPT Plus 年费」时，第二路写成「ChatGPT Plus 订阅价格」，往往能补上第一路没打到的官方页。两路按网址去重，不是按名次加权。

语义重排之后，再用权威度和发布时间做软加权。 引擎顺序经常把词典页和转载排在官方说明前面。权威度不维护品牌名单：「哪些媒体可信」会过期，也会和产品绑定。.gov / .edu 和浅路径这些信号在不同领域都还站得住。问句带时间意图时再加新近度，避免过期报价压过今年的说明。

默认只读前三条，读失败保留摘要。 搜索引擎给的摘要经常截半句，价格、日期和免责声明尤其容易被裁掉。五条全读会把这一轮拖得很长，一条都不读则模型只能拿着残句作答。对话不会因为对方站点超时而整轮空白。

重排失败按原序继续。 工具要先保证有结果可引用，而不是先保证排序完美。全部低于阈值才按没有结果处理。

1.4 其它方案

  1. 只绑定一个搜索引擎。

    • 优点：实现短，排障时只看一家的返回，也不必解释 auto 的三张表。
    • 缺点：密钥没配、代理不通、或者这一家当天限流，整轮就空了。auto 降级是为了在国内常见网络条件下还能搜到东西。

  2. 不做语义重排，只按引擎返回的顺序截断。

    • 优点：少一次 HTTP，第一个字出现得更快，也不依赖博查重排额度。
    • 缺点：词典页、聚合转载和问答站经常排在官方说明前面。问年费时，模型更容易先看见过期转载，再据此报一个已经作废的数字。

  3. 五条结果每一条都读页。

    • 优点：正文更齐，摘要骗人的机会更少。
    • 缺点：五次外站请求叠在 15 秒总时限里，慢站会把整轮卡住。默认只读前三条，后面两条仍有标题和摘要，模型若要精读可以再调 fetch_url。

  4. 不在搜索工具里读页，全部交给模型再调一次读页工具。

    • 优点：搜索链路更短，读页失败也不会和搜索绑在一次调用里。
    • 缺点：文字搜索每轮只有两次配额。模型若先搜再逐条读，次数会先被搜占满，指定链接反而读不成。

2 fetch_url：有具体网址才深读

2.1 策略选择

自动读页解决的是「搜索结果够不够看」。用户直接丢过来一个 http(s) 链接，或者模型已经拿到某条搜索结果、要精读那一页，才用 fetch_url。没有网址时不应调用它去「碰运气」。

2.2 如何实现

参数只有 url。函数复用 web_search_reader.py 的 fetch_page：先做公网地址校验，再抓 HTML、抽主文。跳转最多跟 3 次，非 HTML 会拒绝。摘录上限是 4000 字，比搜索链里自动读页的 2000 字更长，因为这一次调用就是冲着「把这一页读清楚」去的。成功时固定编成 [1]，并要求引用标成 [来源1]，URL 必须和返回值逐字一致。失败返回 FETCH_URL_FAILED，不得编造正文。前端来源里这一条的 read_ok 为真。

本轮配额是 3 次，和 web_search 分开计数。本轮如果没有开联网，调用会被禁用，返回禁用前缀。空字符串、或不是 http(s) 的地址，会直接以错误句返回，不发起请求。

还是「今年 GPT Plus 年费多少？」。搜索结果里如果出现官方帮助中心的一条 URL，模型应调 fetch_url 打开那一页，而不是换个关键词再搜一遍。用户自己把帮助页链接贴进对话时，也应直接读，不必先走搜索引擎。工具说明书里把这两件事写在「何时使用」里：有具体网址，或者搜索已经给出了要精读的那一条。

2.3 为什么这样做

有具体网址才深读，没有网址不应拿它去碰运气。 用户贴过来的链接如果先拿去搜，既浪费一次搜索配额，也可能搜到另一份转载。年费页的转载常常改日期、改价格，直接打开用户给的那条 URL，至少知道读的是哪一页。

摘录上限提到 4000 字，高于搜索链里的 2000 字。 搜索链不能把五条结果全部读完，延迟和失败面都太大。指定一页精读，才能在模型已经知道网址时把字数加长，而不拖慢每一次普通搜索。

和自动读页共用 fetch_page，公网校验也一样。 避免出现「搜索能打开、指定链接却绕过检查」的缝。内网、localhost 和需要登录的页面不在范围内：工具不能变成内网探测口；登录墙后面的正文本来也抽不出来，与其返回半页登录框，不如如实说打不开。

配额和 web_search 分开，每轮 3 次。 搜索两次用尽之后，仍应能再读两三页已经搜到的地址。没有独立次数槽，精读会被搜索配额先占满。

2.4 其它方案

  1. 没有 fetch_url，只靠搜索链自动读前三条。

    • 优点：少一个工具，模型不用判断「该搜还是该读」。
    • 缺点：用户贴过来的链接没有落点；搜索结果里排在第四、第五的页面也读不到更长的摘录。官方帮助页若排在后面，自动读页够不着。

  2. 搜索返回的每一条 URL 都自动精读。

    • 优点：模型每次都能看见较长正文，也不必再想要不要调读页工具。
    • 缺点：五次外站请求叠在搜索调用里，首字更慢，失败面也更大。现在把「随便看一眼」和「指定深读」拆开。

  3. 允许模型填写任意 URL，不做公网校验。

    • 优点：内网文档、预发环境也能读。
    • 缺点：工具会变成对内网的开放代理。当前校验就是为了把读页限制在公开网页。需要登录的 SaaS 后台同样不该从这条工具进去。

3 web_image_search：先多捞图，再按画面和来源留下几张

3.1 策略选择

文字搜图是另一条工具，不和网页搜索共用必应 HTML 解析、自动读页，也不走博查那套网页摘要重排。只接受 https 图片。先多召回，滤掉过小的缩略图，有视觉重排模型时再按「这张图和查询词是否相关」打分，然后和来源、尺寸加权，留下六张。前四张直接给出现成的 Markdown 图片行，模型应原样复制到回答里，不要改地址。

查新闻、价格、政策请用 web_search。搜图的 query 要用专名加画面词，而不是「这张图」「类似图片」。

3.2 如何实现

参数是 query，以及可选的 extra_query。两路同样并行合并。例如 query 写「GPT Plus 订阅页」，extra_query 写「ChatGPT Plus 官方定价截图」，两路图会按地址去重后排在一起。调度在 _run_image_search：默认有博查密钥就先走博查图搜，没有再走 ddgs。这条顺序不看有没有代理，和文字搜索的 auto 不同。强制 bocha 或 ddgs 时不降级。无论文字搜索的 provider 怎么写，搜图都不会去解析 bing 的 HTML。博查图搜的时效写死为不限制，也没有 site 参数。

每路最多召回 18 张（WEB_IMAGE_SEARCH_CANDIDATE_COUNT），只留 https，并按图片地址去重。随后丢掉长边小于 240 像素、且宽高已知的缩略图；如果筛完一张都不剩，仍退回原来的缩略图，避免整轮空白。本轮回答里已经用过的图片地址会被去掉，减少同一张图反复贴。

视觉重排复用对话里已经配好的 RERANK_MODEL、RERANK_API_KEY、RERANK_BINDING_HOST。三者都有，且模型名里包含 vl-rerank，才会走 DashScope 多模态重排。图用 https 原图 URL 送进去，不转成本地文件再编码。对方如果拒绝按 URL 拉图，这一路会记失败，按筛选后的原序继续。没有网页重排那种最低分门槛，单张分低也不会整批发空。

最后按相关分、来源页权威度、尺寸做融合，尺寸默认权重 0.15。没有宿主页的条目会略减分。宿主页落在常见聚合站上会再减一截，落在更干净的图床上会略加分。截到 6 条时，如果干净来源已经够数，聚合站会被挤出名单；不够数才把它们补在后面。前 4 条带 ![说明](https://...)，后面两条只给标题和地址。失败前缀是 WEB_IMAGE_SEARCH_FAILED，一张可用 https 图都没有则是 WEB_IMAGE_SEARCH_NO_RESULTS。搜图成功时，图片来源会合并进本轮已经有的网页来源，不会把刚才的搜索结果冲掉。

配额每轮 2 次，和文字搜索分开。本轮没开联网，同样会被禁用。

3.3 为什么这样做

搜图是另一条工具，不走必应 HTML、不自动读页、也不走网页摘要重排。 网页摘要重排只看见标题和一段文字，判断不了画面是不是用户要的那张订阅页截图。再抓一遍宿主页既慢，也帮不上选图。时效和站点参数也不往搜图上搬：图搜引擎对「今年」「只要 openai.com」的支持参差不齐，硬套文字搜索的 freshness 容易整路空掉。

只接受 https，先多召回，再滤掉过小的缩略图。 缩略图和聚合站会把回答撑满广告和水印。筛完一张都不剩时仍退回原来的缩略图，避免整轮空白。

有视觉重排模型时，按画面和查询词是否相关打分。 密钥复用已有的重排配置，少维护一组凭证；模型名必须带 vl-rerank，普通文本重排模型接上去没有意义。图用 URL 送进去，搜到的本来就是外链，不必先下载到应用自己的对象存储再编码。

前四张给出现成的 Markdown 图片行。 模型自己拼地址时，经常改协议、加参数，或者把外链改成站点内部的媒体路径。后面两张只给地址，是给模型一个「不够再看」的余地，又不把六张图都铺进回答。

图片来源合并进本轮已经有的网页来源。 同一轮里先搜网页再搜图时，如果覆盖而不是合并，前端只剩下几张图，刚才的五条网页引用会消失，用户点不开 [来源N]。

配额和文字搜索分开，每轮 2 次。 查新闻、价格、政策应走 web_search；搜图不应占掉那两次文字搜索。

3.4 其它方案

  1. 搜网页，再从结果页里抽图。

    • 优点：少一条工具，引擎也只用一套。
    • 缺点：搜索结果页上的图经常是图标、广告和作者头像，和「GPT Plus 订阅页长什么样」对不上。

  2. 不做视觉重排，只按引擎返回的顺序截断。

    • 优点：少一次外呼，不依赖多模态重排模型。
    • 缺点：引擎排序看的是页面，不是画面。专名对上了、构图完全不对的图，仍会排在前面。

  3. 只回图片 URL，让模型自己拼 Markdown。

    • 优点：工具输出更短。
    • 缺点：模型会改写括号里的地址，前端预览和用户看到的图就对不上。现成行是为了减少这一步走样。

收束

联网三件套分开做事。web_search 负责把公开网页找出来、排好、读前几条；fetch_url 负责打开已经知道的那一个地址；web_image_search 负责留下几张能直接贴进回答的图。次数上限分开计算，本轮开了联网才能用。搜索引擎可以换档，重排和读页失败都按「还有结果就继续」处理；真正没有可用结果时，用稳定前缀要求如实说明，不要编链接，也不要编图片。

问「今年 GPT Plus 年费多少？」通常先走文字搜索；看见官方帮助页再精读；若用户还想看订阅按钮长什么样，再走搜图。三条链不要拧成一次调用。
