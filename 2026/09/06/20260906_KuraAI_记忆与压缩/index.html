「Kura-AI」长短期记忆与超长上下文压缩

⭐ Kura-AI 项目链接: https://github.com/MarisaMagic/Kura-AI

0 前言

这篇文章讲的是对话变长以后，Kura-AI 还让模型看见什么。近期的原话怎样收成一份摘要，被挤出窗口的整轮怎样归档，以及「之前那个订单号」这种指代题怎样捞回来。

Kura-AI 把这件事拆成两层。短期工作记忆是送给主模型的那份视图：一份滚动摘要，加上最近一段原文。长期记忆是已经离开原文窗口的整轮对话，切块后写入独立的向量集合。外层 Agent 只决定要不要调 search_session_memory、query 填什么。压缩阈值、归档水位、预注入都在服务端做完。

记忆机制：「AI Agent」Agent 的记忆机制：四层记忆分类与记忆模块设计。

记忆是这一次会话里已经说过的话。属主知识库里预先入库的退款说明，走 search_knowledge_base；本会话刚上传的 PDF，走附件工具。三者不要混。同一会话里，用户早先说过「订单号是 GP-2026-8841，按开通未满 7 天退」，隔了许多轮再问「之前那个订单号是多少？」——近期原文窗口里往往已经看不见这句话；压缩摘要可能还留着线索，精确编号要靠归档检索。

1 按字符预算压缩，不用固定 N 轮

1.1 策略选择

上下文按估算字符触发压缩，留下最近一段原文，更早的轮次收成一份可重放的摘要。不在库里改写历史。触发看的不是 token 数，也不是「满了 10 轮」，而是一份粗估的 prompt 长度。

压缩只在主循环开始前做一次。工具跑完新产生的回包，这一轮不再压。最后一轮原文永远留下，避免把用户正在问的那句话也摘要掉。

1.2 如何实现

入口是 build_compacted_model_messages。默认 CHAT_COMPACT_ENABLED 打开。估算公式把几块加在一起：工具 schema 粗估 8000、system 人设和检索纪律、已有摘要、原文窗口，再留 12000 给工具回包。加起来达到 80000 字符才压；压完后从后往前留大约 24000 字符原文。关掉压缩，才回退到最近 10 轮的滑动窗口。记忆总开关也关着时，连窗口都不切，全量历史进模型。

记忆压缩：「AI Agent」Agent 记忆压缩：四种方法与 Prompt Caching 互补。

一轮是一条用户消息，加上其后直到下一条用户消息之前的助手和工具回复。被挤出的轮次打成纯文本，和「已有摘要」一起交给子模型，temperature 为 0，滚成一份不超过 4000 字的新摘要。提示要求留下目标、决定、未完成事项，以及文件名、URL、ID、数字这类实体；不要写入本轮检索开关、选档范围或附件名单，也不要抄知识库或网页的大段原文。

摘要写成一条独立的 Human，插在原文窗口前面，标题是 【会话压缩摘要】。本轮用户原话仍是最后一条。附件名单、读图描述、记忆摘录都贴在那一条上，不入库，也就不会被下次摘要吃掉。

这份视图只影响送给主模型的消息。storage 里的原文只追加、不删、不替换。刷新页面仍看得到早先那句订单号。摘要写入 session metadata 的 compact_states，最多留 4 条，按当前路径的 turn_key 前缀匹配：共享前缀复用同一份摘要，分叉后各走各的。turn_key 是该轮用户消息的行 id。

摘要失败（没有密钥、模型空输出、调用异常）时，本轮仍按新窗口截断原文，不更新 metadata。下次再试滚摘要。前端步骤会写成「本轮仅截断较早原文」。

1.3 为什么这样做

按字符预算压，不按固定轮数。 一轮里可能有很长的工具回包，十轮也可能远超窗口；短轮对话里，十轮又往往还没到该扔的时候。固定 10 轮会在短轮时浪费，在长轮时提前丢掉关键信息。

不是 token 计数。 项目里没有 tiktoken 一类的计数器。用字符近似真实 prompt，中英文和图片会有偏差，但够用来决定「该不该再挤一轮」。工具 schema 和回包余量算进估算，是因为压缩不会在工具循环里再跑一次。

摘要进 metadata，原文留在库里。 前端历史仍要完整。把旧消息从库里删掉换成摘要，重新生成、分叉、用户回看都会对不上。模型看不见的，是视图，不是存储。

失败不写坏摘要。 空摘要一旦落进 metadata，后面每一轮都会带着它重放。本轮先硬切，水位不前进，下次还有机会滚出一份能用的。

摘要是独立 Human，不进人设。 写进 system，人设会被一份经常变动的长文撑开，外部对话也更容易被当成指令。插在窗口最前、用户原话仍在最后，本轮材料和压缩摘要才分得开。

1.4 其它方案

  1. 只留最近 N 轮，不做摘要。

    • 优点：实现短，也不依赖子模型。
    • 缺点：「之前那个订单号」如果刚好落在第 11 轮，模型手里什么都没有。硬切没有给关键实体留一份可重放的线索。

  2. 把旧消息从库里删掉，换成摘要。

    • 优点：库更瘦，模型视图和存储一致。
    • 缺点：用户回看、重新生成、切到另一条分支时，原文没了。现在只换送给主模型的那一份。

  3. 压缩失败也写入空摘要。

    • 优点：水位能往前走，后面不再反复撞同一段旧文。
    • 缺点：坏摘要会锁死后面每一轮。宁肯本轮只截断，下次再试。

2 离开窗口的整轮，增量归档进独立集合

2.1 策略选择

只有压缩已经不再送给主模型的那些轮，才写入 kura_ai_chat_memory。按 turn_key 幂等去重。摘要本身不入库。对话落库后默认在后台做，不挡第一个字。

LangChain 长短期记忆（Kura 用 metadata 加独立集合，不照搬）：「LangChain」LangChain 如何实现长短期记忆？。

关掉压缩时，水位线仍读 compact 的 metadata，通常还是 0，几乎不会归档。工具说明书里仍写着「滑动窗口之前」，实际能搜到的是：原文窗口之前、并且已经写入归档水位的那些轮。

2.2 如何实现

助手消息写入存储之后，调用 schedule_archive_session_memory。默认 CHAT_MEMORY_ARCHIVE_ASYNC 打开，丢进后台线程。归档函数先问 verbatim_keep_from_for_session：压缩声明从哪一轮开始还留原文。只处理「下标小于这个水位、且 turn_key 还不在 memory_archived_turn_keys 里」的整轮。

每一轮先 turn_to_text：用户、助手、工具各打成一段纯文本，图片和附件变成占位，不把像素写进向量。再按默认 1400 字硬切，没有重叠。嵌入复用知识库同一套多模态服务，只算文本。集合是独立的 kura_ai_chat_memory，隔离键是 memory_scope = u{user}_a{agent}_s{session}。检索时还要再加当前路径上已归档的 turn_key，旁支轮次即使同 scope 也滤掉。

分叉时，共享前缀只归档一次。切回旧分支再聊，水位里还没有的那些轮会继续补。删会话、删智能体时按 scope 清向量。库里还有一张 mg_chat_memory_cursor，已经不再写入，现行水位在 session metadata 的 turn_key 集合上。

没有 embedding 密钥就跳过归档。压缩失败、metadata 没前进时，本轮被硬切掉的那些轮也暂时不进集合，下一轮压缩成功后再补。

2.3 为什么这样做

水位跟压缩走，窗口里的轮次不归档。 近期原文主模型已经看得见。再嵌一遍，等于给同一段话付两次嵌入，检索时还要和近轮抢名次。

摘要不进向量库。 摘要是给主模型省窗口的，已经丢掉了不少细节。把这份损失过的文本再向量化，长期记忆里就只剩「好像提过一个订单号」，精确的 GP-2026-8841 反而找不到。归档写的是被挤出轮次的原话。

独立集合，按会话隔离。 和知识库共用一张表，会把「用户说过的话」和「属主文档」混在一起。记忆键带上 session，换一个会话就看不见这串订单号，这是对的。

后台归档，不挡第一个字。 嵌入和插入可能慢。对话已经落库，用户正在等下一句；归档失败只打日志，下次按 turn_key 再试，不会把半成品标成已归档。

本轮刚挤出的轮次，本轮还搜不到。 压缩发生在调用主模型之前，归档发生在整轮结束之后。预注入和工具读的是上一轮及更早已入库的块。隔一轮再问「之前那个订单号」，才稳。

2.4 其它方案

  1. 每一轮都归档，包括仍在原文窗口里的。

    • 优点：刚说过的话立刻能搜，也不必等压缩。
    • 缺点：近轮原文和向量里是同一段话。预注入再贴一遍，上下文重复，嵌入费用也上去。

  2. 记忆写入知识库那个集合。

    • 优点：少维护一套 schema 和混合检索。
    • 缺点：隔离键少了 session，分享智能体时可能搜到别人会话里的订单号。文档检索和对话检索也会互相抢召回。

  3. 把压缩摘要也当成记忆块写入。

    • 优点：主模型正在看的那份线索，检索也能打到。
    • 缺点：摘要会覆盖原话里的编号和约束。现在只归档原话，摘要留给短期视图重放。

3 预注入摘录，不够再调一次工具

3.1 策略选择

每轮用当前问句先捞几条较早摘录，写进本轮 Human。仍不够，模型再调 search_session_memory，同一轮只许成功一次。答案已经出现在最近原文里，或者该查知识库、该读附件时，不必调。

3.2 如何实现

预注入走 proactive_session_memory_inject_text，默认 top 3。流式路径里和知识库选档并行预取，用的是上一轮已经归档的 turn_key。有命中就拼进本轮上下文块，标题写明「仅供参考；若仍不足可再调用 search_session_memory」。这块不入库。

工具只有一个参数 query。先 try_acquire_memory_tool_slot，占不到就回 TOOL_CALL_LIMIT_REACHED，要求用已有结果作答。过了配额，先把「那个 / 上次」改写成适合检索历史的短句，再做混合检索，默认 top 5。过滤条件是当前 memory_scope，加上当前路径上已归档的 turn_key。没有嵌入密钥，工具回「会话记忆检索不可用」。无命中则说较早对话里没有相关片段。

改写失败就用用户原话。检索异常当成没有命中，循环不拆。系统提示里没有单独的「记忆失败不得编造」纪律，约束写在工具说明书里：近轮正文里找得到就别调。

3.3 为什么这样做

指代题不应等用户说「检索历史」。 「之前那个订单号」就是在问窗口外面的事实。预注入用当前问句先捞一把，主模型第一跳往往已经够答。

摘录进本轮 Human，不进 system。 旧对话是外部文本。写进人设，模型更容易把几年前的一句偏好当成长期指令。跟在用户问句后面，只对这一问有效，刷新后再 load 也不会把摘录当成用户原话。

工具每轮只许成功一次。 记忆没有本轮开关，但有次数槽。模型若为同一句指代连调两次，第二次应停下来用已有片段作答，而不是把归档当知识库那样改写再搜。

先改写再检索。 「那个订单号」单独做向量检索，打不中早轮里的 GP-2026-8841。改写成「GPT Plus 退款订单号」，语义和字面都更近。改写失败仍用原句，总比这一轮空着强。

Query Rewrite：「RAG」如何润色用户的 Query（Query Rewrite）？目的是什么？。

只搜当前路径上已归档的轮。 另一条重新生成的旁支里，用户可能报过另一个号。不过滤 turn_key，模型会把分叉里的话当成这一条线的事实。

3.4 其它方案

  1. 不做预注入，全靠模型自己调工具。

    • 优点：少一次嵌入和一次改写，首字更快。
    • 缺点：模型不一定记得去调。指代题更容易在近轮原文里瞎猜一个号。

  2. 把预注入写进 system。

    • 优点：每轮都能在最前面看到。
    • 缺点：人设被一份变动的摘录撑长；旧对话进了 system，注入风险更大。

  3. 记忆检索不限次数。

    • 优点：第一次没命中还可以换个说法再搜。
    • 缺点：没有次数槽，模型会在循环里反复打同一份归档。现在预注入已经先捞过，工具再补一次够了。

  4. 不做 query 改写，原句直接检索。

    • 优点：少一次子模型调用。
    • 缺点：「那个」「上次」几乎没有字面可对。订单号这种题，改写就是为了把指代补全。

收束

近期靠原文加滚动摘要，远期靠归档向量。压缩不删库，归档不写摘要，检索只看当前路径上已经离开窗口的那些轮。主模型开始前压一次，工具循环里不再压；刚挤出的轮次要等本轮结束后入库。订单号还在近轮原文里，不必搜记忆；已经只剩摘要线索时，先看预注入，不够再调一次工具。
