「Kura-AI」知识库构建设计

⭐ Kura-AI 项目链接: https://github.com/MarisaMagic/Kura-AI

0 前言

这篇文章讲的是 Kura-AI 知识库是如何构建的：一份文档怎么变成可检索的叶子块，对应的向量和原文分别存储在哪，以及删掉或替换时为什么不能把正在用的旧库直接删除。

什么是 RAG：「RAG」什么是 RAG？详细描述一个完整 RAG 系统的详细工作流程？。

Kura-AI 选的是 一份智能体一份库，先切成三层分级树状的结构，然后只把叶子切块进行向量化。「这份知识库属于谁」交给 kb_scope 隔离；「切多细、重叠多少、怎么少切断语义」交给页内递归切分；「失败了会不会把旧文档清掉」则由后台流水线在算完向量之后再安全替换清除。混合检索、查询改写、检索结果打分和是否拒答留给后文。

1 知识库三部分构成

1.1 策略选择

Kura-AI 中的知识库由三部分构成：元数据进 PostgreSQL，叶子向量进 Milvus，文件本体进 MinIO 对象存储。项目里没有单独的「知识库」表，也没有 kb_id 外键——隔离靠一个字符串 kb_scope = u{user_id}_a{agent_id}。一个用户多个智能体，就是多套互不可见的库。

启动时会预热集合。MilvusManager().init_collection 写在应用启动阶段，第一次连得慢，提前做完，避免首个上传任务卡在建表。管理页只对属主开放：上传、取消、删除、看进度。被分享用户没有管理入口，只能在对话里检索。

1.3 为什么这样做

三套存储各管检索里真正不同的一件事：叶子负责被找到，父块负责被读回来，原件负责被取走。 问「GPT Plus 年费怎么退」的时候，这三件事不会落在同一套引擎上。

叶子进 Milvus。 真正拿去近邻搜索的，是「开通未满 7 天可全额退」这类 L3 短句，以及同一页抽出来的 L4 图。集合只要把这件事做稳：写入 dense 向量，由服务端按 text 算出 BM25，再按 kb_scope、filename 先圈定范围再搜。全站共用一个 kura_ai_kb，隔离写在字段上，schema、HNSW 和 BM25 Function 只建一次。启动时预热的也是这一份，不必每来一个智能体就再建一张表。

向量数据库：「RAG」什么是向量数据库？。

父块进 PostgreSQL。 L1 / L2 不是拿来搜的。检索打中那句退款叶子之后，若要把整段退款规则一并读给模型，后文会按 chunk_id 回表，把更大的 L2、L1 捞回来。入库时只有 L3 / L4 会走 embedding；父块用 Text 存全文就够。把 1800 字的根块再向量化一遍，既多花钱，也会和短叶子抢召回。Milvus 的 text 字段上限是 2000 字符，本来就是给可检索的短叶子用的，不是给大段正文准备的。

原件进 MinIO。 kb_service.py 模块头写得很直白：文档和图片本体存对象存储，PostgreSQL 只留元数据。上传上限 50MB，原 PDF 要下载、抽图要按路径取，这些按对象 key 处理更合适。向量行里只留 image_path 这类字符串，不把整份文件塞进集合。应用用的 MinIO 和 Milvus 内部那套是分开的，互不抢盘。

不做一张独立的知识库实体表。 「这份库是谁的」用 kb_scope 就能定下来。共享集合省运维，代价是每条写入都必须带对隔离键。被分享的人没有管理入口，对话里搜到的仍是属主那一份——隔离键比再复制一份库更合适。

1.4 其它方案

  1. 每个智能体一个 Milvus collection。

    • 优点：隔离写在集合名上，过滤条件更短，误写也不容易串到别人的库。
    • 缺点：每多一个智能体，就要多建一份 schema、HNSW 和 BM25 Function。启动预热、备份、升 schema 都得逐个做。现在清空一个智能体，是按 kb_scope 删行，不是丢掉整个集合。Kura-AI 目前还只是一个小项目，一个集合加字段过滤够用。

  2. pgvector，向量也进 Postgres。

    • 优点：文档行、父块和向量可以放进同一套事务，删除时一条 SQL 就能对齐。
    • 缺点：项目要的是 dense 近邻再加服务端 BM25，还要和会话记忆共用同一套 Milvus 运维。官方 postgres:17 镜像没有向量扩展；pgvector 能和业务表做 JOIN，但混合检索和 HNSW 仍弱于专用向量库。再在 Postgres 里自建一套，等于把向量库的活搬进文档关系库。

  3. 本地 Chroma / FAISS，自己拼 BM25。

    • 优点：依赖少，单机就能跑，原型验证更快。
    • 缺点：按 kb_scope 过滤、多智能体隔离、词法检索都要自己扛。本地向量索引能做近邻，但服务端 BM25、标量过滤这些还是得另写。项目里走过进程内自建 BM25：重启一次词表会漂，IDF 也会歪。后来才把稀疏检索交给 Milvus，dense 原样复制，不再维护那份本地词表。

2 三级分块，叶子进向量库

2.1 策略选择

文档切分走的是 按页递归、按自然边界下刀切块。先把 PDF 的一页、Excel 的一张表、或 txt / md 的整篇当成一个切分单位，再用三套字符级 RecursiveCharacterTextSplitter（递归字符切分：先找段落，找不到再找句子）嵌套切出 L1 → L2 → L3。

这里其实有 两层递归：分隔符从粗到细试，直到这块能塞进这一层的窗口；层级上则是页切完 L1，再对每个 L1 切 L2，再对每个 L2 切 L3。某一层的文本如果已经不超过窗口，就原样留下，不再往下切——但三层还是都会各写一行，不会因为够短就跳过 L2 或 L3。

页内不按 Markdown 标题切，也不按 token 切。知识库里大量是 PDF 和 Word，没有可靠的 heading 树；.md 也和 txt 走同一条 _load_text_pages，不会先抽一级、二级标题。页和页之间也不合并，短页就是一页一条链，长页才在页内分出多个根。

分隔符策略 主要是：段落 → 换行 → 中英文句号问号 → 逗号顿号 → 空格 → 实在不行再硬切。相邻块大约重叠 13%，避免一句话被拦腰截成两半之后两边都检索不上。

规避语义切割：「RAG」怎么规避语义被切割掉的问题？。

只检索叶子块。 细的 L3 块用来 ANN 近邻搜索语义相似度高的向量，粗的 L1 / L2 块留在 PostgreSQL，命中碎了再升到更大上下文——那是后文 Auto-merge 的事，构建阶段先把父子关系留下。PDF 和 Word 里抽出的图单独做成 L4，整张一块，不参与这段文本切分。

文档切割：「RAG」RAG 中的文档是怎么存的？有哪些文档切割（Chunking）策略？。

2.2 如何实现

默认 chunk_size=900、chunk_overlap=90，推导出三层窗口。重叠大约都是窗口的 13%，落在常见的 10%～20% 区间里：

层级 角色 窗口 重叠
L1 根块 / 粗上下文 1800 240
L2 中间父块 900 120
L3 检索叶子 450 60
L4 图片叶子 整张图 无

切的时候尽量停在段、句上；切完之后，跨边界的半句会靠重叠出现在下一块里。真正切开 L1 的门槛是 1800 字，不是 Milvus 那个 2000 字的字段上限——2000 管的是后来进集合的叶子，L1 根本不进向量库。

还是「GPT-Plus退款说明.pdf」。第 2 页如果字不多，比如只有 400 字，三层窗口都切不动（400 小于 1800、900、450），就会退化成一条链：一个 L1 下面挂一个 L2，再挂一个 L3，三段正文几乎就是整页。父子关系还在，只是三层内容重合。

第 2 页如果很长，比如 2500 字，超过 L1 窗口，就会在页内切成多个根，相邻 L1 重叠约 240 字；每个 L1 再切自己的 L2 / L3。这一页是两棵树并排，不是一条链：

中间长度按窗口决定在哪一层分叉。一页 600 字仍是一个 L1、一个 L2，但 600 大于 450，叶子可能切成两块；一页 1000 字仍是一个 L1，但会先分出多个 L2。

「开通未满 7 天可全额退」如果刚好落在两个 L3 的交界上，前一块会带上后半句的开头，后一块会带上前半句的尾巴。父子靠 parent_chunk_id / root_chunk_id 串起来。L1 / L2 全文进 PostgreSQL；后文检索若同一父块命中够密，再升到更大段——构建时已经把这个钩子留下了。

格式分流在 load_document。先按类型读成「页」，再对每一页走同一套三级切：

类型 怎么读 切分单位 图
PDF PyPDFLoader 抽文本，PyMuPDF 抽图 每页独立三级切 小于 100×100 丢掉
Word Docx2txtLoader + python-docx 抽图 按 loader 的页 有，位置只能估算
Excel 每个可见 sheet 转 Markdown 表 一 sheet 当一页 不抽
TXT / MD 整文件当成 page=0 同一套三级切 无

只接受 pdf / docx / doc / xlsx / xls / txt / md。代码文件进不来。chunk_id 带上 scope、文件名指纹、页码和层级。文本叶子长得像 u1_a3::{fingerprint}::p2::l3::0，图片再加 ::i{序号}。图文关联写在图片行的 related_text_ids 里：PDF 优先按页面位置找图上方最近的 L3；对不上坐标的，按阅读序配对。同一页如果有流程图，会再出一块 L4，并记下它关联了哪几个 L3。

2.3 为什么这样做

按页递归，按自然边界下刀。 语义被切断，往往不是字丢了，而是一句话被拆成两半之后，每一半单独看都不够像答案。退款说明里如果写成「开通未满 7 天可全额退，超过则按剩余整月折算」，切刀刚好落在逗号上，前半只有「可全额退」，后半只有「按剩余整月折算」——问「年费怎么退」，两边都可能检索不上。分隔符从段落试到句子，是为了让切刀尽量停在句号和换行上，而不是停在词中间。

页内不按 Markdown 标题切，也不按 token 切。 知识库里大量是 PDF 和 Word，没有可靠的 heading 树；.md 也和 txt 走同一条加载路径。一套按页、按段落和句子的切法，才能覆盖现在允许的全部格式。

相邻块大约重叠 13%。 切刀再小心，仍可能落在句中。重叠把跨界的半句补进下一块，前一块带着后半句的开头，后一块带着前半句的尾巴，两边才都还有机会被找到。

只检索叶子，父块不向量化。 块太大，退款条款和免责声明这样的类似文本挤在一起，相似度会被冲淡；块太小，模型看见的是半句话。细的 L3 / L4 负责被找到，粗的 L1 / L2 留在 PostgreSQL，命中够密再升段。少算两层 embedding，集合也更小。

图不能单独当文档上传。 没有页内位置，就挂不上旁边的文字，后文也补不回同页关联。PDF / Word 里抽出的图做成 L4，整张一块，不参与这段文本切分。

2.4 其它方案

  1. 按 Markdown heading / AST 切。

    • 优点：章节边界清楚，标题不会被拦腰截断。
    • 缺点：不是不能按标题切，而是知识库里的 PDF、Word、Excel 撑不起 heading 树。txt 更没有结构。一套按页、按段落和句子的切法，能覆盖现在允许的全部格式。

  2. 固定窗口一层切到底。

    • 优点：实现短，块大小均匀。
    • 缺点：检索和阅读用同一粒度。没有重叠时，切刀落在句中，语义会直接断掉；没有父块时，命中碎了也补不回上下文。

  3. 父子块都进向量库。

    • 优点：检索可以直接打到大段上下文，少一次回表。
    • 缺点：embedding 费用和集合体积都会上去。父块本来就不是拿来近邻搜索的，放进 PostgreSQL 按 id 回捞就够。

3 图文多模态稠密向量，BM25 稀疏检索

3.1 策略选择

叶子分块进 Milvus 集合之后，检索会走多路召回。

  • 稠密向量，主要看语义相似度：问「年费怎么退」，也能撞上写着「全额退款」的句子，以及同一页里那张退款流程图。文本和图共用 DashScope qwen3-vl-embedding，都是 1536 维，落在同一套空间里。
  • BM25 稀疏向量，主要看关键词匹配：问「GPT Plus」，就要靠这两个词本身把叶子分块召回。

稠密向量由客户端算完再写入。BM25 那条稀疏向量交给 Milvus 的服务端 Function：写入时从 text 字段自动生成 bm25_sparse。图片块的 text 是空的，词法检索基本只服务文本叶子；图主要靠同一空间里的稠密向量被找到。

3.2 如何实现

一份文件落库以后长这样：

写入拆成两段，写在 app/kb/multimodal_milvus_writer.py 的文件头里：embed_documents 只算稠密向量，write_documents 才 insert。文本按 EMBEDDING_BATCH_SIZE=10 一批；图一张一请求，失败填零向量，不中断整篇。单次嵌入 HTTP 超时 90 秒，避免 SDK 默认 300 秒把任务挂死。稀疏那一侧不用客户端填数，insert 带上 text 即可，集合里的 bm25_fn 会现场算好。

检索真正用到的字段是 dense_embedding（HNSW + 内积）和 bm25_sparse。隔离、文件名、层级、内容类型都是普通字段，给过滤用。filename 是展示名，主要用于删除和选档。分词用的是内置 standard 分析器：英文按词切开，中文精确的单字对上主要还是靠稠密向量兜底。

3.3 为什么这样做

文本和图共用同一套多模态稠密向量。 问「年费怎么退」，既要撞上写着「全额退款」的句子，也要撞上同一页里那张退款流程图。各用一套 embedding，文本查询就打不到图，还要维护两套维度和两套失败重试。现在都是 1536 维，入库和检索只走一条路。

稠密向量由客户端算完再写入。 语义相似度这一路跟 embedding 模型绑定，必须在插入前算好。图一张一请求，失败填零向量，不中断整篇。

BM25 稀疏向量交给服务端 Function。 BM25 要两样东西：一份词表，给每个词编一个编号；以及 IDF，也就是这个词在多少篇文档里出现过（文档出现频率）——越稀有，越能把文档区分开，「的」几乎每篇都有，权重接近零，「退款」只在少数叶子里，权重就高。旧方案把这两样放在 Kura-AI 进程的内存里，先算出每个叶子的稀疏向量（一串「词编号 → 权重」），再写进 Milvus。查询时也必须用同一份词表，编号对得上才能搜到。

词表跟进程走，重启一次编号就会漂。 应用一重启，内存清空，词表往往要按当时库里的文档重新建。重建顺序、后来新上传的文件只要有一点不一样，「退款」就可能从 42 号变成 87 号。库里旧叶子还写着「42 号很重要」，查询却按 87 号去对，对错了号。这就是跨重启索引漂移：索引还在，语义编号已经换了。多开几个进程时，每份词表还可以各编各的，同一句查询编出来的编号都不一样。

IDF 也会慢慢对不齐。 它依赖写入那一刻整个库有多少篇、这个词出现在几篇里。后来又传了二十份文档，「退款」从很稀有变成挺常见，新查询按新库算权重，旧叶子里却还是老数字，对不齐就是 IDF 失真。

所以客户端只写原文 text。 Milvus 在插入时自己生成 bm25_sparse，查询也直接喂这句话，由同一套函数编码。词表和 IDF 跟集合走，不跟 Python 进程走，应用重启，编号不会换。migrate_bm25.py 换的是集合的 schema，不是 embedding 模型：已经算过的 1536 维稠密向量原样搬到新集合，不再打 DashScope；旧的进程内稀疏向量丢掉，插入时带上 text，由 bm25_fn 重新生成。

图片块的 text 是空的。 词法检索基本只服务文本叶子；图主要靠同一空间里的稠密向量被找到。问「GPT Plus」靠字面召回句子，问「年费怎么退」靠语义召回句子和图。

3.4 其它方案

  1. 客户端自己维护 BM25 词表。

    • 优点：不依赖 Milvus 版本，换向量库也能把这套编号带走。
    • 缺点：词表跟进程走。重启一次、多开几个实例，编号和 IDF 都可能对不齐，召回就会飘。项目里走过这条路，后来才把稀疏检索交给集合，正是不想再维护那份本地词表。

  2. 文本、图片各用一套 embedding 模型。

    • 优点：各自可以选更「专」的模型。
    • 缺点：文本查询打不到图，还要维护两套维度和两套失败重试。多模态同一个空间，入库和检索都只走一条路。

  3. 每份文档一个 collection，或把分区当主键。

    • 优点：删一份文件等于丢一个集合，级联最干净。
    • 缺点：文档一多，集合爆炸。按文件名字段过滤就够，现有字段已经能做到。

4 失败不毁旧库，删除按层清干净

4.1 策略选择

一份文档同时存储在四层：Milvus 里的叶子、PostgreSQL 里的父块和文档行、Redis 里的父块缓存，以及 MinIO 里的原件和抽图。这几套存储之间没有外键，也没有 ON DELETE CASCADE。删一份文件、清空一个智能体、或者用同名文件覆盖，都只能由应用按 kb_scope 和文件名，一层一层清干净。

同名替换不是「先删再解析」，而是先建好再级联删除旧的数据。 新版本还没算完向量之前，对话里仍能搜到旧的退款说明；只有新叶子确实正常写入数据库，旧的数据才会被安全清除。

4.2 如何实现

上传接口只负责受理。POST /kb/upload 做完魔数校验（文件类型校验）和 50MB 上限，立刻返回 task_id。解析和嵌入会堵住事件循环，所以丢进 kb_job 的线程池，最多 8 路并行。进度按阶段往前走：queued → parsing → chunking → embedding → writing。

真正入库的是 run_ingest_pipeline_sync。注释把顺序写死了：解析和全部向量都成功之前，不碰正在用的旧数据；成功之后才进替换临界区，删旧、写父块、插入叶子、补图片元数据、最后写下文档行。

如果这份 GPT-Plus退款说明.pdf 的内容 哈希没变，直接标 unchanged 跳过，省掉一次 embedding。内容变了，才用 Redis 的 NX 锁走进临界区，后完成的那一次生效，避免两个人同时传同名文件把半成品交错写进去。失败、超时或用户取消，只清掉这次的临时文件，旧文档原样留着。

用户主动删掉某一个文档时，走 delete_kb_document：先按 kb_scope 和文件名删向量，再删 父块和缓存，再删文档行，再删抽图——同名替换时可以把新图正在用的 key 排除掉，免得刚传上去的图被一起清掉——最后删原件。删整个智能体时，delete_user_agent 在 obj.delete() 之后调用 purge_kb_for_scope，按 scope 把上面这几步做完。账号删除目前不走这条清空。

4.3 为什么这样做

同名替换先建好，再级联删除旧数据。 嵌入是整条流水线里最慢、也最贵的一步。如果一上来先把旧行删掉，再去解析和算向量，超时或用户点了取消，刚才还能搜到的退款说明突然没了，进度条上却只看得到失败。先把新版本完整准备好，再替换，空档只会落在「删旧到写新」这一小段临界区里。

四套存储没有外键，也没有统一事务。 PostgreSQL 里就算给三张表加上 ON DELETE CASCADE，也管不到 Milvus 和 MinIO。删一份文件、清空一个智能体，都只能由应用按 kb_scope 和文件名，一层一层清干净。

图片对象的 key 带内容哈希。 同名文件覆盖时要删旧图，新图正在用的 key 必须排除掉，才不会把刚写进去的图一起清掉。

4.4 其它方案

  1. 数据库 ON DELETE CASCADE。

    • 优点：PostgreSQL 里的文档行、父块和图片索引可以跟着主表一次清掉，应用少写几步。
    • 缺点：清不了 Milvus，也清不了 MinIO。这几套存储不在同一个数据库事务里，外键帮不上忙。级联还是得写在应用层。

  2. 先删再解析。

    • 优点：同名文件不会短暂并存，实现也短。
    • 缺点：解析失败或 embedding 超时，正在用的旧库就被砸空。用户刷新进度条看到的是失败，对话里搜到的是空白。

  3. 只软删除，后台再回收。

    • 优点：删除可以回滚，页面也能做「回收站」。
    • 缺点：检索过滤要一直带着「未删除」条件，对象存储会堆一批垃圾。管理页现在很薄，没有回收站，硬删除按层清更直接。

收束

知识库是挂在智能体上的，不是全局文件夹。知识库存储的时候分成三部分：叶子进向量库，父块和索引进 PostgreSQL，原件进对象存储。切的时候先按页，再按段落和句子往下找边界，相邻块留约 13% 重叠，只把叶子送去 embedding。写的时候先算完再替换，删的时候按层清。
