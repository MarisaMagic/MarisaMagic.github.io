「Kura-AI」项目中多模态知识库是如何构建的

⭐ Kura AI 项目链接：https://github.com/MarisaMagic/Kura-AI

0 前言

这是 Kura-AI 专题的第 2 篇。第 1 篇写的是对话 Agent 的推理范式：主循环是 Function-Calling ReAct，知识库检索藏在 search_knowledge_base 的 LangGraph 子图里。这一篇往 retriever 的上游走一步，回答：多模态知识库是怎么建出来的？

先把结论放在前面。Kura-AI 的知识库不是把一份 PDF 压成一个向量，也不是把图文融合成一条「超级 embedding」。它是：

  • 文本：按页做 L1 / L2 / L3 层级分块，只有叶子 L3 进 Milvus；父块进 PostgreSQL，检索时按 Auto-merge 上卷成更完整的上下文；
  • 图片：从 PDF / Word 抽出独立 L4，和文本 分别 用 qwen3-vl-embedding 写入同一集合；图文关系用 related_text_ids 记在 PG，命中文本后再并入候选；
  • 本体：文档和图片进 MinIO；PG 只存元数据。按 kb_scope = u{uid}_a{aid} 隔离到每一个智能体；
  • 入库：后台线程 Job，先处理完全部向量，再替换落库。失败、超时、取消，旧文档原样保留。

选型的第一约束还是产品形态。Kura-AI 是用户可配置的智能体中心：每个智能体一份知识库，属主上传、对话按需检索、共享用户能问但不能改。构建时必须同时满足三件事——细粒度召回、图表跟得上对应段落、半途失败不能把正在用的库砸掉。

flowchart TD
  upload[上传 API 立即返回 task_id] --> job[kb_job 线程池]
  job --> parse[解析文本并抽图]
  parse --> split[L1 L2 L3 分块 + L4 图片块]
  split --> link[同页图文关联 related_text_ids]
  link --> embed[文本批嵌入 / 图片逐张嵌入]
  embed --> swap[替换临界区]
  swap --> milvus[Milvus: L3 文本 + L4 图片]
  swap --> pgParent[PG: L1 L2 父块]
  swap --> pgImg[PG: 图片元数据与关联]
  swap --> minio[MinIO: 原文档 + 图片]

1 功能设计：一份文档入库要完成什么

谈分块之前，先把「上传一份文档」当成产品合同写清楚。实现入口是 app/api/v1/user_agents/kb.py 的 kb_upload（只校验、入队）和 app/kb/kb_service.py 的 run_ingest_pipeline_sync（真正解析、嵌入、落库）。前端在 web/src/views/agents/knowledge-base/index.vue。

1.1 边界

  • 能做什么：属主给某个智能体上传 PDF、Word、Excel、TXT、Markdown（默认上限 50MB）；列表、按文件名删除、取消进行中的任务；同名再传等于替换，内容 SHA256 没变则跳过重建。
  • 不能做什么：共享（非属主）用户可以对话检索属主的库，但知识库 API 走 get_owned，不能上传或删除。没有独立的「重建索引」接口。不接受把一张独立图片当成知识库文档。Excel 和纯文本不抽图。没有 OCR——扫描件如果抽不出文字，文本通道几乎是空的。
  • 必须让位：解析或嵌入失败时，旧版文档必须仍可检索；不能先删后写，把正在对话的库写成空洞。
  • 什么算成功：叶子块能被以文 / 以图检索命中；父块能按层级合并；命中文本能拉到同页关联图；进度可看、任务可取消；删文档或删智能体时，Milvus、父块、图片对象、文档对象一起清掉。

这四条决定了后面所有设计。分块再漂亮，上传同步卡死 API、重传把旧库先砸了、共享用户改了属主的文档，都不算做成。

1.2 一份文档的生命周期：任务在 Redis，就绪才进 PG

系统里没有 pending / processing / ready / failed 这种文档状态机。处理中只存在于 Redis 任务快照，列表里出现的文档就是已就绪。

上传接口读完整文件、校验扩展名和魔数之后，立刻返回 task_id：

任务状态写在 kb_upload_job:{task_id}:meta：queued → running（阶段 parsing / chunking / embedding / writing）→ completed / failed / timeout / cancelled。前端每 500ms 轮询进度——这和对话 Job 的 Redis SSE 不是一套。对话要续传思考过程和正文；知识库上传只要最新百分比，一份快照够了。

mg_kb_documents 只在替换落库成功后才写入。处理期间旧版仍可查、仍可被 Agent 检索。失败则任务终态带 error，文档表不动。

隔离键是：

一个智能体一份命名空间。智能体 ORM 不存知识库外键；Milvus 过滤、OBS 路径、PG 行都靠这串 scope。对话侧固定用属主的 scope，所以发布出去的智能体，别人问到的仍是发布者那份库。

1.3 四级分块：叶子负责被找到，父块负责被读懂

MultimodalDocumentLoader 模块头把模型写死了：三组 RecursiveCharacterTextSplitter 对应 L1 / L2 / L3，图片作为独立 L4，和文本块通过位置关联。

默认 chunk_size=900、chunk_overlap=90 时，三层大约是 1800 / 900 / 450，重叠按倍递减。分隔符带了中英文句读，避免中文被按空格切碎。

层级 存哪 检索时干什么
L1 / L2 文本 PostgreSQL mg_kb_parent_chunks + Redis 缓存 不直接 ANN；Auto-merge 的上卷目标
L3 文本 Milvus：dense + 服务端 BM25 默认叶子层（LEAF_RETRIEVE_LEVEL=3）
L4 图片 Milvus dense + PG mg_kb_images + MinIO 原图 以文搜图、以图搜图；text 为空，没有 BM25

chunk_id 用展示文件名的 SHA256 前 16 位做指纹，避免路径里的特殊字符：

入库时按层级拆开，只有叶子进向量库：

类型分发也在 loader 里一次做完。PDF 用 PyPDFLoader 抽分页文本、PyMuPDF 抽内嵌图和 bbox；Word 用 Docx2txtLoader 加 python-docx 抽 inline 图；Excel 逐 sheet 转 Markdown 表格（隐藏表跳过）；TXT / MD 整篇当一页。不认识的扩展名直接抛错。

PDF 小于 100×100 的图当图标丢掉。Word 没有真实页码，用段落序号顶上，纵坐标按 para_idx * 100 估算。.doc / .xls 扩展名放行且魔数认 OLE，但 loader 吃的是 OOXML——老二进制格式实际上可能解析失败。

1.4 存储分层：向量、正文、像素各管各的

构建产物拆在四处，检索时再拼：

层 放什么
MinIO 原始文档 user_agent_docs/；抽出的图片 user_agent_images/user_{uid}/{aid}/{fingerprint}/
PostgreSQL 文档行（content_hash、叶子数）；L1/L2 全文；图片元数据与 related_text_ids
Redis 上传进度、同名替换锁、父块缓存、选档文件名列表
Milvus kura_ai_kb L3 / L4 的 dense；文本块另有服务端 BM25 稀疏向量

Milvus 里图片块的 text 故意留空，image_path 只是相对 IMAGES 前缀的 relpath。像素不进向量库，base64 也只在检索期 rerank 时现读对象存储——入库路径不生成 caption，KbImage.caption 字段预留着，当前不用。

2 实现思路：为什么是这套，而不是其它

2.1 主干：先处理后替换

run_ingest_pipeline_sync 的语义写在函数头里，比任何设计文档都直白：

顺序可以压成：

  1. 同展示名且 content_hash 相同 → 直接返回 unchanged，不解析不嵌入；
  2. 临时目录写源文件、抽图、三级分块、图文关联；
  3. MultimodalMilvusWriter.embed_documents 只生成向量，不写 Milvus；
  4. 向量齐了，才把图片和文档本体上传到对象存储，并把 chunk 里的 image_path 改成 relpath；
  5. 拿 Redis NX 锁，删旧、写父块、按预计算向量 write_documents、写 KbDocument。

写入拆成两段，就是为了第 5 步里不再调嵌入 API。临界区只有纯 I/O，数秒内结束。同名并发上传时锁把落库串行化，后完成者生效；图片文件名带内容哈希 8 位后缀，删旧图时用 exclude_image_rels 保护「新旧内容相同、key 撞车」的那几张。

为什么不先删后写？嵌入是分钟级的，PDF 里几十张图还是逐张 HTTP。先删的话，用户点一次重传，对话立刻检索空洞，失败还没得回滚。为什么不按块增量更新？一份文档的层级树、图文关联、BM25 统计是整份一起算的，块级 patch 省不了多少，正确性成本更高。当前粒度就是整文档替换。

2.2 为何图文分块，不用融合向量

MultimodalEmbeddingService 里其实实现了 get_multimodal_fusion_embeddings（enable_fusion=True）。全仓库没有调用方。生产路径是 writer 按 content_type 拆开：

图片写入 Milvus 时 text 为空、chunk_level=4：

融合一条向量看起来省事，但和后面的检索合同对不上。以图搜图需要独立的图片向量；命中一段说明文字再把旁边的图拉进来，需要 related_text_ids，不是一次融合能代替的；工具输出要把文本和带签名的 /api/v1/media/ Markdown 分开格式化；BM25 只吃 text 字段，融合块会把 BM25 赖以计分的 text 搅浑。同一模型、同一 dense_embedding 字段、分别 embed，查询文本和图片块才能直接做内积——这已经是跨模态，不必再做 CLIP 式双塔对齐。

2.3 为何三级文本切分，叶子进 Milvus、父块进 PG

细叶子召回准，短句子当最终上下文又碎。Milvus 只索引 L3，命中同一 parent_chunk_id 的子块达到阈值（默认 3）就用 PG 里的 L2 / L1 替换。检索永远是先叶子后合并，所以构建时必须把层级树写完整：parent_chunk_id、root_chunk_id、chunk_level、页内 position_start / position_end。

父块不进向量库，因为 Auto-merge 是按 id 取全文，不是再做一次 ANN。PostgreSQL 对这种主键点查更合适，还可以 Redis 缓存 kb_parent_chunk:{chunk_id}。反过来，把 L1 也建成向量，检索会被大段重复文本冲掉，过滤表达式还更难写。

L4 不参与 RecursiveCharacterTextSplitter。图片是文档内嵌资源，不是切出来的句子；它的 parent_chunk_id 在关联阶段指向某个 L3，而不是 L2。

2.4 图文如何关联：几何优先，顺序兜底

检索不靠「同一个 filename 就当配图」。构建时就要把 L3 和图片绑上。PDF 曾经把字符下标和页面纵坐标混在一起比，后来改成两套策略：能搜到 L3 的页面 bbox 时，优先把「在图片上方」最近的那块文绑给这张图；搜不到 bbox，再按阅读顺序和图片纵向顺序 zip。非 PDF 没有同一套坐标系，直接顺序配对，避免再把字符 offset 和 y 坐标比大小。

关联结果双向写：图片带着 related_text_ids，文本块带着 related_image_ids。真正持久化的是 PG 里 KbImage.related_text_ids（JSONB）。Milvus 不存这张关系表——向量库负责「像」，关系表负责「这张图属于哪段话」。

图片为什么不 OCR？VL embedding 直接吃像素，少一条错误传播的管线。代价很明确：扫描版 PDF 几乎没有有效 L3，只能靠图侧 dense 碰运气。caption 不在入库时生成，也是同一逻辑：构建阶段不把多一次视觉模型调用打进上传关键路径，描述留给对话侧的两阶段读图（第 1 篇写过）。

2.5 为什么选 Milvus

先前 RAG 专题里写过面试口径：原型 Chroma、中规模 Qdrant、千万到亿级分布式才上 Milvus。Kura-AI 没有按数据规模选。个人智能体中心的体量，pgvector 或 Qdrant 都扛得住。真正绑住实现的，是 同一 collection 里 dense + 服务端 BM25 + 标量过滤是不是一等公民。

产品侧要同时成立的三件事，都落在 app/kb/milvus_client.py：

文本叶子要语义检索和关键词检索两路并行。 hybrid_retrieve 用 HNSW / IP 搜 dense_embedding，同时把查询原文交给 bm25_sparse，RRFRanker(k=60) 融合。图片块 text=""，BM25 覆盖不到图，以图检索只走 dense_retrieve。中文精确单字召回注释里写了由 dense 向量兜底——Milvus 2.5 的 BM25 Function 还不接受 analyzer 参数，用内置 standard。

查询侧 BM25 直接传文本，不用客户端再算一遍稀疏向量：

写入时由库计算 BM25，客户端不维护词表。 旧集合用进程内 BM25 词表，migrate_bm25.py 注释写得很狠：跨重启索引漂移、IDF 失真。迁移脚本只拷 scalar 和 dense，不重调 embedding，专门把 BM25 改成服务端 Function。这是 Milvus 2.5 的能力，也解释了 compose 钉在 milvusdb/milvus:v2.5.14。

过滤和图文块挤在同一个集合。 检索表达式是 kb_scope、可选 filename in [...]、chunk_level == 3 || 4。会话记忆另开 kura_ai_chat_memory，不和知识库抢 schema。多模态不是两个库，是同一张表里 content_type 分流。

对照其它选项，用产品约束收口，不写成向量库百科：

  • pgvector：项目已经用 PostgreSQL 存 L1/L2 和图片元数据，向量却故意不进 PG。父块要的是按 id 取全文做 Auto-merge，不是 ANN；叶子要 hybrid + RRF + 服务端 BM25。pgvector 通常还得另接 tsvector 或 ParadeDB，过滤表达式和 hybrid_search 也没有这一套现成。把父块和叶子塞进同一张关系表，层级合并和 ANN 会互相污染。
  • Chroma：嵌入式、适合原型。扛不住「每智能体一个 scope、前置选档 filename、图文混排」这条布尔过滤链，也没有写入即计算的 BM25 Function。
  • Qdrant：中规模生产很强，稀疏向量也有。但当前路径绑的是 Milvus 2.5「Function 写时出稀疏、查询传原文」，以及已经 docker 化的 standalone（etcd + 专用 minio + milvus）。换成 Qdrant 要重写 schema、混合检索和迁移脚本，对当前体量收益不明显。
  • Elasticsearch：向量检索是后补能力。Kura-AI 要的是 ANN 原生，顺带 BM25，不是倒过来。

运维只需要一句：本地 compose 跑 standalone；云上可填 MILVUS_TOKEN 接 Zilliz。不把部署手册写进这篇。

2.6 为何后台线程 Job，而不是同步解析

抽图、批文本 embedding、逐图 HTTP，动辄几十秒到几分钟。同步放在 FastAPI 路由里会堵住事件循环，对话 Job 一起排队。kb_job.py 模块头把根治点写在第一段：专用 ThreadPoolExecutor（默认并行 8），worker 里跑同步 run_ingest_pipeline_sync，任务线程自建 MilvusManager，避免跨线程共用单例客户端。

进度按阶段映射到百分比：parsing 0–10，chunking 10–12，embedding 12–85，writing 85–100。嵌入占了大半条，和真实耗时对齐，避免解析刚结束进度条就跳到 90%、然后在 embedding 上假死。超出并行上限的任务保持 queued。单次嵌入 HTTP 超时默认 90 秒，避免 DashScope SDK 默认 300 秒把整单悬死；整单上限 900 秒。

2.7 构建产物必须撑住怎样的检索

检索细节是下一篇的事。构建时只要记住消费侧的几条硬约束，存错了后面全补不回来：

  • 只存纯文本：没有 L4，以文搜图、以图搜图、KB_RELATED_IMAGE_EXPANSION 全废；工具也给不出带 exp / sig 的图片 Markdown。
  • 不写 related_text_ids：命中说明文字之后，只能靠向量偶然撞上旁边的图。
  • 没有 parent_chunk_id 和 PG 父块：Auto-merge 无法 L3 → L2 → L1，召回上下文永远碎。
  • filename 必须是稳定的 file_key：前置选档和 Milvus filename in [...] 共用同一字符串，模型不能在工具参数里改范围（第 1 篇写过选档在 Agent 调用前做完）。
  • 图片二进制和向量分离：rerank 需要时才从对象存储读成 Data URI；构建期不把原图塞进 Milvus。

3 优化：性能、体验、可靠性

流水线能跑，还不等于能用。下面这些是已经落地的，不是规划。

3.1 性能与成本

文本批处理，图片串行但可取消。 EMBEDDING_BATCH_SIZE 默认 10，文本 embed 和 Milvus insert 共用。图片受 DashScope 限制必须一张一张来，但每张前走 tick_cb → KbUploadTaskGuard.checkpoint()，取消和超时不用干等到当前图的 HTTP 结束才发现。单次 HTTP 90 秒封顶。

同内容秒跳过。 展示名 + SHA256 命中现有 KbDocument，整条解析 / 嵌入 / 替换都不走，任务直接 unchanged。这是唯一的「增量」：没有块级 patch。

BM25 迁移不重调 embedding。 migrate_bm25 把旧集合的 dense 原样拷到新 schema，BM25 改由 Function 计算。换检索算法不该再付一次向量账单。

父块读路径有 Redis。 Auto-merge 按 id 取 L1/L2 是检索热路径，ParentChunkStore 写入时就种缓存。选档用的文件名列表也按 kb_scope 缓存一小时，文档变更时主动失效。

3.2 体验

知识库页要让人看出「现在卡在哪」，而不是一个转圈。前端是双层进度：HTTP 上传百分比，和后台 parsing → embedding → writing 阶段进度。多文件并行，每个文件独立 task_id、独立轮询；批次总进度取均值。进行中的任务写入 sessionStorage，刷新页面能接着问状态。

可取消不是装饰。取消标记写 Redis，worker 在批边界 checkpoint() 退出；嵌入阶段失败时旧文档仍在，用户不用面对「取消了但库已经空了」。超时文案带 900 秒提示。同内容重传会明确说「内容未变化」，避免以为卡住。

聊天里知识库图片必须走同源相对路径 /api/v1/media/...（带签名），不拼 PUBLIC_API_BASE 的绝对 URL，以免被前端 CSP img-src 拦掉。构建时把像素放进对象存储、检索时再签发，就是为了这条展示合同。

3.3 可靠性

  • 失败分阶段：解析 / 嵌入失败只清临时目录，不碰旧 Milvus / PG / OBS。临界区内失败是窄窗口——旧数据此刻已删——代码会尽力清掉新上传对象，并承认同名再传可自愈。
  • 图片单张 embed 失败用零向量继续，避免一张坏图打掉整份 PDF；文本 embed 条数对不上则整单中止，因为 BM25 和 dense 必须对齐叶子列表。
  • 几何关联失败退回顺序配对，打不开 PDF 也不阻断入库。
  • 协作式超时：整单 900 秒、单次 HTTP 90 秒，加上逐图检查点，避免 SDK 默认超时把线程池占满。
  • 权限：进度查询校验 meta.user_id，防止拿别人的 task_id 看任务；管理接口一律 get_owned。
  • 过滤表达式转义：milvus_escape 处理 scope 和 filename 里的引号，避免用户文件名打穿 expr。

4 对照与收束

把常见多模态知识库做法和 Kura-AI 实装置在同一张表里，会更清楚「我们选的是哪一层，改的是哪一层」：

维度 常见做法 Kura-AI 实装
文档表示 整篇或整页一个向量；或图文融合单一 embedding L1/L2/L3 文本树 + 独立 L4 图片；分别 embed
图片 OCR 进文本通道；或整页截图 抽内嵌图，VL embedding 吃像素；无 OCR、入库不生成 caption
图文关系 检索时按页猜测 构建期写 related_text_ids，命中文本再扩图
切分 单层 chunk 直接检索 叶子进 Milvus，父块进 PG，Auto-merge 上卷
向量库 pgvector 把所有东西塞进 PostgreSQL；或 Chroma 原型库 Milvus hybrid（HNSW + 服务端 BM25 + 标量过滤）；PG 只放父块和关系
原图 base64 进向量 payload MinIO + relpath；rerank 时才现读 Data URI
更新 先删后写，或同步解析 后台 Job + 先处理后替换；同 hash 跳过
隔离 全局一个库 kb_scope 一智能体一份；共享只读属主库

一句话收束：文本负责被问到，图片负责被看到；关联在入库时写死，检索时再拼回来。 Milvus 负责「像不像、词能不能对上」，PostgreSQL 负责「这段话的父块和旁边那张图」，对象存储负责像素。三者叠在一起，才是 Kura-AI 现在的多模态知识库。
