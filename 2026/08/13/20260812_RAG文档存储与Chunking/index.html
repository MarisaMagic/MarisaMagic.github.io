「RAG」RAG 中的文档是怎么存的？粒度是多大？详细说说文档切割（Chunking）策略？

0 前言

本文内容整理自公众号「小林面试笔记」的文章 4. RAG 中的文档是怎么存的？粒度是多大？详细说说文档切割（Chunking）策略？，用于记录与总结 RAG 相关的核心面试知识点。

「RAG 中的文档是怎么存的？粒度是多大？详细说说文档切割（Chunking）策略？」，可以这样作答：

文档不能整篇直接存进向量库，必须先切成语义完整的小块（chunk），逐块向量化后作为一条记录入库。原因是向量模型有输入长度限制，而且整篇压成一个向量会把细节"平均掉"，检索时无法精准定位。每条记录有三个核心部分：向量负责相似度检索、原文是检索命中后塞给 LLM 阅读的内容、metadata 负责过滤与溯源。

粒度没有银弹，一般以 500~1000 token 为起点，更关键的是按文档类型选策略：普通文本用固定大小 + 重叠保底；有段落、标题结构的文档按语义边界切；代码按函数切、表格整块保留；既要检索精度又要上下文完整时，用父子切割——小块检索、大块返回。

1 文档是怎么存的？

1.1 为什么不能整篇直接存？

先说结论：原始文档不能直接进向量库，必须先切成小块（chunk）再存。上一篇我们说 RAG 把知识"放进外部知识库"，那这个库里装的东西到底是什么形态？答案就是 chunk——文档存进向量库的最小知识单元。

为什么不能偷懒整篇存？两个硬原因：

  1. 向量模型有输入长度限制：Embedding 模型一般只能处理几百到几千 token，一篇几千字的文档根本塞不进去；
  2. 细节会被"平均掉"：就算模型支持超长输入，把整篇文章压缩成一个向量，所有细节都会被揉成一团——你想找"退款政策"，向量里却混着"配送时效"“积分规则”，最后检索到的只能是这篇笼统的文档，而不是精确的那段话。

向量模型并没有那么神通广大，它和人类阅读一样：信息太密集就抓不住重点。所以正确姿势是提前把文档切成可检索的小块，入库流程是这样的：

一篇 5000 字的文档，切成 500 字一个 chunk，就变成向量库里的 10 条记录；100 篇文档就是 1000 条记录。RAG 存储的本质，就是"一篇文档 → 多条 chunk 记录"的转换。

1.2 每条 chunk 记录里存了什么

向量库里每一条记录包含三个部分，缺一不可：

可以用一个直观的类比来记：向量是索引卡，原文是书页，metadata 是书签。

  • 向量：一串高维浮点数，决定这段内容在"语义坐标系"里的位置，用于快速找到相关 chunk；
  • 原文：纯文字，检索命中后原封不动塞进 prompt，这才是 LLM 真正读的内容；
  • metadata：来源文件名、页码、章节等附加信息，用于过滤（“只搜客服部门的文档”）和溯源（“这个答案来自哪个文件的第几页”）。

花一分钟想这个问题：为什么向量和原文要同时存？因为两者角色完全不同——向量是一串浮点数，LLM 看不懂，只有检索系统用它；原文是纯文字，没有向量就无法做相似度检索。向量负责"找到"，原文负责"阅读"，缺了谁都不行。

1.3 查询时的完整链路

理解了存储结构，查询时就顺理成章了：

用户问题 → 向量化 → 在向量库里找相似的 chunk → 取出 chunk 的原文 → 塞进 prompt → LLM 生成答案

注意这条链路里：向量只在"找"的阶段出场，喂给 LLM 的一直是原文。

2 切割粒度怎么定？

既然要切，切多大合适？粒度选择本质上是一场取舍，切得大则笼统、切得小则碎片：

  • chunk 太大：向量把太多语义压缩在一起，变得笼统，容易召回只和问题部分相关的内容，还可能超出 Embedding 模型的长度上限；
  • chunk 太小：单个 chunk 语义不完整、上下文丢失，LLM 拿到碎片也看不懂，而且检索噪音更多。

所以切割粒度没有银弹，500~1000 token 只是合理起点，更关键的是结合文档的内容结构选择策略——这就是下一节的内容。

3 文档切割策略有哪些？

3.1 策略一：固定大小切割（Fixed Size Chunking）

最简单粗暴的方式：不管语义，按固定字符数或 token 数硬切。优点是实现简单、chunk 大小可控；缺点是可能在句子中间截断，撕坏语义。

纯固定大小几乎不会单独用，通常会加上**重叠（overlap）**来缓解边界截断：前一个 chunk 的末尾和下一个 chunk 的开头保留一段重叠内容，确保跨边界的语义至少被一个 chunk 完整覆盖。就像扫描仪扫跨页内容时，特意把两页的边缘都扫两遍。

举个例子，chunk_size=500、overlap=100：后一个 chunk 的前 100 个字符和前一个 chunk 的后 100 个字符是相同的——就算边界恰好切在一句话中间，这句话也一定完整地出现在某个 chunk 里。

一句话总结：固定大小 + 重叠是最简单也是最保底的策略，适合纯文本、没有明显结构的文档。

3.2 策略二：语义边界切割（Semantic / Structure Based Chunking）

固定大小最大的毛病是可能切断语义，那为什么不顺着文本的天然断点来切？这就是语义边界切割：按段落、句子、标题层级等自然边界切分，绝不在语义中间下刀。

为什么语义边界更好？因为一个句子是语言表达意思的最小完整单位——在句子中间截断，就像切断一段话的呼吸，前半句后半句单独拿出来都看不懂；按段落切就更进一步，每个 chunk 都是围绕同一话题展开的完整段落，语义独立性最好。

实际操作时，常见的做法是维护一个分隔符优先级列表：先尝试按段落切，段落太大就按句子切，句子还超限就按标点切，逐级降级直到满足 chunk_size 限制。

对于有明确标题结构的 Markdown / HTML 文档，按标题层级切是更优选择：每个 chunk 对应文档中的一个完整章节，metadata 自动带上所属标题（比如"产品手册 > 退款政策 > 申请流程"），既语义独立，又方便过滤和溯源。

3.3 策略三：特殊内容专项处理

通用切割策略碰到代码和表格就会露馅，这两类内容需要单独开小灶：

  • 代码按函数 / 类切：一个函数是最小的语义完整单元，从函数中间截断就失去了逻辑意义——试想把函数参数定义和返回值拆到两个 chunk，单独看哪一个都不知道这段代码在干嘛。实践中可以用语法解析工具（比如 Python 的 AST 模块）识别函数和类的边界；
  • 表格整块保留，转成 Markdown 存储：表格的每一行都依赖表头才有意义，"2 小时"单独看不知道是什么，配上列名"响应时间：2 小时"才清晰。整张表作为一个完整 chunk，才能保留列语义和行间对比关系。

3.4 策略四：父子切割（Parent-Child Chunking）

前面几种策略各有局限：固定大小可能切断语义，语义边界切割质量好但粒度不好控。有没有办法同时兼顾检索精度和上下文完整？父子切割就是工程里效果最显著的答案之一，核心思路一句话：

检索时用放大镜（小块，精准定位），返回时用全景图（大块，上下文完整）。

存储时同一段内容存两份：一份是细粒度的小 chunk（比如 200 token），语义聚焦、检索精度高，专门用于向量检索；另一份是包含小 chunk 前后上下文的大 chunk（比如 1000 token），通过 ID 与小 chunk 关联。查询时先用小 chunk 定位精准命中点，再顺着关联 ID 取出大 chunk，把完整上下文交给 LLM 阅读。

可以类比图书馆找书：你用目录卡（小 chunk）定位到某章某节，但拿出来读的是完整的那一章（大 chunk），而不是目录卡上的那句简介。

代价也很直白：存储量翻倍、索引构建更复杂。但在召回质量要求高的场景下，这个成本是值得的。

3.5 补充：Late Chunking——先编码，后切分

最后聊一个 2024 年出现的新思路：Late Chunking（Jina AI 提出）。它换个角度解决"切割丢失上下文"的问题。

传统做法是先切块再编码：每个 chunk 独立过一遍 Embedding 模型，跨块的上下文（代词指代、前后背景）在编码阶段就丢了。Late Chunking 反过来，先编码后切分：

  1. 把整篇文档丢给支持长上下文的 Embedding 模型，做一次完整的前向传播，输出文档里每个 token 的向量——由于注意力机制，这些 token 向量彼此感知过全文语境；
  2. 再按 chunk 边界，把落在同一个 chunk 里的 token 向量做 mean pooling（均值池化），得到这个 chunk 的最终向量。

关键在于"延迟"二字：先编码后切分，每个 chunk 的向量天然融入了全文语境，跨块的代词、背景、对比关系都能保留。代价是对模型要求高：需要支持足够长的上下文（比如 jina-embeddings-v2 支持 8192 token），且要保留 token 级中间结果，开销比传统方式大。

3.6 策略选型总览

把几种策略梳理成一张表，选型时可以对照来看：

策略 适用文档 优点 缺点
固定大小 + 重叠 纯文本、无明显结构 实现简单、chunk 大小可控 可能在语义中间截断
语义边界切割 段落分明的文章 语义完整、召回质量好 实现稍复杂，chunk 大小不均
标题层级切割 Markdown / HTML 文档 天然语义独立，带结构 metadata 依赖文档有清晰标题结构
代码按函数切 代码文件 保留代码逻辑完整性 需要 AST 解析，限定语言
父子切割 各类文档（追求高质量） 检索精准 + 上下文完整两全 存储量翻倍，索引构建复杂
Late Chunking 各类文档 chunk 向量保留全文上下文 需要模型支持长输入

4 面试总结

Chunking 这道题，考的是你对 RAG 存储层的理解深度。答题按三步走：

  1. 先说为什么不能整篇存：向量模型有输入长度限制；整篇压成一个向量，细节会被平均掉，检索无法精准定位；
  2. 再说怎么切：固定大小 + 重叠是最基础的兜底；语义边界切割更智能；代码和表格要特殊处理；父子切割能兼顾检索精度与上下文完整；
  3. 最后强调粒度无银弹：500~1000 token 只是起点，关键是按文档类型选策略。

如果被追问"你实际用的什么策略"，标准回答是：固定大小加重叠做兜底，结构化文档用语义边界切割，高质量要求场景用父子切割——这个回答既有层次，又显得有工程经验。
