「RAG」如何缓解 RAG 系统中大模型的幻觉？

0 前言

本文内容整理自公众号「小林面试笔记」的文章 17. 如何规避 RAG 系统中大模型的幻觉？，用于记录与总结 RAG 相关的核心面试知识点。

「如何规避 RAG 系统中大模型的幻觉？」，可以这样作答：

先分清 RAG 幻觉的两类来源：检索层没找到——相关 chunk 没被召回，prompt 里没有可用上下文，LLM 靠预训练知识"猜"一个听起来合理的答案（且说得无比自信）；生成层超发挥——内容召回了，但 LLM 没严格照着资料说，在原文基础上加了推断、脑补甚至拼接。

应对策略从成本低到机制严格依次有四层：一是 Prompt 强约束，明确"只能照资料回答、资料里没有就说不知道"，压制生成层幻觉；二是检索质量门控，用 Rerank 分数做门槛，低于阈值直接拒答"知识库无相关信息"，不让 LLM 在低质量上下文上硬撑；三是生成后引用核查，让 LLM 当"编辑"逐条核查答案里的每个声明在 chunk 里有没有依据；四是结构化输出强制溯源，强制输出 JSON，每条结论附 source_ids 来源编号，既能逼 LLM 自查，也方便程序化验证。

成本最低、收效最快的是 Prompt 强约束 + 检索质量门控，生产系统上线前这两个必须做。核心认知一句话：治幻觉，先治检索——检索质量才是幻觉最大的来源。

1 幻觉是什么，为什么 RAG 里会有幻觉？

先厘清"幻觉"这个词。LLM 的幻觉，就是模型一本正经地说了一件压根不存在的事。它不是在撒谎——它只是在「预测下一个词」，当它没有可靠依据时，就会拼凑出一个"听起来合理"的答案（这个机制我们在第二篇提过：幻觉是知识缺失的副产品）。

你可能会想：RAG 不是已经把知识库内容塞进 prompt 了吗，LLM 为什么还会编？这是最常见的误区——塞进去，不等于 LLM 会"老老实实照着说"。LLM 有自己的预训练知识储备，当 prompt 里的资料和它"学到的"不一致，或者根本没召回到相关内容，它就可能绕开资料、自己发挥。所以 RAG 里的幻觉有两个完全不同的来源，必须分开理解：

第一种：检索层没找到，LLM 靠"猜"回答。 这是最根本的问题——检索失败，prompt 里是空的或不相关内容，LLM 不会说"我不知道"，而是用训练时见过的知识编一个像答案的东西，说得还很自信。举个具体例子：知识库里记录的退款政策是「7 天无理由退款」，某次检索没召回到这个 chunk，LLM 用"自己的知识"给出「30 天退款」的答案——用户照做，退款失败，这就是检索层幻觉造成的实际损失。

第二种：检索到了，但 LLM 没有严格照着说。 这种幻觉更隐蔽、也更常见：相关 chunk 确实被召回塞进 prompt 了，但 LLM 在生成时"超发挥"——把资料当基础，加上自己的推断、补充原文没有的细节、甚至把两段不相关的信息拼在一起凑出"更完整"的答案。读者很难分辨哪句话来自文档、哪句是 LLM 加的。

两类幻觉的根源不同，解法也完全不同。下面四个方案，是从"成本最低"到"机制最严格"依次递进的思路：

2 方案一：Prompt 强约束——只准照着资料说

成本最低、最容易上手，效果也立竿见影。很多人搭 RAG 时只是把 chunk 塞进 prompt 然后问"请回答这个问题"，没约束 LLM 的行为——LLM 就默认"资料只是参考，我可以结合自己的知识一起回答"，幻觉就这样产生了。

修复方法是在 system prompt 里立规矩：

回答规则：

  1. 只能使用【参考资料】中的信息来回答，不得引入资料之外的知识
  2. 如果参考资料中没有足够信息，必须明确回答：「根据现有资料，无法回答该问题」
  3. 回答时标注信息来源（来自哪条参考资料）
  4. 不要推断、不要猜测、不要补充资料中没有明确说明的内容

每条规则都各有道理：

  • 第一条让 LLM"知道自己的边界"——你只是个传话人，不是百科全书，只能照资料说话；
  • 第二条给了 LLM 一个"合法的逃生出口"——当资料里没有答案时，说"不知道"比编一个合理答案好得多，允许它优雅地认怂；
  • 第三条让 LLM 回答时主动对照原文，相当于加了一个自检动作。

这个方案能压制「生成层幻觉」，但对「检索层幻觉」帮助有限——如果 prompt 里根本没有相关内容，再强的约束也顶不住 LLM 瞎编。所以要靠下一个方案补上。

3 方案二：检索质量门控——检索质量差就拒答

方案一管不住"检索失败"的情况：prompt 里全是无关内容时，与其让 LLM 硬撑一个"可能是错的答案"，不如直接告诉用户"知识库里没有这个信息"——前者让用户误以为答案是对的，后者虽然看起来不那么智能，但至少不给错误信息。答错比不答更危险。

怎么判断检索质量够不够好？用 Rerank 模型打分（Rerank 的原理我们在第 10 篇讲过）：

  1. 检索召回 Top-K 个候选 chunk；
  2. Rerank 给每个候选打 0~1 的相关度分数；
  3. 看最高分：低于阈值 → 直接拒答（“知识库无相关信息，建议联系人工”），不让 LLM 强行回答；达标 → 把合格 chunk 筛出来喂给 LLM。

阈值没有通用数字，得按业务数据调：拿一批"已知答案在知识库里"和"已知答案不在知识库里"的测试集跑一遍，看两种情况下 Rerank 分数的分布，找能把两类分开的切点。经验值一般在 0.3~0.6 之间：对精度要求高（金融、医疗）偏高，对召回率宽松（闲聊型问答）偏低，先从中间值开始，根据线上误判样例上下微调。

把这个思路和 CRAG（第 15 篇讲过）对照看：CRAG 是评估后路由到不同来源，这里是评估后决定"答还是拒答"——本质都是给检索质量加一道决策门。

方案一 + 方案二正好互补：方案二负责"检索质量差时不让 LLM 胡说"，方案一负责"检索质量还行但 LLM 容易超发挥时把它框住"。两个一起做，两类幻觉同时被压制，这也是 RAG 上线前成本最低的基础配置。

4 方案三：生成后引用核查——事后审稿

前两个方案都在"生成之前"做防控，万一还是漏了呢？方案三在生成之后做校验：LLM 生成完答案，再发起第二次 LLM 调用，把原始答案和 chunk 一起送回去，让它充当"编辑"角色，逐条核查每个关键声明在 chunk 里有没有依据——没有依据的内容标注"无法核实"或直接删掉。

这个方案和方案一的对比很形象：方案一是事前约束作者的行为，方案三是事后请编辑审稿，两道工序补上了"生成后"的空档。

代价是明摆着的：多一次 LLM 调用，响应延迟增加、成本翻倍。所以它一般只用在容错率极低的场景——医疗问诊、法律咨询，答错了代价很大。普通的企业知识库问答，方案一 + 方案二通常已经够用。

5 方案四：结构化输出强制溯源——每条结论带来源编号

方案三在内容层面做校验，方案四则在格式层面做约束，和方案一的 Prompt 约束配合效果更好：强制 LLM 输出结构化 JSON，每条结论都必须附上来自哪条参考资料的编号。

为什么有效？两个原因：

一是构建 JSON 的过程本身就是自查——LLM 必须主动想"这条结论我从哪条资料里找到的"，就好比让学生写论文必须标注参考文献，他自然就不敢随便编了；

二是系统可以做程序化验证——拿到 JSON 后，如果某个 source_ids 里的编号对应的 chunk 和 claim 明显不相关，就可以自动过滤掉这条结论。

6 四个方案怎么组合？

从易到难、按场景递进：

  • 普通的企业知识库、客服问答：方案一 + 方案二，成本极低、幻觉问题解决大半；
  • 可信度要求高（金融分析、法律文档）：再加方案四，每条答案带来源编号，用户可以回原文核实；
  • 容错率极低（医疗问诊、合规审核，答错代价大）：四个方案全上，用延迟和成本换最高级别的准确性。

说到底，规避幻觉没有一劳永逸的银弹，但有一条最重要的认知必须记住：

检索质量是幻觉的最大来源。 检索到了正确的内容，Prompt 再约束一下，幻觉已经少了一大半；检索这一步就烂的话，生成层再多的约束也填不了这个坑——治幻觉，先治检索。

7 面试总结

这道题考察的其实是两个认知层面的东西，先纠正一个很多人带进面试的错误：

  1. "检索做好就不会幻觉"是错的——它只看到了检索层失败，忽略了"检索到了但 LLM 超发挥"的生成层幻觉，两类根源不同、解法不同；
  2. "加一句’请根据资料回答’就够了"也是错的——那是一整套系统防控策略里的一个环节而已。

完整答题框架：先讲两类幻觉来源（检索层靠猜 / 生成层超发挥），再按四个方案从低到高讲，最后给组合建议（普通场景 1+2 基础配置，高可信场景加 4，低容错场景全上）。收尾抛核心认知：治幻觉，先治检索。

如果被追问"拒答阈值怎么定"，标准回答：没有通用值，用已知答案在库/不在库的测试集看 Rerank 分数分布找切点，经验值 0.3~0.6，按业务精度要求调整；如果被追问"为什么强约束 JSON 输出能减少幻觉"，答案是双保险：构建源引用的过程逼 LLM 自查，系统拿到结构化的 source_ids 后还能做程序化过滤。
