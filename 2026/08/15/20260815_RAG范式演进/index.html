「RAG」了解哪些更复杂的 RAG 范式？

0 前言

本文内容整理自公众号「小林面试笔记」的文章 15. 了解哪些更复杂的 RAG 范式？，用于记录与总结 RAG 相关的核心面试知识点。

「了解哪些更复杂的 RAG 范式？」，可以这样作答：

RAG 大致经历三代演进：Naive RAG 是最基础的"检索 + 生成"，两天能跑通 Demo 但没有任何优化；Advanced RAG 在检索前加 Query 改写与扩展、检索后加 Rerank 精排和内容压缩，是目前生产环境的主流形态；Modular RAG 则把每个环节拆成可独立替换的模块，像乐高一样按需组合（LlamaIndex Workflow、LangGraph 都是这个思路）。

在这之上还有四个值得关注的高级范式，分别针对朴素 RAG 的特定痛点：Self-RAG 解决"不是所有问题都需要检索"——让 LLM 自主决定要不要检索、评估检索质量（前提是模型需要专门微调）；CRAG 解决"检索质量差怎么办"——加质量评估和三级路由，质量差时自动降级到网络搜索兜底；GraphRAG（微软 2024）解决"全局理解"——用 LLM 抽取实体关系建知识图谱，社区发现 + 层次摘要，支持跨文档的全局查询；Agentic RAG 解决"复杂问题需要多轮动态检索"——把 RAG 嵌入 Agent 循环，检索几次、搜什么由 LLM 运行时自己决定。

回答时不要只罗列名字，要讲清楚每种范式解决了什么痛点、核心机制是什么、适合什么场景。

1 什么是 RAG 范式？

「范式」听起来很学术，其实就是一套固定的处理流程和设计思路。RAG 范式，就是指从「用户提问」到「生成答案」这条链路上，各个环节的组织方式和工作逻辑。

不同的 RAG 范式，本质上都在回答同一个问题：在「检索」和「生成」之间，系统应该怎么协调、怎么决策、怎么处理中间的各种异常情况？

最朴素的 RAG 是这样的：用户提问 → 向量检索 → 拼 prompt → LLM 生成答案。这套流程一两天就能跑起来，大多数教程演示的都是这个形态——但一旦进入真实业务场景，问题就来了。

2 为什么需要不同的 RAG 范式？

朴素 RAG 的问题，随着使用场景变得复杂会越来越明显：

第一个问题是检索质量参差不齐。 有些问题一次检索就能命中，有些问题向量检索完全召不到相关内容，但系统不区分，一律把检索结果喂给 LLM——然后呢？LLM 就会在低质量上下文上胡说八道，用户完全不知道答案有没有依据。

第二个问题是所有问题都走同一套流程，太死板。 有些问题根本不需要检索（「你好」「今天天气怎么样」强行去知识库找毫无意义），有些复杂问题需要多轮检索才能拼出完整答案，而朴素 RAG 一律只检索一次——该省的地方没省，该深挖的地方浅尝辄止，既浪费又不准。

第三个问题是知识库覆盖有盲区。 找到相关内容时，朴素 RAG 要么让 LLM 编造答案，要么返回风马牛不相及的回答——用户拿到的是自信满满的错误答案，体验极差。

你可能会想：这些问题用 Advanced RAG 的手段（Query 改写、Rerank、混合检索，我们在第 10、12 篇讲过）不就能缓解吗？确实能，但它们有一个共同的隐含假设：流程是固定的，只是每个环节做得更好。真正复杂的场景需要的是"流程本身能根据情况调整"——什么时候该检索、检索结果不行怎么办、需不需要再检索一次，这些决策要系统自己做。这就是高级范式要解决的问题。

3 三代 RAG 的演进

3.1 Naive RAG：能跑，但满身窟窿

最早的形态，逻辑直白：用户提问 → 向量检索 → 拼 prompt → LLM 生成。像搭积木的第一步，把环节拼在一起就能跑，两天上线一个 Demo。但它什么都没优化：检索召回什么就送什么，提问写得差就找得差，找到的内容有没有用也不管，一股脑塞给 LLM——幻觉和偏差就是这么来的。

3.2 Advanced RAG：在固定流程上打补丁

意识到问题后，Advanced RAG 出现了：在「检索前」和「检索后」各加一道工序。检索前加 Query 改写和扩展，把口语化提问打磨成更容易命中知识库的形式；检索后加 Rerank 精排和内容压缩，筛出最相关的几条、滤掉噪音。不用改框架，只需在原有流程上插入几个步骤，工程改动小、效果提升明显——目前大多数生产系统用的都是这个形态。

3.3 Modular RAG：把流程拆成乐高

Advanced RAG 有一个隐含假设——流程固定（检索前优化 → 检索 → 检索后优化 → 生成），不管用户问什么都走这套。Modular RAG 突破了这一点：把 RAG 的各个环节拆成可以独立替换的模块，像乐高一样按需组合——检索模块可以选向量检索、BM25 或图检索；改写模块可以选 HyDE、Step-back 或多 Query 扩展（第 12 篇讲过）；生成模块可以是普通输出，也可以是带引用的结构化输出。不同业务场景挑不同模块组合，灵活性大幅提升。LlamaIndex 的 Workflow 和 LangGraph 都是这个设计思路的实现。

理解了三代演进，再看后面的高级范式就有了参照系——它们都是在 Modular RAG「灵活组合」的思路之上，针对特定痛点做了更深度的设计。

4 高级范式

4.1 Self-RAG：LLM 自己决定要不要检索

朴素的第二个痛点（流程死板）催生了 Self-RAG。普通 RAG 不管用户问什么都检索，但有些问题根本不需要检索（比如「1+1 等于几」），有些检索结果根本不相关。Self-RAG 训练了一个特殊的 LLM，让它自主决定要不要检索，并通过四类特殊的 reflection token 做全程质检：

  1. Retrieval token：当前问题需不需要检索？
  2. Relevance token：检索回来的内容和问题相不相关？
  3. Support token：生成的答案有没有幻觉？
  4. Utility token：最终答案质量够不够好？

它的执行流程分五步：

  1. 判断是否需要检索：常识性问题或不需要外部信息时，直接生成答案；
  2. 检索并逐条评估相关性：对每个召回的 chunk 独立判断"和问题相关吗"，不相关的直接跳过；
  3. 基于相关 chunk 生成候选答案：每个相关 chunk 各自生成一个候选答案；
  4. 评估答案质量：给每个候选答案打两个分——有没有文档支撑（防幻觉）、对用户有没有用；
  5. 选出最优答案返回：综合两个分数，选出最好的那个。

这里有一个容易被忽略的前提：那四类 reflection token 不是现成 LLM 自带的——需要在专门构造的数据集上对基础 LLM 做监督微调，把 token 作为新词表的一部分训练进去。也就是说，Self-RAG 不能拿一个普通 LLM 直接"套用"，要么用论文开源的微调版本（基于 Llama2-7B/13B），要么自己造数据微调。这是它和后面几个范式很不一样的地方。

4.2 CRAG（Corrective RAG）：检索质量差时自动纠错

Self-RAG 解决"要不要检索"，那检索了但结果质量很差怎么办？知识库覆盖盲区（第三个痛点）就会导致这种情况，CRAG 专门解决这个问题——在检索完之后加一个质量评估环节：

  1. 本地检索：先从知识库召回 Top-K 个 chunk；
  2. 质量评估：用轻量级的检索评估器（专门训练的分类模型，或用 Rerank 模型分数近似）判断检索结果和问题的相关程度；
  3. 三级路由决策：评估为「相关」，直接用本地结果生成；评估为「不相关」，说明知识库没覆盖，丢弃本地结果、降级走网络搜索；评估为「模糊」，把本地结果和网络搜索结果合并使用。阈值需按业务场景调，没有固定数值；
  4. 生成答案：基于最终上下文生成回答。

核心价值是「兜底」：知识库覆盖不到的问题不会直接乱答，而是自动去网上找。很多人以为 RAG 只能用本地知识库回答，CRAG 打破了这一点——把知识库当主力，把网络搜索当备胎。

4.3 GraphRAG：用知识图谱增强全局理解

Self-RAG 和 CRAG 解决的都在「检索策略」层面，但还有一种瓶颈是检索方式本身的局限。普通向量检索只能召回"和问题直接相关的文档片段"——而向量检索本质上是一对一匹配，用 query 向量对比 chunk 向量，擅长局部匹配，却无法理解知识库的宏观结构和跨文档关联。对于「这批文档的核心主题是什么」「A 公司和 B 公司之间有什么关联」这类全局理解问题，单纯向量检索只能找到局部信息，拼不出全貌。

GraphRAG 是微软 2024 年 7 月发表的方案，把知识图谱、社区发现、层次摘要这几样现成工具系统化地组合起来解决这个问题。

  • 预处理阶段：先用 LLM 从文档里抽取实体和关系，建成知识图谱；再用 Leiden 社区发现算法对实体聚类，把紧密关联的实体分成一个个「社区」；最后对每个社区生成一份 LLM 摘要，形成从细粒度到粗粒度的多层层次结构；
  • 查询阶段：局部问题（「A 公司的 CEO 是谁」）直接在图中做实体查找和关系遍历；全局问题（「这些文档的主要主题有哪些」）用 Map-Reduce 方式——先让 LLM 分别阅读各社区摘要提取信息，再汇总生成最终答案。

「社区摘要 + Map-Reduce」正是 GraphRAG 区别于普通知识图谱方案的核心创新：它把全局信息提前"蒸馏"好了，查询时不需要遍历所有文档就能回答全局性问题。适合实体关系强、需要全局视角的场景（企业关系分析、药物-疾病-症状关联、大规模文档主题归纳），代价是构建图谱和摘要需要大量 LLM 调用，预处理成本较高。

4.4 Agentic RAG：把 RAG 做成 Agent

前面几种范式流程都是预先定义好的，最多按条件做分支。但有些问题复杂到连"需要检索几次、每次检索什么"都无法预先定义——比如「帮我分析 A 公司最近三年的财报，找出营收增速放缓的根本原因」，一次检索完全不够，需要多次、有针对性地检索不同维度。这就引出了 Agentic RAG：

  1. 接收问题，进入循环：LLM 拿到用户问题，开始 Agent 决策循环；
  2. LLM 决定下一步动作：根据当前上下文判断——信息够了吗？不够的话下一步搜什么关键词？
  3. 执行检索，累积上下文：按 LLM 指定的关键词检索，把新召回的 chunk 追加进已有上下文；
  4. 重复判断，直到信息充分：每轮重新评估"现在能回答了吗"，不够就继续检索；
  5. 生成最终答案：信息充分后退出循环，基于所有累积上下文作答——为防止死循环，还要设置最大迭代次数兜底。

和前面几种范式相比，Agentic RAG 最大的区别是**「流程不是写死的，而是 LLM 在运行时自己决定」**。一句话总结四个范式的关系：

Self-RAG 是给 RAG 加了一个「要不要检索」的开关，CRAG 是加了一个「检索不好怎么办」的兜底，GraphRAG 是加了一副「全局视角」的眼镜，而 Agentic RAG 是把整个检索流程变成了一个可以不断循环、不断调整的智能体。

把几个范式的特点对比一下，选型时有个参考：

范式 核心创新 适合场景 工程复杂度
Advanced RAG Query 改写 + Rerank 大多数生产场景 低
Self-RAG LLM 自主决策检索 问题类型多样、部分不需要检索 高（需特殊训练模型）
CRAG 检索质量差时降级网络搜索 知识库覆盖不全的场景 中
GraphRAG 社区发现 + 层次摘要，支持全局查询 实体关系复杂、需要全局理解的场景 高（图构建 + 摘要成本大）
Agentic RAG 多轮动态检索 复杂多步骤问题 中（Agent 框架）

5 面试总结

回答这道题，最大的扣分点是只背名字——"Self-RAG、CRAG、Agentic RAG 我都听说过"等于没说。正确的答题框架是痛点 → 机制 → 场景三层：

  1. 先给演进的脉络：Naive → Advanced（生产主流）→ Modular（乐高式组合），说明你不是背名字，而是理解这条演进线的逻辑；
  2. 再讲四个高级范式各解决什么痛点：Self-RAG 解决「不是所有问题都需要检索」、CRAG 解决「检索质量差怎么办」、GraphRAG 解决「全局理解和跨文档关联」、Agentic RAG 解决「复杂问题需要多轮动态检索」；
  3. 最后落场景：每种范式的适用场景和代价（Self-RAG 要微调、GraphRAG 预处理成本高、CRAG 依赖网络搜索能力、Agentic RAG 靠 Agent 框架）。

如果被追问"Self-RAG 和 Agentic RAG 有什么区别"，标准回答：Self-RAG 是在固定流程上加"要不要检索"的决策开关，流程本身不变；Agentic RAG 是流程由 LLM 运行时动态决定，检索多轮、每轮搜什么都不写死；如果被追问"Self-RAG 为什么不能直接套用现成模型"，答案是：reflection token 需要专门构造数据集监督微调、作为新词表训练进去，普通 LLM 不具备这套能力。
