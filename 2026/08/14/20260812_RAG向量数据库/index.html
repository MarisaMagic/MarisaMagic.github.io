「RAG」什么是向量数据库？有没有做过向量数据库的对比选型？

0 前言

本文内容整理自公众号「小林面试笔记」的文章 8. 什么是向量数据库？有没有做过向量数据库的对比选型？，用于记录与总结 RAG 相关的核心面试知识点。

「什么是向量数据库？有没有做过向量数据库的对比选型？」，可以这样作答：

向量数据库是专门用来存储和检索高维向量的数据库，核心能力是近似最近邻搜索（ANN）——在百万甚至亿级的向量里毫秒级找出最相似的 Top-K 个。它和"普通数据库加个向量字段"有本质区别：MySQL 擅长精确匹配（WHERE id = 123），向量数据库擅长语义相似，两者解决的是完全不同的问题。普通关系型数据库的 B-tree 索引只能处理一维有序数据，对 1024 维向量的相似度检索基本失效，暴力遍历百万条又不可接受，所以才需要专门设计。

索引算法主要讲两个：HNSW（多层图结构逐层导航，召回率高、查询快、吃内存，Qdrant/Milvus/Chroma 默认使用）和 IVF（聚类分桶、只搜相关桶，省内存、适合超大规模，需调参）。选型按三个维度——数据规模、部署方式、是否需要混合检索：原型验证用 Chroma，中到大规模生产用 Qdrant，千万到亿级分布式选 Milvus，不想运维用 Pinecone（注意数据出境合规），已有 PostgreSQL 就用 pgvector 插件。

1 什么是向量数据库？

向量数据库，顾名思义，就是专门用来存储和检索「向量」的数据库。

这里的向量，指的是嵌入模型（Embedding Model）把文本、图片、音频等内容转换出的一串浮点数——一句话可能被转换成像 [0.12, -0.87, 0.34, ...] 这样的 768 维或 1024 维数组。每一个向量都代表了这段内容的语义含义：语义越相近的内容，它们的向量在高维空间里的距离就越近。

向量数据库支持的核心操作叫近似最近邻搜索（ANN，Approximate Nearest Neighbor）：给你一个查询向量，在库里找出和它最相似的 K 个向量，返回对应的原始内容。这正是 RAG 里「检索」那一步的底层支撑——用户提问 → 问题向量化 → 去向量库里找最相关的文档片段 → 喂给大模型生成回答。我们在第一篇讲离线流程时提到的"向量数据库（Chroma、Milvus、Qdrant）"，干的就是这件事。

这里有个高频误解必须澄清：向量数据库 ≠ MySQL 加个向量字段。用一句话概括两者的本质区别：

MySQL 擅长精确匹配（WHERE id = 123），向量数据库擅长语义相似（“找和这个意思最接近的内容”），两者解决的是完全不同的问题，不是互相替代的关系。

2 为什么需要专门的向量数据库？

理解了它是干什么的，自然会问：为什么不直接在 MySQL 或者 ES 里存向量，非要引入一个新数据库？ 两个理由。

第一，普通数据库的索引对高维向量失效。关系型数据库（MySQL、PostgreSQL）依靠 B-tree 索引做结构化数据查询，WHERE id = 123 这种精确匹配效率极高。但向量检索完全不是"找等于"，而是"找最相近"——没有精确匹配，只有相似度排序。而 B-tree 只能处理一维的有序索引：你不可能对一个 1024 维的向量建一棵 B-tree，然后说"帮我找和它最近的"，因为「近」本身是高维空间的综合判断，不是某一个维度上的排序。

第二，暴力遍历代价不可接受。朴素做法是把查询向量和库里每一条向量都算一遍相似度——百万条数据就要算一百万次，延迟完全不可接受。至于 Elasticsearch，它的向量检索能力是后来加的"补丁"，不是原生设计，数据量一大性能就扛不住。

所以向量数据库的价值就在于：用专门的索引结构把相似度搜索加速，在可接受的精度损失下把延迟压到毫秒级。那它是怎么做到的？秘密全在索引算法上。

3 核心索引算法：HNSW 与 IVF

目前主流的两大索引算法，面试至少要把这两个讲清楚。

3.1 HNSW：多层图导航

HNSW（Hierarchical Navigable Small World） 是目前召回率最高的 ANN 算法之一。它构建一个多层图结构：查询时从最上层的稀疏图开始导航，逐层收窄范围，最终在底层找到最近邻。

打个比方：在地图上找最近的餐厅，你不会把全国所有餐厅都遍历一遍，而是先在全国层面确定大致方向，再锁定省、市、区，一层层缩小范围——HNSW 就是把这个"逐层逼近"的过程建成了结构。

  • 优点：召回率高（相同延迟下通常能到 95%+）、查询速度快；
  • 缺点：建索引时内存消耗大，不适合内存极度受限的场景；
  • 市场地位：Qdrant、Milvus、Chroma 默认都用 HNSW。

3.2 IVF：聚类分桶

IVF（Inverted File Index） 是另一种思路：先对向量做聚类，把相似的向量分进同一个「桶」里；查询时只搜最相关的几个桶，而不是全量遍历。

类比图书馆的分类体系：找一本编程书，不需要把整个图书馆翻一遍——先找到「计算机科学」那个区域，再在里面找，范围瞬间缩小。

  • 优点：内存占用小，适合超大规模；
  • 缺点：精度比 HNSW 略低，需要调参（聚类数量 nlist、搜索桶数量 nprobe）；
  • 市场地位：Milvus 在超大规模场景下会用 IVF 系列索引。

3.3 为什么两个都要？

你可能会问：HNSW 精度高、速度快，为什么还需要 IVF？原因很简单——HNSW 的内存消耗和向量数量成正比，到了亿级规模内存可能扛不住；IVF 用聚类换内存，牺牲一点精度换来处理超大规模的能力。一个吃内存换精度，一个省内存换规模，各有各的适用场景，面试时把这个取舍讲清楚就很有深度。

4 向量数据库的核心能力

索引算法是底层核心，但生产级向量数据库光有 ANN 搜索还不够，还要具备几个关键工程能力：

4.1 Metadata 过滤（混合检索）

实际业务里，知识库往往横跨多个部门、多个产品线，用户只想搜"技术部的文档"或"2024 年更新的内容"。向量数据库支持给每个向量挂上 metadata 字段，检索时先加过滤条件，只在符合条件的子集里做 ANN 搜索。

你可能会想：为什么不先 ANN 搜完再过滤？因为那样搜出来的 Top-K 结果可能大部分都不满足条件，白白浪费检索名额。先过滤再搜索，才能保证召回的都是真正想要的。

4.2 实时更新

RAG 的知识库经常要新增、修改、删除文档，向量索引不是建好就不能动的：主流向量数据库都支持在线写入，新数据进来后增量构建索引，不需要停服重建。

4.3 与关键词检索融合

纯向量检索对精确词语（比如产品型号「GPT-4o」、专有名词）效果不好，所以很多向量数据库同时支持向量检索 + BM25 关键词检索的混合召回，两者互补效果更好。

5 选型建议

产品落地总绕不开"到底选哪个"的问题。选型主要看三个维度：数据规模、部署方式、是否需要混合检索。主流的五个选项逐一过一遍：

  • Chroma：上手最快的选项，Python pip install 后本地内存直接跑，零配置，配合 LangChain / LlamaIndex 原生集成非常方便；现在也支持 Client-Server 模式和云托管，2025 年还加入了 BM25/SPLADE 稀疏向量混合检索。适合快速原型验证和中小规模生产，超大规模（千万级以上）的稳定性和性能还比不过专门为大规模设计的方案；
  • Qdrant：Rust 写的，性能稳、API 简洁、文档完善，Docker 一条命令就能部署；支持分布式模式（分片 + 副本），已有亿级规模的生产案例。作为中小到大规模生产环境的首选，覆盖面广——很多团队先用 Chroma 做原型，上生产再切 Qdrant，是条常见路径；
  • Milvus：支持多种索引类型、有完整的集群方案，国内大厂（字节、小米等）用得最多。适合千万到亿级的分布式场景，但部署运维复杂度也最高，团队需要有人力维护；
  • Pinecone：全托管 SaaS，按用量付费，无需运维，适合快速验证商业化产品。注意数据出境问题——业务数据有合规要求时就不合适了；
  • pgvector：如果项目已经在用 PostgreSQL 且数据量不大，直接装个插件就行，不用引入新组件，查询还能和业务数据做 SQL JOIN，运维成本为零。

把几个常用选项摆在一起对比：

数据库 部署方式 适合规模 混合检索 主要优势 主要劣势
Chroma 本地 / Client-Server / 云 中小规模 支持（BM25 / SPLADE） 零配置上手快，生态集成好 超大规模稳定性待验证
Qdrant 自托管 / 云（支持分布式） 中到大规模（亿级） 支持 性能好、API 简洁、Rust 高性能 超大规模需调优
Milvus 自托管（分布式） 大规模（亿级） 支持 可水平扩展，大厂验证多 部署运维复杂
Pinecone 全托管云服务 中大规模 支持 无需运维，按量付费 费用高，数据出境
pgvector PostgreSQL 插件 中小规模 支持（配合全文检索） 无需新组件，可 JOIN 业务数据 性能弱于专用向量库

6 面试总结

面试官问"什么是向量数据库"，千万不能把它理解成"普通数据库加个向量字段"——那是这道题最典型的雷。完整答题框架分三层：

  1. 先说定义与本质：专门为高维向量相似度搜索设计的数据库，核心能力是 ANN（近似最近邻搜索）；普通关系型数据库的 B-tree 索引对高维向量检索基本失效，这不是加个字段能解决的；
  2. 再讲索引算法：HNSW 多层图导航、召回率高但吃内存（Qdrant/Milvus/Chroma 默认）；IVF 聚类分桶、省内存适合超大规模、需调 nlist/nprobe 参数——这是核心技术点，面试官大概率追问；
  3. 最后给选型：从数据规模、部署方式、是否需要混合检索三个维度回答——原型用 Chroma、中到大规模生产用 Qdrant、超大规模分布式选 Milvus、不想运维上 Pinecone、已有 PostgreSQL 用 pgvector。

如果被追问"你最常踩的选型坑是什么"，答案很现成：别拿 GitHub Star 数量当选型依据——Chroma 的 Star 最多，但超大规模生产场景它并不是最优解，要看数据规模和部署需求；如果被追问混合检索的实现，记得答"向量检索 + BM25 关键词检索并行召回再合并"。
