「RAG」怎么规避语义被切割掉的问题？

0 前言

本文内容整理自公众号「小林面试笔记」的文章 5. 怎么规避语义被切割掉的问题？，用于记录与总结 RAG 相关的核心面试知识点。

「怎么规避语义被切割掉的问题？」，可以这样作答：

语义截断的本质是：一个完整的语义被切成了两半，每一半单独看相关度都不够，检索时直接全军覆没——不是信息丢了，而是被拆散之后没人认得它。规避思路有两条线：一是切的时候别截断——用重叠切割（overlap）兜底，相邻 chunk 保留 10%~20% 的重叠内容，再用语义边界切割顺着句子、段落这类自然边界下刀；二是切完之后把上下文补回来——句子窗口检索（单句向量化、命中后前后几句一起返回）、父子切割（小块检索、大块返回）、命题化切割（用 LLM 把文档拆成天然自包含的命题），以及 Anthropic 的 Contextual Retrieval（向量化之前先让 LLM 看整篇文档、给每个 chunk 生成一句背景说明再入库）。

工程上通常是组合使用：重叠切割做兜底，语义边界切割保切割质量，高质量场景再加父子切割或 Contextual Retrieval。

1 语义被切割是什么问题？

先说清问题本身。上一篇讲 Chunking 时我们提过，固定大小切割可能在句子中间下刀，这里把具体的"事故现场"亮出来。假设文档里有这么一段：

如果 chunk 的边界恰好切在「响应时间不超过 2 小时，」这里，「企业用户享有优先客服通道」和「并可申请专属技术顾问服务」就被分到了两个 chunk。

你可能会想：两个 chunk 里都有部分答案，搜到其中一个不就行了？问题恰恰出在这里——两个 chunk 单独来看相关度都不够高，极可能一个都召回不了，答案就断了。

这就是语义截断的核心问题：不是信息丢了，而是信息被拆散之后，每一半都不够强，检索时全军覆没。理解了这一点，后面的所有方案都是在回答同一个问题——怎么让拆散后的每一半都"够强"。

2 方向一：切的时候别截断

第一个方向很直觉：既然切会切坏，那就切得聪明一点，别在语义中间下刀。这一方向下有两大方案。

2.1 重叠切割（Overlap）

最基础的方案：让相邻 chunk 之间保留一段重叠内容，就算边界恰好切在语义中间，跨边界的内容也一定完整地出现在其中一个 chunk 里。

重叠量通常取 chunk_size 的 10%~20%，比如 chunk_size=800、overlap=150。

你可能会问：为什么不干脆重叠 40%？这是实践摸出来的平衡点：

  • 太小（比如 5%）：重叠区域覆盖不了完整的跨边界语义，保护效果弱；
  • 太大（比如 40%）：重复内容太多，存储和检索成本上升，大量重复还会干扰 LLM 的阅读理解。

需要再次强调：重叠切割只是兜底。它保证跨边界的文字不丢失，却解决不了「一个完整语义被拆散」的根本问题——很多人以为加了 overlap 就万事大吉，面试官最想看到你否定这一点。

2.2 语义边界切割

既然要避免在语义中间截断，最简单的办法就是只在自然的语义边界处切——也就是按句子、段落切。

为什么句子的优先级这么高？因为句子是语言表达意思的最小完整单位：一个句子有主语、谓语、宾语，能独立表达一个意思；而把句子从中间截断，前半截后半截单独看都是残缺的，向量化出来的语义也是扭曲的。

实际操作时，用 NLP 工具（比如 spacy、nltk）识别句子结束位置，然后以句子为单位填充 chunk：一句句往当前 chunk 里加，加满了就封存、开启新的，绝不拦腰截断。对于段落分明的文档，还可以在句子边界的基础上优先在段落边界处切，效果更好。

3 方向二：切完之后补回上下文

切得再聪明，也难免有失手的时候。第二个方向换个思路：切切归切，检索的时候再把上下文补回来。这一方向下方案更多，也更有亮点。

3.1 句子窗口检索（Sentence Window Retrieval）

前两个方案都在「怎么切」上做文章，句子窗口检索直接换了个战场：不追求 chunk 大小，而是让检索粒度细、返回范围宽。

类比一下：在图书馆里你用关键词定位到了某本书里的一句话，但你实际阅读的是这句话所在的整个段落，而不是只拿走那一行。

具体做法是：存储时把文档切成单个句子，每个句子单独向量化，用于精准检索；检索命中某个句子后，并不只返回它，而是把它前后各 N 个句子一起取出来，形成完整的上下文窗口交给 LLM。

好处是两全其美：检索粒度细（单句定位准、相关度高），给 LLM 的内容却是完整上下文，不会因为检索太细导致信息残缺。代价是存储量较大——每个句子都要向量化，记录数等于文档的句子总数。

3.2 父子切割（Parent-Child Chunking）

父子切割我们在上一篇（Chunking 策略）详细讲过：小 chunk 检索命中、大 chunk 内容输出，两者通过 ID 关联。这里只补一个和句子窗口检索的对比，方便面试时串起来讲：

  • 句子窗口检索是"检索命中后动态扩展上下文"，实现简单，但窗口大小不灵活；
  • 父子切割是"提前把父子关系存好"，更结构化的实现，父 chunk 大小可以精确控制，代价是要维护父子 ID 关系、存储翻倍。

一句话：两者思路同源，都是从"检索取到点、生成读到面"出发，只是实现方式不同。

3.3 命题化切割（Propositions-based Chunking）

前面几个方案，要么在"怎么切"上打补丁，要么在"检索后"补上下文。命题化切割想得更远：能不能让每个 chunk 天生就是完整独立的？

做法是：用 LLM 把文档分解成一条条独立的「命题」（Proposition）——每个命题都是一个完整、自包含的陈述句，只包含一个核心事实，单独拿出来就能看懂，不依赖任何上下文。举个例子，原文是：

质量最高，成本也最高——每个 chunk 都要额外调 LLM 来生成命题，适合对检索质量要求极高的核心知识库。

3.4 Contextual Retrieval（Anthropic）

命题化切割是用 LLM 重组 chunk 内容，而 Contextual Retrieval 换了一个角度：不改变 chunk 本身，在向量化之前把缺失的上下文补进去。这是 Anthropic 在 2024 年提出的方案。

先看它要解决的根本问题：chunk 被单独拿出来后，就失去了语境。

chunk 向量化时，Embedding 模型只能看到这段文字本身，不知道它来自哪篇文档、讲的是什么主题。比如：

孤立地看，完全不知道「此条款」指的是什么。你可能会奇怪：向量不是能捕捉语义吗，为什么会丢信息？原因很简单：向量只能编码它"看到"的文字里的语义，它看不到的背景信息，自然无法编码进向量。向量里没有主题信息，正是孤立 chunk 召回质量低的根本原因。

Contextual Retrieval 的核心做法分两步：

  1. 生成 Context：让 LLM 看着整篇原始文档，为每一个 chunk 生成一段简短的背景说明（通常 1~2 句话），说清这个 chunk 在文档中的位置和主题；
  2. 拼接再向量化：把生成的 Context 前置拼到 chunk 前面，然后对这个「Context + chunk」整体做 Embedding 和 BM25 索引。

3.5 成本控制：Prompt Caching

你可能会担心：每个 chunk 都要调一次 LLM，成本得多高？这确实是 Contextual Retrieval 最大的顾虑，但 Anthropic 的 Prompt Caching 特性可以把成本降低 80%~90%。

原理是：同一篇文档的所有 chunk 请求共享相同的前缀（full_document）。开启 Prompt Caching 后，第一次调用把文档内容缓存进 KV Cache，后续同一篇文档的 chunk 请求都复用这份缓存，只有 chunk 部分需要重新计算。

算一笔账就清楚了。一篇文档有 100 个 chunk：传统做法要把整篇文档的 token 重复处理 100 次；开启 Prompt Caching 后，第一次写入缓存时文档部分按 1.25 倍计费（25% 的写入溢价），后续 99 次命中缓存的部分只按正常价的 10% 计费——文档部分的成本整体降到原来的 10%~20%。按 Anthropic 官方参考数据，8k token 的文档配合 800 token 的 chunk，处理一百万文档 token 的总成本大约 1 美元出头，完全可控。

工程效果上，Anthropic 的测评数据显示：Contextual Retrieval 结合 BM25 混合检索，能将检索失败率（Top-20 未命中目标 chunk 的比例）降低约 49%，是目前业界实测效果最显著的 chunk 质量提升方案之一。

4 方案选型对比

把六个方案的核心思路、适用场景和代价放在一张表里，实际选型时对照着挑：

方案 核心思路 适合场景 代价
重叠切割 相邻 chunk 内容重叠 所有场景，基础兜底 存储轻微增加
语义边界切割 在句子/段落边界处切 段落结构清晰的文档 需要 NLP 工具
句子窗口检索 精细检索 + 扩展返回窗口 追求高召回精度 存储量大
父子切割 小块检索、大块返回 通用场景，效果均衡 存储翻倍、索引复杂
命题化切割 LLM 拆解为独立命题 高质量要求、重要知识库 LLM 调用成本高
Contextual Retrieval 向量化前补全背景上下文 文档语境强、chunk 孤立感重的场景 LLM 调用成本（Prompt Caching 可大幅降低）

5 面试总结

面试官问你语义截断，回答不能只停留在"加个 overlap"——那是这道题最明显的扣分点。完整的答题框架分三步：

  1. 先说清问题本质：chunk 被单独拿出来后失去语境，完整语义被拆散，每一半相关度都不够，导致检索召回不到——不是信息丢了，是没人认得它了；
  2. 再分两个方向讲方案：切的时候别截断（重叠切割、语义边界切割），切完之后补回上下文（句子窗口检索、父子切割、命题化切割、Contextual Retrieval）；
  3. 最后落回工程组合：重叠切割兜底 + 语义边界切割保证质量 + 高质量场景再加父子切割或 Contextual Retrieval——能把这套组合思路讲出来，面试官就满意了。

如果被追问"overlap 不是够用了吗"，标准回答：overlap 只是兜底，它能保证跨边界的文字不丢失，但一个完整语义被拆散之后，每一半单独看相关度依然不够，该召回失败还是失败；如果被追问 Contextual Retrieval 的成本问题，记得用 Prompt Caching（成本降 80%~90%、百万 token 约 1 美元）来应答。
