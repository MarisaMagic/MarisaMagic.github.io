「RAG」RAG 在线阶段工作流程

0 前言

本文内容整理自公众号「小林面试笔记」的文章 10. 你使用 RAG 给大模型一个输入，系统是怎样的工作流程？，用于记录与总结 RAG 相关的核心面试知识点。

「你使用 RAG 给大模型一个输入，系统是怎样的工作流程？」，可以这样作答：

RAG 在线流程是一条「检索 → 整理 → 生成」的流水线，用户问题不会直接丢给大模型，而是先经过六步：

① Query 预处理：把口语化、带指代的问题改写成适合检索的形式，常用三种技术——简单改写、HyDE（让 LLM 先假设一个答案、拿假设答案的向量去检索）、多角度扩写（扩展成 3~5 种表述分别检索再合并）；② Query Embedding：把问题向量化，必须用和离线建库时完全相同的 Embedding 模型，否则两边的向量不在同一坐标系，距离计算没有意义；③ 向量检索 + 多路召回：ANN 搜索找 Top-K 相似片段，同时并行做 BM25 关键词检索——向量抓语义、BM25 抓精确词，结果用 RRF 融合；④ Rerank 精排：粗排结果混有噪音，用 Cross-Encoder 把问题和每个候选拼在一起深度打分，最终只留 Top 3-5；⑤ Prompt 拼装：用约束"只根据资料回答、资料里没有就说不知道"抑制幻觉，参考资料编号方便溯源；⑥ 大模型生成 + 溯源：模型基于参考资料作答，答案标注来源可回到原始文档验证。

一句话总结：每一步都在为下一步准备更好的输入，最终目标是让大模型"开卷作答"，而不是凭空发挥。

1 为什么不能直接把问题扔给大模型？

先说为什么需要这套流程。两个直接原因：

  1. 上下文窗口有限：大模型的窗口装不下整个知识库，不可能把全部资料都塞进去；
  2. 没有依据就会编：缺乏外部知识时，模型只靠参数里的记忆回答，容易产生幻觉（这个我们在第二篇讲过）。

所以 RAG 的在线流程本质是一个**「精准取件」**的过程：从海量知识里找到和这个问题最相关的那几段，再让大模型在这个「小范围」里作答——还是第一篇那句老话，给 LLM 开卷考试，只不过这次要仔细说说"翻书"的每一个步骤。

你可能会想：为什么不把用户问题直接拿去向量库里搜，搜完就完了？因为实际业务里，用户的提问往往是口语化的、带指代的、甚至有歧义的，直接拿去检索效果极差。所以整个在线流程按顺序分六步，每一步都在为下一步准备更好的输入。

2 第一步：Query 预处理（Query Rewrite）

为什么把它放在第一步？因为用户原始提问的质量决定了后续所有环节的天花板——输入就差，后面再怎么精排、怎么拼 Prompt 都是白搭。

用户的提问要么口语化、带指代（"上次那个方案怎么样"离开对话上下文完全没法检索），要么用词和知识库文档不一致（直接检索命中率低）。这一步通常让 LLM 对原始问题做改写，常见三种技术：

  • 简单改写：把口语化问题改写成更正式、独立完整的检索句；
  • HyDE（Hypothetical Document Embeddings）：让 LLM 先"假设"一个可能的答案，再用假设答案的向量去检索。你可能会觉得奇怪——不用问题去搜，反而用假设答案去搜？原因在于：问题和答案的用词往往差异很大，但假设答案和真实答案的用词更接近，它们的语义空间天然更匹配，命中率往往更高；
  • 多角度扩写：把同一个问题扩展成 3~5 种不同表述，分别检索后合并结果，覆盖面更广。

3 第二步：Query Embedding（问题向量化）

问题改写好了，下一步把它转换成向量，才能去向量库里搜索。这一步本身很简单，但藏着一个最容易翻车的细节：

必须用和离线建库时完全相同的 Embedding 模型。

为什么？不同 Embedding 模型的训练数据、目标函数、输出维度、向量空间的"形状"都不一样：模型 A 可能让「苹果手机」和「iPhone」的向量落在空间的某个方向，模型 B 则让它们落在完全另一个方向；甚至维度都对不上（A 是 1024 维，B 是 1536 维，根本没法算距离）。用 A 建的库、拿 B 来检索，两边的向量就像在不同坐标系里，距离计算完全没有意义。

类比一下：用经纬度定位，一个系统用的是北京坐标系、另一个用 WGS84 坐标系——数值看起来差不多，实际位置却差了十万八千里。所以一旦换 Embedding 模型，整个知识库必须重建，老向量和新查询不在同一套坐标系里，没法兼容。

4 第三步：向量检索（ANN）+ 多路召回

拿着问题向量，去向量数据库做近似最近邻搜索（ANN），找出相似度最高的 Top-K 个片段。这一步非常快：百万量级的向量库通常几十毫秒就返回结果（索引算法的原理我们上一篇讲过）。

但工程实践里，只用向量检索这一路往往不够，所以这一步通常同时做多路召回：

  • 向量检索负责捕获语义相似性（“找意思接近的”）；
  • BM25 / 全文检索负责捕获关键词精确匹配（“找词面一样的”）。

很多人以为向量检索已经够用了，为什么还要 BM25？因为向量检索对精确词语（产品型号、专有名词、错误拼写）的识别能力弱，而 BM25 对精确匹配更在行。比如用户问"LSTM 和 Transformer 的区别"：向量检索能找到"序列模型对比"相关的语义内容，BM25 能精准命中包含「LSTM」「Transformer」这两个词的文档。

多路结果通过 RRF（Reciprocal Rank Fusion，互倒排名融合） 算法合并——各路结果按排名倒数加权求和，最终召回的覆盖面比单路更广、质量更高。

5 第四步：Rerank 精排

粗排召回的 Top-20 里不可能条条都相关，肯定混了干扰项。Rerank 就是来收拾这个残局的。

向量检索是"粗排"，算的是向量距离，速度快但粗糙。Rerank 模型采用 Cross-Encoder 结构：把用户问题和每个候选片段拼在一起输入，深度理解它们之间的语义匹配程度，重新打分排序，最后只保留 Top-3 到 Top-5 的高质量片段，把噪音过滤掉。

你可能会问：为什么不直接用 Rerank 模型检索，还要先粗排再精排？因为 Cross-Encoder 要把查询和每个候选拼起来过一遍模型，计算量比向量检索大得多——拿它对百万条数据逐一算分，延迟完全不可接受。所以工程上采用**「粗排筛到几十条，精排再从几十条里挑最好的几条」的两阶段策略**，兼顾速度和质量。Rerank 整体耗时几百毫秒以内，对用户体感影响不大，质量提升却非常明显。

6 第五步：Prompt 拼装

这个 Prompt 看起来简单，但每一条指令都有明确的工程意图：

  • 「只根据资料回答」：抑制模型凭记忆发挥的倾向——大模型天生爱"帮忙"，你问什么它都想着回答，哪怕资料里没有；
  • 「资料里没有就说不知道」：防止它在信息不足时强行补全、编出幻觉内容；
  • 「参考资料带编号」：为后续引用溯源做准备，让用户知道每句话的依据来自哪份资料。

很多人以为把检索结果丢给大模型就行了，其实 Prompt 拼得不好，大模型一样会乱回答。

7 第六步：大模型生成 + 溯源

大模型拿到 Prompt 后，基于参考资料生成答案。到这一步，在线流程的核心工作就完成了，工程上还会要求模型在答案里标注每句话的来源（比如"根据资料[1]…"）。

这一步容易被人忽视，但它非常关键：大模型即使在有参考资料的情况下，依然可能过度发挥或误读资料，溯源让用户有能力判断哪些内容是可靠的、哪些需要再确认——这也是 RAG"答案可溯源"价值的最后一公里。

把整个链路串起来，在线阶段的耗时分布大概是：Query 改写几十毫秒 → 向量检索几十毫秒 → Rerank 几百毫秒 → Prompt 组装可忽略不计 → 大模型生成 1~10 秒（取决于输出长度，是最耗时的一环）。常见的工程优化手段：缓存高频 Query 的检索结果，以及把向量检索和 BM25 并行执行，让两路召回的延迟从"串行叠加"变成"取最大值"。

8 面试总结

面试官问"RAG 在线流程是怎样的"，不能只说「检索 + 生成」四个字就完事——这就像别人问"一顿饭怎么做"，你回答"买菜和做饭"，中间的洗菜、切菜、调味、火候一个都没提。正确回答按顺序把六步讲清楚：

  1. Query 预处理（改写、HyDE、多角度扩写），把口语化问题转成适合检索的形式；
  2. Query Embedding，必须用和建库时相同的模型；
  3. 向量检索 + 多路召回，向量和 BM25 各有所长，RRF 融合结果；
  4. Rerank 精排，Cross-Encoder 深度理解语义，过滤粗排噪音；
  5. Prompt 拼装，约束"只根据资料回答、不知道就说不知道"；
  6. 生成 + 溯源，标注引用来源提升可信度。

每个环节的干什么、为什么需要、有什么工程细节都要能说清楚，面试官就知道你的理解不只在表面。

如果被追问"HyDE 为什么有效"，标准回答是：问题与答案的用词空间差异大，假设答案与真实答案的用词更接近，用假设答案的向量检索命中率更高；如果被追问"Rerank 为什么不能直接检索"，答案是Cross-Encoder 计算量太大，必须先粗排把候选缩到几十条再做两阶段精排。
