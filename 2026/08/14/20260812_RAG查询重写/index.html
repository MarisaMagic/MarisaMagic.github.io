「RAG」如何润色用户的 Query（Query Rewrite）？目的是什么？

0 前言

本文内容整理自公众号「小林面试笔记」的文章 12. 如何润色用户的 Query（Query Rewrite）？目的是什么？，用于记录与总结 RAG 相关的核心面试知识点。

「如何润色用户的 Query（Query Rewrite）？目的是什么？」，可以这样作答：

目的是弥合用户提问和知识库文档之间的「语义鸿沟」：用户的问题口语化、模糊、带缩写和指代，而文档是正式书面语，两者在向量空间里的"坐标"天然离得很远，导致该召回的内容没被召回。常见四种方法：

一是直接改写，让 LLM 把口语化问题改写成更精准的书面检索表述，同时补全指代和上下文，适合多轮对话场景；二是 HyDE，先让 LLM 生成一段"假设答案"、用假设答案的向量去检索——因为答案到答案的向量距离比问题到答案近得多，假设答案只充当"风格像文档"的检索代理，解决问句与陈述句的文体差异；三是 Step-back Prompting，把太具体的问题向上升级成背景问题，先检索背景原理再作答（如"HNSW ef 参数设多少合适"→"HNSW 索引的参数调优原则"）；四是多 Query 扩展，把问题改写成 3~5 个不同角度分别检索、合并去重，像拦截网一样提升覆盖面。

一句话选型口诀：口语化用直接改写，文体差异用 HyDE，问题太具体用 Step-back，角度单一用多 Query 扩展。

1 为什么需要 Query Rewrite？

先看它要解决的问题。用户在说话，文档在写话，这两者之间存在一道天然的表述鸿沟：

  • 用户可能这样问：「这东西坏了咋整」，而文档里写的是「产品故障排查与维修指南」；
  • 你可能会想：这两句话意思差不多，向量检索应该能匹配上吧？

遗憾的是，实际效果往往不如预期——即便语义相关，向量相似度也可能低到召回不了正确文档，因为口语和书面语在向量空间里的「坐标」差距不小。

上一讲（在线工作流程）我们说过：用户提问的质量决定了后续所有环节的天花板。Query Rewrite 就是在检索之前先对问题做加工，让它在向量空间里离正确文档更近——相当于出发前先校准导航：目的地不变，但路线更准。

接下来看具体怎么做，四种方法各有各的"用武之地"。

2 方法一：直接改写（Query Rewriting）

表述鸿沟最简单的形态，就是口语化。把所有口语化、模糊的表达改写成更精准、更书面化的检索表述，这是最基础的改写方式——「这东西咋退」和「申请退款的操作流程」在向量空间里不是同一个邻居，改写就是把前者的向量拉近到后者。

顺带还能做两件事：补全上下文（"这个功能"改写成具体功能名称）、处理代词指代（多轮对话里的模糊引用变成检索可识别的具体词汇）。给 LLM 的 Prompt 长这样：

但直接改写有个绕不过去的天花板：问题也好、文档也罢，本来就是不同的文体——一个是疑问句、一个是陈述句。就算把问题改写得再规范，它在向量空间里还是"问句"的坐标，而文档是"陈述句"的坐标，两类文体之间天然有距离。这个问题，催生了 HyDE。

3 方法二：HyDE（Hypothetical Document Embeddings）

HyDE 的直觉可以这样理解：正常是用"问题的影子"去找答案的样子，HyDE 先描绘出答案可能长什么样，再去找长得像它的文档——先让 LLM 根据用户问题生成一段「假设性的答案」，再用这段假设答案的向量去检索。

第一次听说的人多半会觉得奇怪：让 LLM 生成一个可能不准确的答案，再用它去检索，不是多此一举吗？其实不然，关键在于向量空间里的一条规律：

答案到答案的距离，比问题到答案的距离近得多。

假设答案不需要准确，只需要**「风格像文档」**就够了——它的作用是充当一个向量上更好的「检索代理」。用原始问题检索是"拿着问题的影子找答案"，用假设答案检索是"拿着答案的画像找答案"，命中率自然天差地别。生成假设答案的 Prompt：

（我们在第 10 篇在线流程里提过 HyDE 的江湖地位，这篇算是把它讲透了。）HyDE 解决的是「文体差异」，但还有一类情况是改写和 HyDE 都处理不好的——问题太具体，知识库里没有直接答案，只有背景原理。这就轮到 Step-back 登场。

4 方法三：Step-back Prompting（后退提问）

有些问题涉及具体细节，知识库里没有直接对应的答案，但有背景原理文档。Step-back 把具体问题"后退一步"，提升到更抽象的层次，先检索背景知识，再结合背景知识回答具体问题。

类比一下就很直观：做一道数学题，不是一上来就硬套公式，而是先想想「这道题用的是哪种定理」，再用定理解题。知识库里可能没有「ef 参数设 100 是否合适」的直接答案，但一定有「HNSW 参数调优原则」这样的背景文档——把具体问题后退成背景问题，才能找到真正有用的参考资料。生成"后退版本"的 Prompt：

效果示例：具体问题「Qdrant 的 HNSW ef 参数设多少合适」→ 后退问题「HNSW 索引的参数调优原则是什么」。后退后的问题能命中更多通用背景文档，让 LLM 生成有原理支撑的答案。

5 方法四：多 Query 扩展

前面三种方法都在「一个问题」上做文章——要么改写它、要么给它配个假设答案、要么把它抽象化。但有时候问题角度本身就窄，用一个角度去检索，覆盖面不够。这时候换个思路：不求一个问题改得更好，而是多生成几个不同角度的问题。

用 LLM 把用户原始问题改写成 3~5 个不同角度的版本，分别去检索，再把所有结果合并去重。核心思路是：只要有一个改写版本和文档的表述对上了，就能把正确的内容召回来——就像拦截网越宽，捕到鱼的概率越高。适合用户提问风格多变、和文档表述差异大的场景，代价是多几次 LLM 调用。

6 方法对比与选型

把四种方法放在一起对比，各自的定位一目了然：

方法 解决的核心问题 额外开销 适合场景
直接改写 口语化、指代不清、上下文丢失 1 次 LLM 调用 多轮对话场景
HyDE 问题和文档文体风格差异大 1 次 LLM 调用 专业知识库、文体差异明显
Step-back 具体问题需要背景知识辅助 1 次 LLM 调用 技术文档、需要原理支撑的场景
多 Query 扩展 单一角度覆盖不全 N 次 LLM 调用 答案涉及多个维度的复杂问题

7 面试总结

这道题的最大扣分点是只说一种方法——"把口语转书面语"是标配答案，但对不了几招。完整的答题框架分两层：

  1. 先说目的：Query Rewrite 不是"把口语转成书面语"这么简单，它的核心是弥合用户提问和文档表述之间的语义鸿沟，而这道鸿沟有四种不同形态；
  2. 再按鸿沟形态配方法：口语化表达用直接改写、文体差异用 HyDE、问题太具体用 Step-back、角度单一用多 Query 扩展——让面试官看到你理解了"不同场景需要不同策略"。

如果被追问"改写之后还是对不上怎么办"，标准回答是顺着鸿沟形态走一遍：改写解决口语化 → 对不上可能是文体差异（上 HyDE）→ 再不行可能是问题太具体（上 Step-back）→ 角度太窄就用多 Query 扩展；如果被追问"四种方法什么时候组合使用"，答：多轮对话里改写和 HyDE 可以串用（先改写再假设答案），复杂问题四者可以并行、按各自召回合并结果。
